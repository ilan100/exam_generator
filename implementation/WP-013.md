# 2. Objective

Implement the control layer that turns generation and validation into a reliable **single-question production cycle**.

The flow becomes:

```text
generate candidate
       ↓
run required validators
       ↓
evaluate deterministic acceptance policy
       ↓
   ┌───────────┐
   │ accepted? │
   └───────────┘
      ↓     ↓
     YES    NO
      ↓      ↓
   return   regenerate
           if attempts remain
```

WP-013 owns:

* running the required validators for a candidate;
* deterministic candidate acceptance;
* bounded generation attempts;
* recording each attempt and its validation outcomes;
* returning an accepted candidate or a clear exhausted-attempts result/error.

It does not yet generate a complete exam.

---

# 3. Core Principle

The LLM must **not decide whether its own candidate is accepted**.

Acceptance is application policy implemented deterministically in Python from the independent validation results.

Conceptually:

```text
CandidateQuestion
      ↓
GroundingValidationResult
MCQValidationResult
CategoryValidationResult
QualityValidationResult
TextbookCheckResult
      ↓
deterministic Python policy
      ↓
ACCEPT / REJECT
```

Do not ask another LLM:

```text
"Considering all validators, should we accept this?"
```

---

# 4. Acceptance Policy

For V1, a candidate is acceptable only when all **primary validators** pass:

```text
Grounding  = PASS
MCQ        = PASS
Category   = PASS
Quality    = PASS
```

The textbook check is secondary.

Therefore textbook status must **not** be treated as another mandatory `passed=True` validator.

Use the actual existing `TextbookCheckStatus` values.

The policy should be:

```text
CONSISTENT
    → does not block acceptance

NOT_FOUND
    → does not block acceptance

POTENTIAL_CONFLICT
    → blocks acceptance
```

This preserves the architecture established in WP-012:

> textbook support is useful secondary evidence, but lack of textbook evidence does not invalidate an otherwise grounded candidate.

A potential textbook conflict, however, is a sufficient reason not to accept the candidate automatically.

Document this policy explicitly.

---

# 5. Validation Order

Use a deterministic validation order.

Recommended:

```text
1. Grounding
2. MCQ
3. Category
4. Quality
5. Textbook
```

For V1, run the complete required validation set for each successfully generated candidate rather than short-circuiting after the first negative verdict.

Reason:

```text
Grounding FAIL
MCQ       FAIL
Category  PASS
Quality   FAIL
```

is much more diagnostically useful than recording only the first failure.

This information will also be valuable for future audit and quality analysis.

Operational failure is different: if a validator cannot execute because of an LLM/provider/prompt/system error, do not fabricate the remaining results.

---

# 6. Validation Bundle

Introduce a small immutable result representing all validation outcomes for one candidate.

Conceptually:

```python
CandidateValidationResults(
    grounding=...,
    mcq=...,
    category=...,
    quality=...,
    textbook=...,
)
```

The exact name is an engineering decision.

It should expose deterministic acceptance evaluation, either directly or through a separate policy function.

Do not modify the five existing validator result models.

---

# 7. Acceptance Decision

Keep the acceptance calculation explicit and easy to inspect.

Conceptually:

```python
accepted = (
    grounding.passed
    and mcq.passed
    and category.passed
    and quality.passed
    and textbook.status != TextbookCheckStatus.POTENTIAL_CONFLICT
)
```

Use the actual current model fields/enums.

Do not introduce weighted scores such as:

```text
grounding × 0.4
quality × 0.2
...
```

Do not use confidence thresholds unless an existing project requirement explicitly establishes one.

V1 acceptance should be rule-based and explainable.

---

# 8. Single-Question Production Interface

Create a focused control-layer interface conceptually similar to:

```python
produce_question(
    *,
    category: str,
    generation_mode: GenerationMode,
) -> ...
```

It should coordinate the existing:

* `QuestionGenerator`;
* `GroundingValidator`;
* `MCQValidator`;
* `CategoryValidator`;
* `QualityValidator`;
* `TextbookValidator`.

Dependencies must be injectable for tests.

The exact class/module naming is Claude's engineering decision.

Do not place this logic inside `QuestionGenerator`.

Generation and control/orchestration remain separate responsibilities.

---

# 9. Attempts

A production cycle may generate more than one candidate when validation rejects earlier candidates.

The number of attempts must be bounded by configuration.

Inspect existing configuration first.

If no suitable generation-attempt setting already exists, add a small explicit configuration value such as:

```yaml
generation:
  max_attempts: 3
```

or place it in the configuration location that best matches the established config architecture.

Do not hard-code the attempt limit deep inside orchestration code.

Requirements:

```text
max_attempts >= 1
```

Reject invalid configuration.

Do not add elaborate retry configuration.

---

# 10. Attempt Semantics

One attempt means:

```text
one CandidateQuestion generation
        +
its validation cycle
```

For example, with:

```text
max_attempts = 3
```

the sequence may be:

```text
Attempt 1 → generated → validation FAIL
Attempt 2 → generated → validation FAIL
Attempt 3 → generated → validation PASS
                                  ↓
                               accepted
```

or:

```text
Attempt 1 → FAIL
Attempt 2 → FAIL
Attempt 3 → FAIL
                 ↓
             exhausted
```

Stop immediately after the first accepted candidate.

Never exceed `max_attempts`.

---

# 11. Validation Failure vs Operational Failure

This distinction remains critical.

A candidate receiving:

```text
grounding.passed = False
```

is a **normal rejected attempt** and may lead to regeneration.

Likewise for:

* MCQ failure;
* category failure;
* quality failure;
* textbook `POTENTIAL_CONFLICT`.

By contrast:

```text
OpenAI connection failure
invalid structured response
prompt-loading failure
retrieval infrastructure failure
```

is an **operational failure**.

Do not automatically consume the remaining generation attempts trying to hide infrastructure failures.

Unless an existing project requirement says otherwise, propagate operational failures immediately.

`max_attempts` controls candidate-quality regeneration, not API resilience.

---

# 12. Attempt Record

Preserve the result of every successfully generated candidate attempt.

Conceptually:

```python
QuestionAttempt(
    attempt_number=1,
    candidate=...,
    validations=...,
    accepted=False,
)
```

Requirements:

* 1-based attempt number;
* candidate preserved;
* validation results preserved;
* deterministic accepted/rejected status;
* immutable/read-only where practical.

This becomes important later for audit output.

Do not discard failed candidates internally once they have been fully evaluated.

---

# 13. Production Result

Return enough information for later exam orchestration and audit.

A successful result should contain conceptually:

```text
accepted CandidateQuestion
all attempts leading to it
```

For example:

```python
QuestionProductionResult(
    candidate=accepted_candidate,
    attempts=(attempt1, attempt2, attempt3),
)
```

Exact naming is flexible.

Do not return only the final candidate and lose attempt history.

---

# 14. Exhausted Attempts

If all allowed attempts are valid executions but all candidates fail acceptance, fail clearly.

A project-specific error such as:

```text
QuestionAttemptsExhaustedError
```

is appropriate.

The error/result must preserve enough information for later diagnostics, ideally the completed attempt records.

Do not return the last rejected candidate as though it were accepted.

Do not silently relax acceptance criteria on the final attempt.

---

# 15. Regeneration Behavior

For WP-013, regeneration may simply call the existing WP-009 generation path again with the same:

```text
category
generation_mode
```

Do not yet implement sophisticated validator-feedback prompts.

Do not dynamically rewrite the generation prompt with:

```text
"Your previous answer failed because..."
```

unless such feedback infrastructure already exists, which it currently should not.

The first goal is to establish **bounded validated regeneration**, not optimize it.

This also gives us an honest baseline for how often repeated independent model generations pass.

---

# 16. Generation Mode

The requested generation mode remains constant across attempts.

If the caller requests:

```text
STYLE_SIMILAR
```

all attempts remain `STYLE_SIMILAR`.

Do not automatically switch to `INDEPENDENT` after failure.

Likewise, do not change categories.

Retry policy must not silently alter the user's requested question specification.

---

# 17. Historical Reference Behavior

WP-009 currently uses deterministic historical-reference selection.

Do not redesign it in WP-013 merely because multiple attempts may therefore use the same style reference.

That is acceptable for this control-layer baseline.

Exam-level style diversity and improved historical-reference rotation can be addressed later when multiple questions are orchestrated.

---

# 18. No Exam-Level Diversity Yet

Despite earlier planning language around "diversity/retry," WP-013 should **not** implement broad exam-level diversity logic.

Do not yet attempt to enforce:

* semantic uniqueness across an exam;
* duplicate-question similarity thresholds;
* answer-position balancing across many questions;
* historical-reference rotation across an exam;
* category-distribution orchestration.

Those require visibility into multiple accepted questions and belong naturally with WP-014 exam orchestration or a focused follow-up if needed.

WP-013 owns **single-question acceptance and bounded regeneration**.

# 19. Tests

Add focused tests covering at minimum:

### Acceptance

* all primary validators pass + textbook `CONSISTENT` → accepted;
* all primary validators pass + textbook `NOT_FOUND` → accepted;
* grounding failure → rejected;
* MCQ failure → rejected;
* category failure → rejected;
* quality failure → rejected;
* textbook `POTENTIAL_CONFLICT` → rejected.

### Attempts

* first candidate accepted → exactly one generation attempt;
* first rejected, second accepted → exactly two attempts;
* acceptance stops further generation;
* attempt numbering is 1-based;
* failed candidate records are preserved;
* validation results are preserved for every completed attempt;
* maximum attempts is never exceeded;
* all rejected → exhausted-attempts failure;
* exhaustion preserves diagnostic attempt history.

### Operational behavior

* all five validators run for a normally generated candidate even if an early validator returns a negative verdict;
* validator order is deterministic;
* operational generator failure propagates;
* operational validator failure propagates;
* operational failure does not trigger quality regeneration;
* generation mode/category remain unchanged between attempts;
* no validator or candidate is mutated;
* no feedback prompt or hidden acceptance LLM is introduced.

Use mocks/fakes for all LLM-dependent components.

Run the full suite offline.

# 22. Acceptance Criteria

WP-013 is complete when:

1. All five existing validators can be coordinated for one candidate.
2. Candidate acceptance is deterministic Python policy.
3. Grounding, MCQ, category, and quality must pass.
4. Textbook `NOT_FOUND` does not block acceptance.
5. Textbook `POTENTIAL_CONFLICT` blocks acceptance.
6. Negative validator verdicts trigger rejection rather than operational errors.
7. Rejected candidates can cause bounded regeneration.
8. Attempt count is configuration-controlled and validated.
9. The first accepted candidate stops further attempts.
10. The attempt limit is never exceeded.
11. Every completed attempt preserves candidate and validation results.
12. Exhaustion never returns a rejected candidate as accepted.
13. Operational failures propagate instead of causing blind regeneration.
14. Category and generation mode remain stable across attempts.
15. No LLM decides overall acceptance.
16. No validator-feedback prompting is introduced.
17. No exam-level diversity/orchestration is implemented.
18. Unit tests are offline.
19. Full regression suite passes.
20. One live production-cycle smoke test is executed if an API key is available.
21. Documentation/status is updated.
22. WP-014 has not been started.
