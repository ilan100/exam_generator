# 2. Objective

Implement the provider-independent LLM infrastructure and the first concrete provider implementation using OpenAI.

The desired boundary is:

```text
Application / future generation / future validation
                    ↓
              LLM abstraction
                    ↓
             OpenAI provider
                    ↓
               OpenAI API
```

Later application code must depend on the abstraction rather than importing or constructing OpenAI clients directly.

WP-007 establishes:

* provider-independent LLM request/response infrastructure;
* structured-output support using Pydantic models;
* separate generation and validation execution profiles;
* OpenAI provider implementation;
* provider factory/construction;
* API-key handling at provider construction/use boundary;
* deterministic configuration plumbing;
* clear LLM/provider error handling;
* mocked unit tests;
* one optional/manual live smoke-test mechanism.

WP-007 must NOT implement:

* production neuroanatomy prompts;
* question generation;
* grounding validation;
* MCQ validation;
* category validation;
* textbook validation;
* diversity/retry control;
* exam orchestration;
* production exam/audit writing;
* CLI commands.

# 3. Architectural Boundary

The project already requires the runtime LLM provider/model to be externally configurable and replaceable.

Application logic must not depend directly on OpenAI.

The following future code should be possible conceptually:

```python
result = llm.generate_structured(
    messages=...,
    response_model=SomePydanticModel,
    profile=...,
)
```

without the caller knowing whether the provider is OpenAI or another future provider.

Do not scatter:

```python
from openai import OpenAI
```

through application modules.

Only the OpenAI provider implementation and tightly related provider-specific tests may directly depend on the OpenAI SDK.

# 6. Structured Output Is Mandatory

The project already has Pydantic domain contracts and future LLM outputs must be machine validated.

The LLM abstraction must therefore support:

```text
Pydantic response model
        ↓
provider structured-output mechanism
        ↓
validated Pydantic object
```

Do not build future application behavior around manually parsing arbitrary prose.

Do not use:

```python
json.loads(response_text)
```

as the primary structured-output mechanism if the installed OpenAI SDK provides native Pydantic/schema structured-output support.

Prefer the current official OpenAI structured-output API supported by the installed SDK.

The abstraction must return a validated instance of the requested Pydantic response model.

# 7. Generic Structured Response Models

The provider abstraction must work with arbitrary Pydantic response models supplied by later WPs.

For example:

```python
class ExampleResponse(BaseModel):
    value: str
```

A caller should be able to request:

```text
response_model = ExampleResponse
```

without modifying the LLM infrastructure.

Do not hard-code:

* `CandidateQuestion`;
* `GroundingValidationResult`;
* `MCQValidationResult`;
* any particular future response model

inside the provider.

Those models will be supplied by later application layers.

# 8. Public LLM Interface

Create a focused LLM package.

Suggested structure:

```text
src/exam_generator/llm/
    __init__.py
    errors.py
    models.py
    provider.py
    factory.py
    openai_provider.py
```

Exact separation may vary slightly if justified.

Expose a small provider-independent interface.

Conceptually:

```python
class LLMProvider(Protocol):
    def generate_structured(
        self,
        *,
        messages: ...,
        response_model: type[T],
        profile: LLMProfile,
    ) -> T:
        ...
```

A small abstract base class instead of `Protocol` is acceptable if there is a clear reason.

Do not over-engineer a generic AI framework.

# 9. Message Representation

Introduce a provider-independent representation of prompt messages.

At minimum support the roles needed by future prompting:

```text
system
user
```

Supporting:

```text
assistant
```

is acceptable and useful if implemented cleanly.

Do not expose OpenAI SDK message objects as the application's public contract.

Conceptually:

```text
LLMMessage
    role
    content
```

Requirements:

### role

Use a constrained enum or literal set.

Do not allow arbitrary role strings if avoidable.

### content

* required string;
* non-empty;
* whitespace-only rejected;
* Unicode preserved exactly.

The representation must safely preserve:

* Hebrew;
* English;
* mixed Hebrew/English content;
* source evidence text.

Do not translate, normalize, or rewrite message content.

# 10. Message Sequence

Reject an empty message sequence before making a provider call.

Preserve caller-supplied message order exactly.

Do not automatically insert a hidden system prompt in WP-007.

Production system prompts belong to WP-008.

# 11. LLM Profiles

Generation and validation are different LLM operations and already have separate configuration sections.

Introduce an explicit provider-independent execution-profile concept containing exactly the currently supported roles:

```text

VALIDATION
```

A string-backed enum such as:

```python
LLMProfile.GENERATION
LLMProfile.VALIDATION
```

is appropriate.

Do not add speculative profiles.

# 12. Profile Configuration

Conceptually:

```text
    -> llm.yaml validation configuration
```

# 14. Temperature Compatibility

Different OpenAI model families may support different parameter sets.

The configured model must remain replaceable.

Therefore:

* do not assume every model supports every optional parameter;
* do not silently rewrite configuration;
* do not implement a large model-capability registry in WP-007.

Use the simplest behavior supported by the current configured model and official SDK.

If the actual configured model rejects an established optional parameter such as temperature during the live smoke test, report the incompatibility.

Do not build speculative model-specific branching without evidence.

# 15. Provider Construction

Provide a clean construction API conceptually equivalent to:

```python

```

The factory should inspect:

```text

```

and construct the appropriate implementation.

For WP-007, the only supported provider is:

```text

```

Unknown providers must fail clearly.

Do not silently fall back to OpenAI.

The factory boundary should make adding a future provider possible without modifying generation/validation application code.

# 16. API Key Handling

The OpenAI API key must come from:

```text
OPENAI_API_KEY
```

Do not place it in:

* `config/llm.yaml`;
* Python source;
* tests;
* committed files;
* logs;
* error messages.

WP-001 deliberately did not require the API key during normal application configuration loading.

Preserve that decision.

Therefore:

```text
load configuration
```

must still work without `OPENAI_API_KEY`.

The key becomes required only when constructing or invoking the OpenAI provider, according to the chosen clean implementation boundary.

Preferred behavior:

```text
build OpenAI provider
    ↓
validate OPENAI_API_KEY exists
    ↓
construct client
```

Missing key must produce a clear project-specific error.

# 20. Structured Request Execution

The OpenAI provider should conceptually:

1. receive provider-independent `LLMMessage` objects;
2. preserve their order/content;
3. convert them to the SDK request representation;
4. select configured generation/validation parameters;
5. request structured output matching the supplied Pydantic response model;
6. obtain the parsed/validated response;
7. return the Pydantic object.

Do not expose raw SDK response objects to normal application callers.

---

# 21. Parsed Response Validation

A successful call must produce an instance of:

```text
response_model
```

If the provider/SDK returns no parsed structured response, fail clearly.

Do not return:

* `None`;
* arbitrary dictionary;
* raw JSON string;
* raw prose

when the caller requested a Pydantic response model.

The application layer should be able to trust the type boundary.

---

# 22. Refusals

The OpenAI structured-output API may expose model refusals separately from successful parsed output.

Handle refusals explicitly.

A refusal must:

* not be treated as a valid structured result;
* produce a project-specific LLM error;
* preserve a concise refusal diagnostic where available;
* not leak huge raw provider payloads.

Do not attempt to parse refusal prose into the requested response model.

---

# 23. Empty / Missing Responses

Handle expected cases where the provider returns:

* no choices/output;
* missing parsed object;
* otherwise unusable structured response.

Raise a clear project-specific response error.

Do not allow later generation code to encounter unexplained `NoneType` errors.

# 24. Error Model

```text
LLMError
    LLMConfigurationError
    LLMProviderError
    LLMAuthenticationError
    LLMRateLimitError
    LLMResponseError
    LLMRefusalError
```

Requirements:

* authentication failure is distinguishable;
* rate-limit failure is distinguishable;
* malformed/missing structured response is distinguishable;
* refusal is distinguishable;
* common OpenAI SDK boundary exceptions should not be the only diagnostic callers receive.

Do not catch every possible exception.

# 26. No Automatic Retry

Do not add provider-level retries beyond unavoidable/default SDK behavior unless explicitly required by the SDK.

Prefer configuring the OpenAI client to avoid hidden application-level retry semantics if the SDK's default retries would make later retry accounting misleading.

Inspect the installed SDK behavior.

If the SDK automatically retries by default, explicitly decide whether to:

1. disable SDK retries for deterministic application-level attempt accounting; or
2. retain them as transport-level retries.

Preferred architecture for this project:

```text
provider call = one logical application LLM call
```

and future generation attempts are controlled outside the provider.

Small transport retries may be acceptable only if clearly documented and invisible to semantic generation-attempt accounting.

Record the decision in `ARCHITECTURE.md`.

Do not implement semantic retry loops here.
