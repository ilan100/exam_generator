WP-032 begins the V2 architecture.

The project's primary capability is no longer considered to be:

    Generate Exam

The new primary capability is:

    Generate Next Question For Category

Exam generation becomes a client of this capability.

This work package is an architectural refactoring.

Generation behavior should remain unchanged.

No generation-quality improvements belong in this WP.

---

# 1. Objective

Introduce a new top-level service whose responsibility is:

Given:

- a category
- the questions already accepted for that category

produce:

- one additional accepted question
- or an honest failure

This becomes the project's primary public generation API.

---

# 2. New Request Contract

Introduce a new immutable request model.

Example structure:

```json
{
    "category": "...",

    "existing_questions": [
        ...
    ],

    "generation_options": {
        "difficulty": "...",
        "style": "..."
    }
}
```

generation_options may initially contain only default values.

The contract should be designed for future extension.

Do not over-engineer.

---

# 3. New Response Contract

Introduce a new response model.

Example:

```json
{
    "accepted": true,

    "question": {...},

    "attempts": 2,

    "generation_metadata": {...}
}
```

The response should expose the outcome of a single generation request.

Reuse existing models whenever possible.

Avoid duplication.

---

# 4. CategoryGenerationService

Introduce a new service.

Suggested name:

CategoryGenerationService

Responsibilities:

- receive request
- determine generation context
- invoke existing production pipeline
- return exactly one question

This service becomes the project's primary API.

---

# 5. Existing Questions

The request contains previously accepted questions.

Initially:

Pass them unchanged to the generation layer.

Do NOT yet summarize them.

Do NOT yet extract concepts.

Do NOT yet compute diversity.

Those belong to future work packages.

WP-032 is an architectural refactoring only.

---

# 6. Reuse Existing Pipeline

Do NOT duplicate logic.

Reuse:

- QuestionProducer
- Relationship model
- Competitor discovery
- Validation
- Retry behavior
- Acceptance policy

WP-032 should mainly reorganize orchestration.

---

# 7. Exam Generator

Refactor the current exam generator.

It should become nothing more than:

for each category:

    while category requires more questions:

        call CategoryGenerationService

No generation logic should remain inside exam orchestration.

---

# 8. CLI

The current CLI must continue working.

Its implementation should simply invoke the new service repeatedly.

No user-visible behavior change.

---

# 9. Tests

Add tests covering:

- request model
- response model
- CategoryGenerationService
- exam generator delegation
- backward compatibility
- unchanged retry behavior
- unchanged validation behavior

Regression suite must pass.

---

# 10. Evaluation

Run one focused category generation.

Input:

- category
- zero existing questions

Generate one question.

Then repeat using:

- one existing question

Then:

- two existing questions

Then:

- three existing questions

Confirm:

- API behaves correctly
- generation still succeeds
- output contract remains valid

This is an architectural smoke test.

No diversity evaluation yet.

---

# 11. Acceptance Run

Perform one acceptance run.

For every canonical category:

Generate exactly two questions.

However:

Do NOT use the legacy exam-generation entry point.

Instead:

Create a category request.

Call CategoryGenerationService.

Append the accepted question.

Repeat.

This acceptance run verifies that the new architecture can completely replace the previous orchestration.

---

# 12. Success Criteria

Success means:

- identical generation quality
- identical validation
- identical retry behavior
- identical acceptance policy

while replacing the project's public generation architecture.

Behavior should remain unchanged.

---

# 13. Scope Exclusions

Do NOT:

- improve diversity
- summarize previous questions
- extract concepts
- implement distinguishing facts
- redesign prompts
- redesign validators
- redesign retrieval
- redesign competitors
- redesign relationships

Those belong to later work packages.
