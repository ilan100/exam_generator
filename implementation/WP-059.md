# WP-059 — Identity-First Candidate Discovery Across Remaining Targets

## 1. Objective

WP-058 is accepted and the language thread is closed.

The project should now return to the main exam-generation architecture problem:

> **Generation reliability is uneven across targets because the LLM implicitly chooses the question strategy, and some targets repeatedly perform poorly under the default property-generation path.**

The project now has a permanent `IDENTITY_FIRST` strategy for three targets:

```text
גרעיני הבסיס + Caudate Nucleus
    → IDENTITY_FIRST

גרעיני הבסיס + Nucleus Accumbens
    → IDENTITY_FIRST

גרעיני הבסיס + Globus Pallidus
    → IDENTITY_FIRST
```

The remaining targets/categories still use:

```text
DEFAULT
```

unless explicitly mapped.

WP-059 must **not** blindly expand `IDENTITY_FIRST`.

Instead, WP-059 performs a systematic, evidence-based discovery pass across the remaining project targets to answer:

> **Are there additional target/category pairs for which historical evidence justifies a controlled identity-first experiment?**

This is a **diagnostic and candidate-selection WP**, not a production strategy implementation WP.

---

# 2. Why WP-059 Is Needed

The existing architecture has established the following pattern:

```text
Target
    ↓
implicit LLM strategy selection
    ↓
property / classification / identity / other question shape
    ↓
validation
    ↓
retry
```

For some targets, the implicit strategy selection is unreliable.

The successful sequence established by WP-052 → WP-053 → WP-054 and WP-055 → WP-056 → WP-057 is:

```text
historical evidence
    ↓
candidate strategy hypothesis
    ↓
controlled experiment
    ↓
architectural decision
    ↓
narrow permanent implementation
```

Three targets now have permanent identity-first mappings.

WP-059 determines whether there are other targets worth putting through the same process.

---

# 3. Critical Boundary

WP-059 must NOT:

```text
add any new target to IDENTITY_FIRST
modify the permanent strategy mapping
change QuestionGenerator behavior
change QuestionProducer
change prompts
change validators
change retrieval
change schemas
change retry budget
change target representation
change source authority
```

The only permitted production change is:

```text
NONE
```

unless an unavoidable tooling/evaluation artifact is required outside `src/`.

A candidate identified by WP-059 is **not approved for production**.

Candidate discovery is evidence only.

# 4. Architectural Question

The exact question for WP-059 is:

> **Which currently DEFAULT target/category pairs, if any, show sufficient historical evidence of identity-question success and/or repeated property-generation failure to justify a WP-060 controlled experiment?**

The question is intentionally narrower than:

```text
Which targets should use IDENTITY_FIRST?
```

WP-059 does not answer that final architectural question.

It answers:

```text
Which targets deserve an experiment?
```

# 12. Failure Pattern Analysis

For each candidate, identify whether there is evidence of:

```text
repeated property-generation failure
repeated classification/membership failure
repeated grounding failure
repeated quality failure
repeated MCQ failure

```

Do not treat every failed attempt as evidence for identity-first.

The purpose is to determine whether:

```text
question-strategy selection
```

appears to be the problem.

---

# 13. Identity Success Signal

A candidate may be interesting when historical evidence shows:

```text
identity attempts
    → unusually high acceptance
```

relative to:

```text
property attempts
```

However, identity success alone is insufficient.

A candidate with:

```text
1 identity attempt
1 accepted
```

must not automatically rank above a candidate with:

```text
8 identity attempts
6 accepted
```

Sample size and evidence quality matter.

---

# 14. Property Failure Signal

A candidate may be interesting when:

```text
property attempts
    → repeated failure
```

especially when the failures are:

```text
grounding
uniqueness
non-distinguishing proposition
```

and the retrieved evidence actually contains target-specific information.

This mirrors the Globus Pallidus diagnostic pattern.

But do not assume that every property failure means:

```text
IDENTITY_FIRST
```

is the correct solution.

It only means:

```text
candidate deserves investigation
```

if supported by additional evidence.

---

# 15. Classification/Membership Failure Signal

Repeated classification/membership failures may indicate that:

```text
the target is being treated as a group member
```

rather than:

```text
the target is being identified directly.
```

This may make a target interesting for identity-first investigation.

However, distinguish this from:

```text
legitimate classification targets
```

where classification is actually the intended question type.

Do not flag classification as a failure merely because it is classification.

---

# 16. Evidence Availability Requirement

Before recommending a candidate, verify that the project has sufficient evidence to support meaningful questions about the target.

Do not recommend a candidate merely because:

```text
identity questions historically succeeded
```

if the evidence basis is unclear.

At minimum document:

```text
target evidence availability
target-specificity
historical strategy evidence
```

using existing project artifacts.

---

# 17. Candidate Scoring

Create a deterministic candidate-ranking heuristic.

The exact formula must be documented.

A suggested structure is:

```text
Candidate Score =
    strategy contrast
    + sample-size support
    + repeated failure signal
    + target-specific evidence support
    - ambiguity/insufficient-data penalty
```

Do not use an LLM to assign the score.

The score is an engineering prioritization tool, not a probability estimate.

---

# 18. Do Not Pretend the Score Is Statistical Significance

The score must not be described as:

```text
probability that identity-first will work
```

or:

```text
statistical proof
```

It is only:

```text
priority for further investigation/experiment
```

The actual controlled experiment remains the causal test.

---

# 19. Candidate Tiers

Classify candidates into:

```text
TIER A — strong candidate for controlled experiment

TIER B — interesting but insufficient evidence

TIER C — no current evidence for identity-first experiment
```

### TIER A

Requires multiple converging signals.

For example:

```text
repeated property failures
+
meaningful identity success
+
sufficient historical attempts
+
target-specific evidence
```

### TIER B

Some evidence exists, but sample size or strategy contrast is insufficient.

### TIER C

No meaningful evidence currently supports identity-first.

# 21. Minimum Evidence Requirement for Tier A

Do not define Tier A merely by a single successful identity example.

A Tier A candidate should have at least two independent signals from:

```text

repeated failure pattern

target-specific evidence availability
cross-round repetition
```

```text

```

Do not manufacture candidates.

# 22. Independent Evidence

Where possible, distinguish:

```text
same round / same generation sequence
```

from:

```text
independent rounds
```

because a strategy transition after failure may introduce retrospective bias.

This was a central caveat in WP-052.

Historical identity success is not automatically evidence that identity-first would have succeeded if attempted first.

---

# 23. Retrospective Bias

For each candidate, explicitly report whether identity successes were:

```text
FIRST ATTEMPT
```

or:

```text
AFTER PRIOR FAILURES
```

or:

```text
UNKNOWN
```

This is critical.

A candidate whose only identity successes occurred after multiple property failures has weaker evidence for an identity-first causal hypothesis than one with independent first-attempt identity successes.
