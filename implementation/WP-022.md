# WP-022 — LLM-Facing Validator Evidence References

## 1. Context

Before implementation, read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-022.md`

WP-001 through WP-021 are complete and approved.

WP-021 added bounded recovery when grounding/textbook validators return valid structured responses containing provenance that was never supplied.

The subsequent 40-question acceptance run reached 26/40 and then failed because GroundingValidator returned invented canonical evidence IDs twice consecutively.

A read-only architecture diagnostic established:

**A. FEASIBLE — SMALL, LOCALIZED CHANGE**

Key findings:

- prompt formatting already assigns `[Evidence N]` positional labels;
- downstream code only requires canonical chunk IDs after validation;
- nothing downstream requires the LLM itself to reproduce canonical chunk IDs;
- the codebase already uses the pattern:
  LLM-facing response model → deterministic conversion → domain model;
- WP-020 and WP-021 can remain structurally unchanged;
- textbook `source_page` / `reference_text` are not required to establish provenance once a supplied evidence reference resolves deterministically to a canonical chunk;
- `historical_reference_id` is already simple/reliable and requires no change.

WP-022 removes unnecessary reproduction of machine-generated canonical chunk IDs from the grounding and textbook LLM contracts.

Implement only WP-022.

---

## 2. Objective

Replace validator-facing canonical chunk IDs such as:

    STUDENT_SUMMARY:student_summary_2.pdf:0071:0001

with short call-local references based on the evidence ordering already present in the prompt:

    Evidence 1
    Evidence 2
    Evidence 3

Conceptual flow:

    retrieved chunks
        ↓
    application owns canonical IDs

    Evidence 1 → canonical chunk A
    Evidence 2 → canonical chunk B
    Evidence 3 → canonical chunk C
        ↓
    LLM sees/cites local references
        ↓
    LLM response:
        evidence_refs = [1, 3]
        ↓
    strict local-reference validation
        ↓
    deterministic mapping
        ↓
    GroundingValidationResult.evidence_chunk_ids =
        [chunk_A.chunk_id, chunk_C.chunk_id]

Canonical chunk IDs must remain the application's authoritative provenance representation.

Local references must not escape the LLM/validator boundary.

---

## 3. Reuse Existing Evidence Numbering

Inspect and reuse the existing `[Evidence N]` formatting in:

    prompts/formatting.py

Do not introduce a second independent numbering scheme if the existing one already represents evidence position deterministically.

For an evidence sequence:

    chunks[0]
    chunks[1]
    chunks[2]

the LLM-facing references should correspond deterministically to:

    Evidence 1
    Evidence 2
    Evidence 3

The mapping must be created from the exact evidence sequence supplied to the prompt.

---

## 4. Local Reference Representation

Prefer the simplest structured representation.

For example:

    evidence_refs: list[int]

where:

    1 = Evidence 1
    2 = Evidence 2
    ...

This is preferable to asking the LLM to reproduce strings such as `"E1"` unless existing prompt/model conventions make strings clearly cleaner.

Whichever representation is chosen:

- it must be deterministic;
- it must be unambiguous;
- it must be validated strictly;
- it must correspond exactly to the evidence numbering shown in the prompt.

Document the choice.

---

## 5. Grounding LLM-Facing Response Model

Do not change the downstream meaning of:

    GroundingValidationResult

Instead introduce the smallest appropriate LLM-facing response model, conceptually:

    GroundingValidationResponse

It should contain the fields the LLM needs to produce, but provenance should use local evidence references rather than canonical chunk IDs.

Conceptually:

    passed
    confidence
    reason
    evidence_refs

Use the actual existing GroundingValidationResult fields as the source of truth for the exact contract.

Do not unnecessarily redesign unrelated fields.

Add clear `Field(description=...)` metadata consistent with WP-018's structured-output hardening.

---

## 6. Grounding Conversion

GroundingValidator should request:

    GroundingValidationResponse

from the LLM.

After receiving it:

1. validate every local evidence reference;
2. reject any reference outside the supplied evidence range;
3. deterministically resolve each valid reference to the corresponding SourceEvidenceChunk;
4. construct the existing GroundingValidationResult;
5. populate its existing canonical `evidence_chunk_ids` using the resolved chunks.

Example:

    supplied chunks:
        Evidence 1 → chunk A
        Evidence 2 → chunk B
        Evidence 3 → chunk C

    response:
        evidence_refs = [1, 3]

    domain result:
        evidence_chunk_ids = [
            chunk_A.chunk_id,
            chunk_C.chunk_id
        ]

The rest of the application must continue seeing canonical IDs.

---

## 7. Strict Fail-Closed Validation

If supplied evidence is:

    Evidence 1
    Evidence 2
    Evidence 3

then:

    evidence_refs = [1, 3]

is valid.

But:

    evidence_refs = [4]

must fail.

Also reject as appropriate:

- 0;
- negative references;
- references beyond the supplied range;
- malformed reference values;
- any representation not permitted by the response model.

Do not:

- clamp values;
- guess intended references;
- fuzzy-match;
- silently remove invalid references;
- substitute another evidence item;
- infer which evidence the model probably intended.

Invalid local provenance remains a provenance failure.

---

Do not remove WP-021 merely because WP-022 should reduce its activation rate.

## 9. Grounding Prompt

Update the grounding validation prompt so the LLM is explicitly told:

- evidence items are identified by their displayed `Evidence N` numbers;
- cite only evidence numbers actually supplied;
- return those local references in the response field;
- never invent another evidence number;
- leave the list empty when appropriate rather than guessing;
- do not return canonical/internal chunk IDs.

Remove instructions requiring the LLM to copy canonical chunk IDs character-for-character.

Keep all factual-grounding and authority semantics unchanged.

---

## 10. Canonical IDs in Prompt Content

Determine whether canonical chunk IDs still need to be visible to the LLM at all.

If they serve no other model-facing purpose, prefer not exposing them in grounding/textbook prompt evidence.

The application already owns the mapping.

However, do not broadly change shared evidence formatting if generation or another component currently depends on canonical IDs being present.

If the shared formatter is used by generation, grounding, and textbook, make the smallest scoped change necessary so WP-022 does not accidentally alter generation behavior.

Document the decision.

---

## 11. Textbook LLM-Facing Response Model

Apply the same architecture to textbook validation.

Introduce a small LLM-facing model, conceptually:

    TextbookValidationResponse

Use local evidence references instead of requiring canonical course-book chunk IDs from the LLM.

After strict validation, deterministically convert local references into canonical chunk IDs and construct the existing:

    TextbookCheckResult

Do not leak temporary Evidence-N references downstream.

---

## 12. Textbook Provenance

Current textbook provenance includes:

- `evidence_chunk_ids`;
- `source_page`;
- `reference_text`.

The diagnostic established that canonical chunk identity is sufficient to determine which supplied source evidence was cited.

Therefore make:

    local evidence reference
        ↓
    canonical SourceEvidenceChunk
        ↓
    canonical evidence_chunk_id

the authoritative textbook provenance mechanism.

Do not require the LLM to reproduce `source_page` or `reference_text` merely to prove provenance if those values can be obtained deterministically from the resolved chunk.

Prefer deriving deterministic metadata from the resolved chunk where existing downstream contracts require it.

Do not invent content.

Do not perform fuzzy matching of reference text.

---

## 13. Preserve Textbook Domain Contract Where Practical

Prefer keeping:

    TextbookCheckResult

stable for downstream consumers.

If `source_page` / `reference_text` remain fields on the existing result contract:

- preserve their documented meaning;
- populate them deterministically where possible from the resolved canonical evidence;
- use `None` where the existing contract legitimately permits absence and no authoritative value exists.

Do not perform broad model/schema refactoring merely to remove fields.

If a tiny contract change is genuinely necessary, document and test it carefully.

---

## 14. Textbook Prompt

Update the textbook validation prompt so the LLM cites the displayed local evidence references.

It should no longer need to copy:

- canonical chunk IDs;
- page numbers as provenance proof;
- exact reference text as provenance proof.

The LLM's job is to determine:

    CONSISTENT
    POTENTIAL_CONFLICT
    NOT_FOUND

and identify which supplied evidence supports that determination where applicable.

Application code owns canonical provenance reconstruction.
