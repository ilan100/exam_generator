# 2. Objective

Implement independent factual grounding validation for a generated `CandidateQuestion`.

The pipeline becomes:

```text
WP-009
CandidateQuestion
      ↓
retrieve/reconstruct relevant
student-summary evidence
      ↓
WP-008 grounding prompt
      ↓
WP-007 LLM
VALIDATION profile
      ↓
GroundingValidationResult
```

The validator determines whether the candidate question and its intended correct answer are actually supported by authoritative student-summary evidence.

This is the first point where the system independently checks the generator.

---

# 3. Core Architectural Rule

Generation and grounding validation are separate operations.

The validator must not trust:

* the generator because it produced the candidate;
* the candidate's claimed evidence IDs as proof of correctness;
* the historical style reference;
* textbook evidence.

The validator evaluates the candidate against factual student-summary evidence itself.

Conceptually:

```text
Generator:
"I used chunks A and B."

             ≠

Grounding validator:
"Chunks A and B actually support this question."
```

The second judgment is what WP-010 implements.

---

# 4. Factual Authority

For primary grounding:

```text
STUDENT_SUMMARY = authoritative factual source
```

Do not use:

* historical questions;
* historical answers;
* course-book evidence;
* model general knowledge

as substitutes for student-summary support.

The course book will be used later as a secondary check.

A fact that is generally true in neuroanatomy but unsupported by the supplied student-summary evidence must not automatically pass grounding.

# 6. Public Interface

Create a focused grounding-validation layer.

Conceptually:

```python
validate_grounding(
    candidate: CandidateQuestion,
) -> GroundingValidationResult
```

A class such as:

```python
GroundingValidator
```

is appropriate if dependencies need to be injected.

The exact internal decomposition is Claude's engineering decision.

Dependencies should be injectable so unit tests can use deterministic fake retrieval and LLM behavior.

---

# 7. Evidence Used for Validation

The validator must independently obtain the factual evidence to evaluate.

Do not simply take:

```text
candidate.evidence_chunk_ids
```

and assume those chunks are sufficient.

Use the candidate's canonical category/question content with the established student-summary retrieval infrastructure to obtain validation evidence.

A good V1 approach is to retrieve using a query containing the actual candidate question and relevant answer text, while remaining category-aware where appropriate.

The precise deterministic query construction is an engineering decision, but it must be documented and tested.

The important invariant is:

```text
validation evidence selection
        ≠
blind trust in generator provenance
```

It is acceptable for independently retrieved validation evidence to overlap with the chunks used during generation.

---

# 8. Retrieval Scope

Grounding retrieval must use only the student-summary index.

Do not retrieve course-book chunks.

Do not retrieve historical questions.

Use existing retrieval configuration rather than introducing unnecessary grounding-specific retrieval configuration.

If no usable student-summary evidence can be obtained, grounding must fail closed.

Do not call the LLM with an empty factual-evidence context.

---

# 9. Validation Prompt

Use the production grounding prompt established in WP-008.

The prompt must receive:

* the candidate question;
* independently selected student-summary evidence.

Use the existing WP-008 formatting/message infrastructure.

Do not create a second grounding prompt inside Python.

---

# 10. LLM Execution

Use:

```text
LLMProfile.VALIDATION
```

and request the existing:

```text
GroundingValidationResult
```

as structured output.

There should be one semantic grounding LLM call per validation invocation.

Do not implement retries in WP-010.

Provider/API failures should remain distinguishable from an actual grounding result of:

```text
passed = false
```

These mean different things:

```text
LLM/provider failed
        ≠
candidate failed grounding
```

---

# 11. Grounding Decision

The grounding validator should evaluate whether the supplied student-summary evidence supports:

1. the factual premise of the question;
2. the intended correct answer;
3. the relationship between the question and correct answer;
4. the intended answer being the best supported answer among the four choices;
5. any factual claims necessary for the question to function correctly.

Insufficient evidence should produce a failed grounding result rather than optimistic inference.

Do not require every distractor to be independently disproven unless the existing grounding contract/prompt requires that to establish one-best-answer support.

Detailed MCQ construction quality belongs to WP-011.

---

# 12. Supporting Evidence Provenance

If `GroundingValidationResult` contains supporting evidence IDs, they must refer only to chunks actually supplied to the grounding validator.

Never accept invented chunk IDs from the LLM.

Validate returned IDs deterministically against the validation evidence set.

If the LLM claims an unknown evidence ID, treat the structured validation output as invalid rather than silently dropping or repairing it.

The final grounding result should therefore have trustworthy provenance:

```text
GroundingValidationResult
        ↓
supporting evidence IDs
        ↓
actual student-summary chunks
supplied to validator
```

---

# 13. Candidate Generation Provenance

The validator may receive a candidate containing generation-time:

```text
evidence_chunk_ids
```

Those IDs may be useful for audit/comparison, but must not determine the grounding verdict.

The grounding prompt/context should not frame them as proof.

If the existing WP-008 candidate formatter includes those IDs, ensure the validator is explicitly instructed that they are generator claims only.

Do not mutate the candidate's generation provenance.

---

# 14. Historical References

A `STYLE_SIMILAR` candidate may contain a historical-reference ID.

That historical reference must not be supplied as factual grounding evidence.

The validator should reach the same grounding standard for:

```text
STYLE_SIMILAR
```

and:

```text
INDEPENDENT
```

Generation mode does not change factual authority.

---

# 15. Errors

Introduce only focused grounding-domain errors where necessary.

Expected operational failures include:

* no factual validation evidence;
* inconsistent/invalid supporting evidence IDs returned by the LLM;
* invalid grounding context.

Do not convert:

```text
GroundingValidationResult(passed=False, ...)
```

into an exception.

A normal negative validation verdict is a successful execution of the validator.

Reuse existing retrieval/prompt/LLM errors where appropriate.

---

# 16. Tests

Add focused tests demonstrating at least:

* clearly supported candidate → grounding pass;
* unsupported candidate → grounding fail;
* validator independently retrieves evidence;
* candidate generation evidence IDs are not blindly used as validation evidence;
* validation evidence comes only from `STUDENT_SUMMARY`;
* historical reference is not factual evidence;
* course book is not queried;
* grounding production prompt is used;
* `LLMProfile.VALIDATION` is used;
* returned supporting evidence IDs must belong to evidence supplied to the validator;
* invented supporting evidence ID is rejected;
* empty retrieval fails before the LLM call;
* `passed=False` is returned normally rather than raised as an error;
* provider failure remains an operational error rather than becoming `passed=False`;
* candidate is not mutated;
* no retry occurs;
* no MCQ/category/quality/textbook validation is triggered.

Mock the LLM for normal unit tests.

Run the complete regression suite offline.

# 17. Live Smoke Test

If `OPENAI_API_KEY` is available, perform one live grounding smoke test after unit/regression tests pass.

Prefer using the real candidate generated during the WP-009 live smoke test if it is readily available through existing project tooling/data.

Otherwise generate exactly one candidate using the existing WP-009 path and immediately validate it.

Do not repeatedly generate candidates trying to obtain a passing example.

Report:

* candidate question;
* intended correct answer;
* grounding `passed`;
* grounding reason;
* supporting evidence IDs;
* validation evidence IDs supplied to the validator.

A grounding failure is **not** a failed WP-010 smoke test.

For example:

```text
candidate generated successfully
grounding validator executed successfully
passed = false
```

is a valid and informative system result.

The smoke test is checking that the validation pipeline works, not that the generator always produces a grounded question.

Keep live API usage minimal.

# 18. Important Interpretation of Live Results

Do not tune prompts or retrieval merely because the first real candidate fails grounding.

At this stage we need honest measurements.

A failure may reveal future work needed in:

* generation quality;
* retrieval quality;
* prompt quality;
* retry behavior.

Record the observation.

Do not hide it.

WP-013 will eventually use validation failures to drive controlled regeneration.

# 21. Acceptance Criteria

WP-010 is complete when:

1. A `CandidateQuestion` can be independently grounding-validated.
2. Validation evidence is independently obtained rather than blindly trusting generator provenance.
3. Only student-summary evidence is primary grounding authority.
4. WP-008 grounding prompt infrastructure is reused.
5. WP-007 is called using `LLMProfile.VALIDATION`.
6. The existing `GroundingValidationResult` contract is used.
7. Supporting evidence IDs are verified against actual validation evidence.
8. Unknown/invented supporting evidence IDs cannot enter a valid result.
9. A negative grounding verdict is distinct from operational failure.
10. Historical references cannot establish factual grounding.
11. Course-book evidence is not used.
12. No other validation stages are implemented.
13. No retry/regeneration behavior is implemented.
14. Unit tests require no network/API key.
15. Full regression suite passes.
16. One live grounding validation is executed if an API key is available.
17. Documentation/status is updated.
18. WP-011 has not been started.
