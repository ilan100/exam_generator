# 2. Objective

Implement deterministic text extraction from the project's PDF factual-source
documents.

The project contains two semantically different factual source classes:

```
Student-summary PDFs
    -> primary factual grounding authority

course_book.pdf
    -> secondary factual reference/check
```

This WP should produce page-aware extracted document data suitable for later
chunking.

Conceptually:

```
PDF file
    ↓
file validation
    ↓
page-by-page text extraction
    ↓
source-aware extracted pages
    ↓
extracted document representation
```

This WP is responsible only for obtaining trustworthy source text and preserving
its provenance.

It must NOT implement:

* chunking;
* embeddings;
* indexing;
* retrieval;
* RAG;
* category mapping;
* question generation;
* factual grounding decisions;
* textbook consistency decisions;
* LLM calls.

Those belong to later WPs.

---

# 3. Architectural Source Roles

The source-role distinction established in WP-002 is mandatory.

`SourceType` contains exactly:

```
STUDENT_SUMMARY
COURSE_BOOK
```

Preserve that distinction throughout PDF ingestion.

### Student summaries

Student-summary PDFs are the future authoritative factual grounding source for
generated questions.

### Course book

`course_book.pdf` is a secondary factual reference/check.

It must NOT silently become equivalent to student-summary grounding.

A future question cannot satisfy its student-summary grounding requirement
merely because matching material exists in `course_book.pdf`.

### Historical questions

Historical questions loaded by WP-003 remain:

```
STYLE / STRUCTURE / TERMINOLOGY DATA
```

They are not PDF factual sources and are outside this WP.

Do not interact with the historical repository except where imports or existing
tests naturally coexist.

# 4. Scope Boundary

WP-004 stops at extracted PDF pages/documents.

The intended future pipeline is:

```
PDF
  ↓

  ↓

  ↓
```

Do not collapse these layers.

In particular, do not implement chunking simply because extracted page text is
available.

# 8. Extracted Page Model

Introduce a typed internal representation for one extracted PDF page.

A suggested model:

```
ExtractedPage
    page
    text
```

Requirements:

### page

* positive integer;
* human-readable;
* 1-based;
* bool rejected.

This must match the 1-based page convention already established by WP-002.

### text

The extracted text for that page.

Text preservation is important.

Do not translate or normalize terminology.

Do not lowercase content.

Do not perform semantic cleanup.

The extraction layer may perform only minimal deterministic boundary cleanup if
required by the PDF library, and such behavior must be documented.

Prefer preserving extracted page text as faithfully as practical.

---

# 9. Extracted Document Model

Introduce a typed representation of one successfully extracted source PDF.

Suggested conceptual structure:

```
ExtractedDocument
    source_file
    source_type
    pages
```

Requirements:

### source_file

A stable source identifier/name representing the PDF.

Do not require an absolute filesystem path in the domain representation.

Prefer the source filename or stable project-relative identity.

### source_type

Required existing WP-002:

```
SourceType.STUDENT_SUMMARY
SourceType.COURSE_BOOK
```

Do not create another competing source-type enum.

### pages

Ordered immutable/read-only sequence of `ExtractedPage`.

Requirements:

* at least one page;
* preserve PDF page order;
* page numbering must correspond to physical PDF page order;
* page numbers must form the contiguous sequence `1..N`.

Do not include:

* chunks;
* embeddings;
* vector IDs;
* retrieval scores;
* categories;
* LLM metadata.

# 10. Relationship to SourceEvidenceChunk

WP-002 defines:

```
SourceEvidenceChunk
    chunk_id
    source_file
    page
    text
    source_type
```

Do NOT create `SourceEvidenceChunk` objects directly from whole PDF pages in
this WP merely to reuse that model.

`SourceEvidenceChunk` represents material after future chunking/retrieval
processing.

WP-004 should provide page-aware extracted source material from which a later WP
can create chunks.

Maintain the distinction:

```
ExtractedPage
    -> extraction-layer representation

SourceEvidenceChunk
    -> future factual evidence/chunk representation
```

Do not blur these responsibilities.

# 12. Public PDF Extraction API

Provide a small public API.

Conceptually:

```
extract_pdf(
    path,
    source_type
) -> ExtractedDocument
```

or an equivalently clear interface.

Requirements:

* explicit PDF path;
* explicit `SourceType`;
* deterministic behavior;
* no global mutable state;
* no network access;
* no printing from library code.

The public API must make it impossible or difficult to accidentally forget the
source type.

Do not infer source type from arbitrary filename substrings inside the generic
extractor.

Source classification belongs at the source-discovery/configuration boundary.

# 15. File Validation

Expected PDF boundary failures must produce clear domain-specific errors.

Handle at minimum:

* path does not exist;
* path is not a file;
* wrong/non-PDF file where a PDF is expected;
* unreadable/corrupt PDF;
* encrypted/password-protected PDF that cannot be read;
* PDF with zero pages;
* PDF from which no usable text can be extracted.

Do not make callers interpret raw PDF-library exceptions for normal ingestion
failures.

Do not catch every possible exception and hide programming errors.

Catch expected file/library boundary failures only.

---

# 16. Error Model

Create clear PDF-ingestion exceptions.

For example:

```
PdfIngestionError
    PdfNotFoundError
    PdfFileError
    PdfFormatError
    PdfEncryptedError
    PdfTextExtractionError
```

Exact names may vary.

Requirements:

* errors identify the affected source file/path;
* extraction failures identify the page when relevant;
* diagnostics are concise and actionable;
* common PDF-library exceptions should not leak as the only user-facing
  diagnostic.

Example:

```
Failed to extract text from student_summary_1.pdf page 7
```

Do not silently skip a failed page.

Fail closed when extraction of a source document is materially incomplete.

---

# 17. Empty Page Semantics

Real PDFs may contain pages with no extractable textual content.

Inspect the actual source PDFs before deciding behavior.

Distinguish:

```
document has some legitimate blank pages
```

from:

```
document has no usable text at all
```

A blank page should not automatically cause the entire document to fail if the
page is legitimately blank and the rest of the document is usable.

However:

* preserve the page number;
* preserve page ordering;
* do not renumber subsequent pages;
* do not silently remove pages if doing so would break source-page provenance.

A document for which no page contains usable text must fail.

Document and test the chosen policy.

# 18. Text Preservation

The source documents contain material where wording matters.

Preserve:

* Hebrew;
* English;
* mixed Hebrew/English text;
* anatomical terminology;
* punctuation where supplied by the extraction library;
* page boundaries.

Do not:

* translate;
* lowercase;
* normalize anatomical terms;
* replace English terminology with Hebrew;
* perform stemming;
* tokenize;
* summarize;
* rewrite;
* remove content because it appears irrelevant.

Do not perform category detection in this WP.

# 19. Unicode Verification

# 20. Page Provenance

Page provenance is mandatory.

For every extracted page, retain:

```
source_file
source_type
page
```

either directly on the page model or through its containing document plus page
number.

A future chunking layer must be able to create a `SourceEvidenceChunk` with
correct source/page provenance without reopening the PDF.

Do not use zero-based page numbers in public/domain representations.

The underlying PDF library may use zero-based indexes internally, but convert
them at the extraction boundary.

---

# 21. Deterministic Ordering

Document and source ordering must be deterministic.

Requirements:

* pages remain in physical PDF order;
* discovered student-summary files use a stable deterministic ordering;
* repeated extraction of the same unchanged file produces the same page order
  and source metadata.

Do not depend on arbitrary filesystem iteration ordering.

A reasonable V1 file policy is lexical ordering by filename unless the existing
project structure establishes a better deterministic order.

---

# 22. Read-Only Behavior

Extracted source representations should behave as read-only after successful
construction.

Future code should not accidentally alter page ordering or replace pages inside
an extracted document.

Tuples or equivalent immutable/read-only representations are appropriate.

Do not build a custom immutable collection framework.

The original source PDFs must never be modified.
