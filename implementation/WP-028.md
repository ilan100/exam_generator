WP-001 through WP-027 are complete.

The validation architecture is now strong:

- provenance
- grounding
- MCQ validation
- category validation
- quality validation
- textbook validation
- diversity planning
- partial exam output

WP-027 significantly reduced false acceptance by strengthening
GroundingValidator to evaluate every answer independently.

Current bottleneck:

Generation still produces too many candidates rejected because:

- distractor also correct
- weak distractors
- broad wording
- relationship ambiguity

Grounding is now correctly rejecting these.

The objective of WP-028 is NOT to weaken validation.

The objective is to improve generation quality so the FIRST generated
candidate is much more likely to satisfy the existing validators.

No validator responsibilities should change.

No acceptance policy should change.

No retry limits should change.

---

# 1. Objective

Change generation from:

    Evidence
        ↓
    Write MCQ

into:

    Evidence
        ↓
    Internal Question Blueprint
        ↓
    Write MCQ

This must happen inside the existing generation LLM call.

No second generation call.

No planning service.

No new pipeline stage.

No orchestration changes.

The blueprint exists only as internal reasoning/output of the existing
generation prompt.

---

# 2. Question Blueprint

Before generating the final MCQ, the model must first construct an explicit
question blueprint.

The blueprint should capture at least:

- knowledge target
- factual relationship being tested
- question style
- intended difficulty
- correct-answer role
- distractor strategy
- why each distractor is wrong

The exact schema is your design decision.

It should be concise.

It should not duplicate the final MCQ.

---

# 3. Relationship-Centered Generation

Generation must stop thinking primarily in terms of:

    "correct answer"

Instead think in terms of:

    "relationship"

Examples:

Instead of

    association fibers

think

    fibers connecting cortical regions
    within the same hemisphere

Instead of

    Broca area

think

    cortical region responsible for
    motor speech production

Questions should test relationships.

Answers should satisfy relationships.

This should naturally reduce multiple-correct-answer situations.

---

# 4. Explicit Distractor Design

Do NOT ask the model to simply invent three plausible distractors.

Require it to intentionally design each distractor.

Every distractor must have:

- a reason it appears plausible
- exactly one reason it is incorrect

Avoid distractors that fail for multiple unrelated reasons.

Avoid obviously absurd distractors.

---

# 5. Distractor Archetypes

Introduce explicit distractor strategies.

Possible examples include:

- sibling structure
- parent category
- child category
- neighboring anatomy
- functional confusion
- location confusion
- developmental-stage confusion
- terminology confusion

Generation should intentionally choose one or more strategies.

Do not randomize blindly.

The objective is educational plausibility.

---

# 6. Evidence-Aware Distractor Check

Before emitting the MCQ, generation must internally verify every distractor.

Conceptually:

For each distractor ask:

    Does the supplied evidence support this distractor as answering the
    exact question?

If yes:

    reject this distractor

and generate another.

This is internal reasoning.

Do NOT make another API call.

---

# 7. Relationship Precision

Generation must distinguish between:

true statement

and

correct answer.

Example:

A distractor may itself be a true anatomical fact.

That does NOT automatically make it a valid distractor.

The question asks about one specific relationship.

Only one answer should satisfy that relationship.

---

# 8. Hierarchy Awareness

Generation should explicitly recognize hierarchical relationships.

Examples:

Peripheral nervous system

contains

Autonomic nervous system

contains

Sympathetic division

Do not create membership questions where multiple hierarchy members satisfy
the wording.

If hierarchy creates ambiguity:

rewrite the question.

---

# 9. Enumeration Awareness

Generation should recognize enumerations.

If evidence says

A consists of

- X
- Y
- Z

then

"Which belongs to A?"

must not present

X correct

Y incorrect.

Rewrite instead.

---

# 10. Blueprint Self-Review

Before producing the final MCQ perform an internal review.

Conceptually verify:

- exactly one answer satisfies the relationship
- distractors fail for one clear reason
- wording is specific
- hierarchy is unambiguous
- evidence supports the intended answer
- evidence does not support distractors

This remains within the same generation call.

---

# 11. LLM-Facing Models

Introduce a small LLM-facing generation model representing the blueprint.

The public CandidateQuestion contract should remain as stable as reasonably
possible.

Prefer:

BlueprintResponse

↓

deterministic conversion

↓

existing CandidateQuestion

following the same architectural pattern already used elsewhere.
