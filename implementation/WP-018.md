## 2. Objective

Harden the existing V1 pipeline against the specific reliability failures measured in WP-017, rerun the same evaluation methodology, compare before/after results, and make an explicit V1 acceptance recommendation.

WP-017 baseline:

- Retrieval Recall@3: 86.5%
- Retrieval Recall@5: 94.6%
- Retrieval Recall@8: 94.6%
- Planned live questions: 20
- Operational failures before validation verdict: 70%
- Dominant failure: `QualityValidationResult.reason == ""`
- Empty-reason failure affected 45% of planned questions
- Acceptance rate among attempts that completed: 85.7%
- Human review found one accepted question with duplicated in-answer numbering

Primary focus:

1. structured-output reliability;
2. generation/validation provenance reliability;
3. the measured quality-validator blind spot;
4. regression and integration hardening;
5. before/after evaluation;
6. V1 acceptance decision.

Retrieval architecture is not a target of this WP.

## 3. Preserve Strict Contracts

Do not improve reliability by weakening correctness.

Do not:

- make required validator fields optional merely because the model sometimes violates them;
- accept empty required explanation/reason fields;
- accept invented evidence IDs;
- silently normalize malformed evidence IDs into valid ones;
- accept shortened evidence IDs or missing prefixes;
- use fuzzy provenance matching;
- weaken WP-013 acceptance criteria;
- skip validators to avoid failures;
- convert operational failures into PASS/FAIL verdicts;
- introduce a generic automatic LLM retry.

The principle remains:

    model output
        ↓
    strict application contract
        ↓
    valid result OR explicit operational failure

Reliability should improve by making valid model output more dependable.

---

## 4. Root-Cause the Empty-Reason Failure

WP-017 found the dominant operational failure:

    QualityValidationResult.reason = ""

Investigate this before changing behavior.

Determine:

- the actual `QualityValidationResult` schema;
- whether `reason` is constrained as non-empty;
- the exact quality-validation prompt;
- the structured-output schema sent through the OpenAI provider;
- the behavior of the currently installed OpenAI SDK;
- whether failure occurs during OpenAI structured parsing or subsequent Pydantic validation;
- whether the empty reason correlates with `valid=True`, `valid=False`, or both.

Document the root cause.

Do not assume the prompt is responsible until the path has been inspected.

If investigation confirms that the model is violating a required non-empty field contract, make the smallest prompt-level correction necessary.

The prompt should explicitly state, using the actual field name, that the reason/explanation field:

- is required;
- must contain a concise explanation;
- must never be an empty string.

Do not weaken the Pydantic constraint.

- nullable fields.

Prompt instructions and Pydantic contracts must agree.

## 6. Generation Evidence-ID Reliability

Review the previously observed generation failures involving:

- dropped `STUDENT_SUMMARY:` prefixes;
- invented evidence chunk IDs.

Keep the existing strict provenance validation.

Where necessary, strengthen the generation prompt so that `evidence_chunk_ids` must be copied character-for-character from identifiers actually present in the supplied evidence.

Explicitly instruct:

- copy IDs exactly;
- never shorten them;
- never remove prefixes;
- never reconstruct an ID;
- never invent an ID.

If `evidence_chunk_ids` is optional under the established contract, do not force the model to invent provenance when it has nothing legitimate to report.

Do not implement fuzzy ID matching or application-side correction.

---

## 7. Grounding Evidence-ID Reliability

Apply the same review to `GroundingValidationResult`.

The grounding validator may report only evidence IDs actually supplied to that validation call.

The prompt should explicitly require:

- exact character-for-character copying;
- no prefix removal;
- no shortening;
- no reconstruction;
- no invented IDs.

Existing application-side provenance validation must remain strict and unchanged unless a genuine correctness defect is discovered.

---

## 8. Textbook Provenance Reliability

Investigate the recurring textbook `reference_text` mismatch.

The existing design has required the LLM to reproduce provenance text exactly, and live testing has shown this to be fragile.

Determine whether the current response contract is unnecessarily asking the model to reproduce arbitrary prose verbatim.

If `SourceEvidenceChunk` already provides a stable identifier that can reliably identify the supplied textbook evidence, prefer the smallest compatible contract improvement:

    LLM selects supplied evidence by stable identity
            ↓
    application verifies that identity deterministically

This is preferable to asking the LLM to reproduce long arbitrary text exactly if a stable identity already exists.

However:

- do not invent IDs that are not already deterministically available;
- do not use fuzzy text matching;
- do not infer provenance;
- do not weaken verification;
- do not broaden this into a large provenance redesign.

If changing the textbook response contract is necessary, make the smallest compatible change and update:

- models;
- prompts;
- tests;
- schemas;
- documentation

as required.

If the current text-based design remains the best option after inspection, strengthen its instructions instead and preserve exact validation.

Document the design decision.

## 9. Deterministic Quality Blind Spot

WP-017 human review found an accepted question containing duplicated in-answer numbering.

Example defect class:

    1. 1. answer text
    2. 2. answer text

or equivalent obvious leading choice-numbering artifacts.

This is mechanically detectable and should not require semantic LLM judgment.

Add a small deterministic structural check at the most appropriate existing validation boundary.

Requirements:

- obvious duplicated leading answer numbering must cause candidate rejection;
- this must be treated as a normal candidate-quality failure, not an operational exception;
- ordinary numerical content inside an answer must not be falsely rejected;
- valid answers must remain unaffected.

Do not build a large heuristic quality engine.

Python should handle only the observed deterministic structural defect.

Semantic judgments remain the responsibility of the existing validators, including:

- distractor plausibility;
- ambiguity;
- anatomical correctness;
- language quality;
- conceptual difficulty.

---

## 10. No Generic Automatic LLM Retry

Do not solve structured-output failures by adding:

    try:
        call_llm()
    except:
        call_llm_again()

WP-013 already owns bounded candidate-quality regeneration.

Provider/network/structured-output resilience is a separate concern.

A generic LLM retry would:

- hide contract problems;
- make costs unpredictable;
- blur operational failure vs candidate-quality rejection.

Default for WP-018:

    no new automatic LLM retry layer

If a narrowly scoped retry becomes genuinely necessary for a clearly transient provider failure, stop and document the rationale before implementing it.

## 11. Regression Tests

Add explicit tests for every measured reliability failure.

### Empty required fields

Test:

- empty quality reason is rejected;
- quality prompt explicitly requires non-empty reason;
- equivalent required explanation fields in other validators are protected where applicable.

### Generation provenance

Test:

- exact supplied ID accepted;
- missing prefix rejected;
- shortened ID rejected;
- invented ID rejected;
- no fuzzy correction occurs.

### Grounding provenance

Test:

- exact supplied ID accepted;
- malformed ID rejected;
- shortened ID rejected;
- invented ID rejected.

### Textbook provenance

Test:

- valid supplied evidence reference accepted;
- invented reference rejected;
- paraphrased/free-text mismatch cannot silently pass;
- any new stable-ID mechanism is checked strictly against evidence actually supplied.

### Structural quality

Test:

- duplicated answer numbering rejected;
- ordinary numerical content is not falsely rejected;
- valid answers remain unaffected.

## 18. Reliability Acceptance Gate

Do not define V1 success as "zero failures ever."

LLM systems retain stochastic operational risk.

Instead determine whether:

1. the dominant systematic WP-017 failure has been removed or materially reduced;
2. provenance-contract failures are rare enough for practical V1 use;
3. operational failures no longer dominate normal production;
4. candidate-quality rejection is handled primarily through the intended bounded regeneration mechanism;
5. full exam generation is practically achievable;
6. strict validation and provenance rules remain intact.

Make the decision from measured evidence.
