# WP-062 — Language Policy Runtime Enforcement

## 1. Objective

WP-061 established `docs/LANGUAGE_POLICY.md` as the authoritative project-wide language policy and identified two remaining runtime enforcement gaps:

```text
GAP 1:
prompts/generation/question.txt
still enforces English only for the correct answer
and in-question target-name reference.

GAP 2:
_validate_target_language_compliance()
still enforces only the narrower WP-058 scope.
```

WP-062 must bring runtime behavior into alignment with:

```text
docs/LANGUAGE_POLICY.md
```

without creating a large terminology subsystem and without changing unrelated generation architecture.

This is an implementation WP.

---

## 2. Authoritative Policy

Claude MUST read `docs/LANGUAGE_POLICY.md` before implementation.

The authoritative rule is:

```text
Questions are written in Hebrew.

For every professional/technical/terminological item,
including anatomical names, acronyms, symbols, abbreviations,
named entities, and domain-specific terminology:

    if an English representation exists:
        English MUST be used.

    if no English representation exists:
        Hebrew MAY be used.

This applies to:
    question-stem terminology
    target names
    correct answers
    distractors
    relevant user-visible generated terminology

This does NOT require the entire question to be written in English.
```

---

## 3. Architectural Goal

The runtime architecture must become:

```text
authoritative policy
        ↓
generation prompt
        ↓
generated question
        ↓
runtime validation
        ↓
policy-compliant output
```

The implementation must preserve:

```text
Hebrew question prose
    → allowed

Hebrew professional/technical item
    → forbidden when an established English representation exists
```

Do NOT implement whole-question English enforcement.

Do NOT implement rejection of Hebrew characters globally.

---

## 4. First Phase — Feasibility Investigation

Before modifying production code, inspect the repository and determine how existing project data can identify:

```text
professional/technical/terminological item
```

and:

```text
whether an established English representation exists
```

Inspect at minimum:

```text
question models
answer models
target models
source evidence
concept inventories
target inventories
historical terminology fields
generation prompt infrastructure
validation prompt infrastructure
language validators
language-related tests
```

Use the actual repository structure rather than assuming paths beyond those already known.

The key design question is:

> How can the project enforce English for professional/technical items without rejecting ordinary Hebrew prose?

Do NOT introduce:

```text

```

If the feasibility investigation concludes that full enforcement requires such a dependency or another major new subsystem:

```text
STOP
```

Document the architectural gap and wait for architect review.

Do not silently expand the scope.

---

## 7. No Invented English

The implementation must distinguish:

```text
established/project-supported English representation
```

from:

```text
plausible English translation
```

Do not invent English terminology.

If the repository cannot establish that an English representation exists:

```text
do not invent one
```

and do not reject Hebrew solely because a model could theoretically translate it.

---

## 8. Generation Prompt

Update:

```text
prompts/generation/question.txt
```

so it no longer contradicts the broad policy.

It must distinguish:

```text
Hebrew question prose
```

from:

```text
English professional/technical terminology
```

where an English representation exists.

The prompt must no longer imply that only:

```text
correct answer
target reference
```

are subject to the English-first rule.

---

## 9. Question Stem

The prompt must cover professional/technical terminology appearing in the question stem while preserving ordinary Hebrew grammatical prose.

---

## 10. Distractors

The prompt must cover terminology in all four answer choices:

```text
correct answer
incorrect answer 1
incorrect answer 2
incorrect answer 3
```

when those choices contain professional/technical terminology.

---

## 11. Acronyms and Symbols

The prompt and validation design must address:

```text
acronyms
abbreviations
symbols
standard professional notation
```

when an established English/international representation exists.

Do not require English for arbitrary ordinary words merely because an English translation exists.

---

## 12. Deterministic Validator

Inspect and update:

```text
_validate_target_language_compliance()
```

or its architectural replacement if the repository already contains one.

The current validator is known to enforce only the narrower WP-058 scope.

The future implementation must cover the broader policy to the extent that the repository can reliably identify applicable terminology.

Do not create false certainty.

---

## 13. Validator Boundary

The validator must not reject valid Hebrew prose merely because Hebrew characters exist.

A policy violation should be rejected only when the validator can establish:

```text
specific professional/technical item
+
established English representation exists
+
Hebrew representation was used
```

If the implementation cannot establish that relationship reliably:

```text
do not falsely reject
```

Document the limitation.

---

## 14. Non-Named-Entity Targets

Explicitly investigate:

```text
non-named-entity targets
```

because the policy is not restricted to target type.

If existing project data supports deterministic enforcement, implement it.

If not, document the limitation rather than inventing a new terminology architecture.

---

## 15. Prompt vs Validator

Preserve the division:

```text
prompt:
    instruct generation to follow the policy

validator:
    deterministically detect violations that the architecture
    can reliably recognize
```

Do not rely on the prompt alone.

Do not force the validator to solve terminology recognition that the repository cannot support.

---

## 16. Fail-Closed Boundary

For violations that can be reliably identified:

```text
fail closed
```

For terminology cases that cannot be reliably classified:

```text
do not fabricate certainty
```

Document which cases are:

```text
enforced
not enforced
ambiguous
```

---

## 17. Tests Required

Unlike WP-061, WP-062 MUST add or extend runtime tests.

At minimum cover:

```text
Hebrew grammatical prose
    → accepted

English professional terminology
    → accepted

Hebrew professional term where English exists
    → rejected

established English acronym
    → accepted

Hebrew substitute for established acronym
    → rejected

English target
    → accepted

Hebrew target where English exists
    → rejected

English professional term in question stem
    → accepted

Hebrew professional term with English representation in stem
    → rejected

English professional terminology in distractors
    → accepted

Hebrew professional terminology with English representation in distractors
    → rejected

Hebrew prose + English professional terminology
    → accepted

entire question in English
    → not rejected by this language policy alone
```

Use the repository's existing test architecture.

Do not build a general terminology-recognition system solely for these tests.
