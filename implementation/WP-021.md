# WP-021 — Validator Provenance Recovery

## 1. Context

Before implementation, read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-021.md`

WP-001 through WP-020 are complete and approved.

Recent reliability testing identified a remaining exam-killing operational failure:

    GroundingValidator
        ↓
    LLM returns a syntactically valid GroundingValidationResult
        ↓
    evidence_chunk_ids contains an ID that was NOT
    supplied to the validator
        ↓
    InvalidGroundingOutputError
        ↓
    entire exam terminates

This is intentionally fail-closed and must remain so.

However, the failure appears stochastic and can terminate a long exam even though the candidate itself may be valid.

WP-021 adds narrowly bounded recovery for validator provenance failures.

Implement only WP-021.

---

## 2. Objective

When a validator returns a structurally valid response but claims provenance that was not actually supplied:

    same candidate
        ↓
    same retrieved evidence
        ↓
    validation LLM call
        ↓
    invalid provenance
        ↓
    discard validator response
        ↓
    retry SAME validation once
        ↓
    valid provenance → continue normally
    invalid again → operational failure

Never repair, normalize, guess, substitute, or silently accept an invented provenance ID.

---

## 3. Grounding Validator

Implement bounded provenance recovery in:

    GroundingValidator.validate_grounding(candidate)

The grounding evidence must be retrieved exactly once for the logical validation operation.

Then:

    retrieve evidence
        ↓
    construct prompt/context
        ↓
    validation call #1
        ↓
    verify evidence_chunk_ids

If valid:

    return GroundingValidationResult

If the result contains evidence IDs not present in the evidence actually supplied:

    discard result
        ↓
    repeat same LLM validation once
        ↓
    verify provenance again

If the second result is valid:

    return it normally

If the second result still contains invalid provenance:

    raise InvalidGroundingOutputError

Do not perform a third provenance retry.

---

## 4. Same Logical Validation

The retry must use:

- the same CandidateQuestion;
- the same retrieved evidence chunks;
- the same evidence ordering;
- the same prompt;
- the same response model;
- the same `LLMProfile.VALIDATION`.

Do not perform retrieval again.

Do not regenerate the candidate.

Do not alter the evidence IDs before resubmitting.

Do not dynamically modify the prompt after the first failure.

The retry is simply another physical LLM call for the same logical grounding validation.

---

## 5. Strict Provenance Remains Mandatory

The following remains forbidden:

    model returns:
    STUDENT_SUMMARY:invented...

    application notices closest real ID

    application substitutes real ID

This must never happen.

Likewise, do not:

- remove invalid IDs and keep valid ones;
- accept the verdict while ignoring provenance;
- map partial IDs to full IDs;
- fuzzy-match IDs;
- infer evidence from `reference_text`;
- trust generation-time evidence IDs.

Either the returned grounding provenance is valid or that validator response is discarded.

---

## 6. Retry Scope

Retry only:

    InvalidGroundingOutputError

when it represents invalid grounding provenance returned from the LLM response for the current validation operation.

Do not retry:

- `passed=False`;
- low confidence;
- unsupported answer;
- ambiguous answer;
- normal grounding rejection;
- authentication failure;
- rate-limit failure;
- network/provider failure;
- prompt failure;
- retrieval failure;
- malformed JSON handled by WP-020;
- arbitrary Pydantic/domain validation failure;
- unexpected exceptions.

A normal grounding verdict of:

    passed=False

is a valid validator result and must immediately return to the normal WP-013 acceptance/regeneration flow.

---

## 7. Interaction With WP-020

WP-020 remains responsible for malformed structured output.

Example:

    grounding physical call #1
        ↓
    malformed JSON
        ↓
    WP-020 structured-output retry
        ↓
    physical call #2
        ↓
    valid JSON, but invented evidence ID
        ↓
    GroundingValidator provenance retry
        ↓
    new logical generate_structured() call

That new logical call may itself use WP-020's bounded structured-output recovery if its physical response is malformed.

Keep the two mechanisms separate:

    WP-020:
    syntactically malformed structured output

    WP-021:
    syntactically valid result with invalid
    application-level provenance

Do not merge their retry budgets.

---

## 8. Retry Count

For WP-021:

    validator provenance retries = 1

Meaning:

    initial logical validation call
        +
    at most one provenance retry

Do not create unbounded retries.

Prefer the smallest clean implementation.

If adding configuration fits the existing architecture cleanly, add an explicit validated value such as:

    validation.provenance_retries: 1

or equivalent.

If this would require unnecessary configuration restructuring, a clearly documented validator-level constant is acceptable.

Do not add a general retry-policy framework.

## 9. Textbook Validator

Inspect `TextbookValidator` carefully.

It also performs provenance verification using course-book evidence.

Determine whether the same stochastic failure class is possible:

    valid TextbookCheckResult
        ↓
    evidence_chunk_ids references chunk not supplied
        ↓
    InvalidTextbookOutputError

If yes, implement the same bounded provenance-recovery pattern:

    retrieve course-book evidence once
        ↓
    validate
        ↓
    invalid provenance
        ↓
    retry same textbook validation once
        ↓
    valid → return
    invalid again → InvalidTextbookOutputError

If the existing textbook contract contains other provenance fields such as `reference_text`, inspect their semantics carefully.

Do not weaken existing textbook provenance validation.

Document exactly which textbook provenance violations are considered retryable.

## 10. Other Validators

Do NOT add this mechanism to:

- MCQValidator;
- CategoryValidator;
- QualityValidator.

They do not own factual evidence provenance.

Do not create a generic validator base class merely to share retry logic.

Grounding and textbook may contain small duplicated control flow if that keeps responsibilities explicit.

---

## 11. Attempt Semantics

A validator provenance retry must NOT create a new:

    QuestionAttempt

Example:

    QuestionAttempt #1
        generation succeeds
        grounding call returns invented evidence ID
        grounding provenance retry succeeds
        MCQ passes
        category passes
        quality passes
        textbook passes
        accepted

This remains:

    QuestionAttempt #1

The discarded grounding response is not a candidate-production attempt.

## 13. Exhaustion

If grounding provenance is invalid twice:

    validation call #1 → invalid provenance
    validation call #2 → invalid provenance
        ↓
    InvalidGroundingOutputError

The existing orchestration-level operational failure handling should then contextualize the error with:

- question position;
- category;
- generation mode;
- completed question count;
- cause.

Do not consume another QuestionProducer attempt after validator-provenance retry exhaustion unless the existing architecture explicitly already does so.

Do not change that policy in WP-021.

The same applies to textbook provenance exhaustion.

---

## 14. Observability

Make provenance retries observable with the smallest reasonable mechanism.

At minimum, tests/evaluation should be able to determine:

- grounding provenance retry occurred;
- textbook provenance retry occurred, if applicable;
- retry succeeded;
- retry exhausted.

Do not introduce a logging framework.

Do not record API keys, complete prompts, or other secrets.

If a simple immutable event/counter mechanism similar to WP-020's:

    structured_output_retry_events

fits cleanly, that is acceptable.

Do not over-engineer it.

## 27. Acceptance Criteria

WP-021 is complete when:

1. Grounding provenance failure is retried at most once.
2. The same candidate and evidence are reused.
3. Grounding retrieval occurs only once per logical validation.
4. Invalid IDs are never repaired or silently ignored.
5. A valid `passed=False` verdict is not retried.
6. Retry exhaustion remains an operational failure.
7. Textbook provenance behavior is inspected and equivalent recovery is implemented if the same failure class exists.
8. MCQ/category/quality validators remain unchanged.
9. WP-020 structured-output recovery remains independent.
10. WP-019 generation-contract recovery remains independent.
11. Provenance retries do not create new `QuestionAttempt` records.
12. Authentication/rate-limit/network errors are not provenance-retried.
13. `max_generation_attempts` remains 3.
14. `מבוא` receives no special production behavior.
15. Retrieval remains unchanged.
16. Tests explicitly cover recovery and exhaustion.
17. Full regression passes.
18. Small live smoke test is performed if credentials are available.
19. Full 2-per-category acceptance exam is attempted exactly once if credentials are available.
20. Results are reported honestly.
21. Strict provenance remains fail-closed.
22. No unrelated V2 feature is introduced.
