# WP-030 — Relationship-Constrained Generation

## Context

Read completely:

- docs/MASTER_PROJECT_BRIEF.md
- docs/ARCHITECTURE.md
- docs/PROJECT_STATUS.md
- implementation/WP-029_ARCHITECTURE_PROPOSAL.md
- implementation/WP-029_ARCHITECTURE_REVIEW.md

WP-029 has been accepted.

Its recommendation is to move generation toward application-controlled,
relationship-driven construction rather than additional prompt engineering.

WP-030 is Phase 1 of that migration.

---

# 1. Objective

Introduce an explicit representation of the relationship being tested.

Today the application tells generation approximately:

- category
- evidence
- target

After WP-030 it should additionally provide:

- tested relationship

The relationship becomes a first-class application concept.

---

# 2. Relationship Model

Design a small immutable model representing the tested relationship.

It should express concepts such as:

- supplies
- innervates
- connects
- contains
- projects to
- located in
- develops into
- receives input from
- drains into
- surrounds

Do NOT hard-code these values.

The representation should be extensible.

---

# 3. QuestionTarget Evolution

Extend QuestionTarget only where necessary.

Avoid mixing:

"What should be tested"

with

"How should generation work."

The relationship belongs to the former.

Generation policy does not.

---

# 4. Relationship Extraction

Implement deterministic extraction of the intended relationship from the
generation target.

This extraction happens before the LLM call.

No additional LLM calls.

No prompt asking the LLM to identify relationships.

Application logic owns this responsibility.

---

# 5. Prompt Changes

Generation prompt should explicitly receive:

- concept
- relationship
- evidence

Generation should now think:

"What satisfies this relationship?"

rather than

"What answer looks plausible?"

Keep prompt changes minimal.

---

# 6. Generation Constraints

Require generation to produce exactly one answer satisfying the specified
relationship.

Distractors may be factually true,

but they must not satisfy the tested relationship.

This is an instruction change only.

No validator changes.

---

# 7. No Distractor Strategies Yet

Do NOT implement:

- sibling substitution
- hierarchy inversion
- archetype selection
- competitor extraction

Those belong to later work packages.

WP-030 introduces only the relationship layer.

---

# 8. Validation Compatibility

GroundingValidator,

MCQValidator,

CategoryValidator,

QualityValidator,

TextbookValidator

must remain unchanged.

WP-030 should improve generation quality without modifying validation.

---

# 9. Diversity

Do not modify diversity planning.

No new diversity scoring.

No new planner.

---

# 10. Cost

No additional LLM calls.

No additional retrieval.

No additional validators.

No orchestration changes.

No retry changes.

---

# 11. Tests

Add tests covering:

- relationship extraction
- immutable relationship model
- QuestionTarget compatibility
- prompt rendering
- deterministic behavior
- backward compatibility

Regression suite must pass.

---

# 12. Focused Evaluation

Generate questions for historically difficult categories, including:

- מערכת העצבים ההיקפית
- תאי מערכת העצבים
- אספקת דם

Compare against WP-027 baseline.

Measure:

- grounding failures
- multiple-supported-answer failures
- acceptance rate
- attempts

Do not tune prompts after evaluation.

---

# 13. Full Acceptance Run

Run exactly once.

20 categories.

2 questions each.

WP-023 partial exam behavior remains active.

No reruns.

---

# 14. Success Criteria

Primary metric:

Grounding rejections caused by multiple supported answers should decrease.

Secondary metrics:

- acceptance rate
- average attempts
- first-pass acceptance

Correctness must never decrease.

---

# 15. Scope Exclusions

Do NOT:

- implement competitor extraction
- implement distractor archetypes
- redesign retrieval
- redesign validators
- redesign orchestration
- redesign retries
- add embeddings
- add vector databases

Those belong to future work packages.
