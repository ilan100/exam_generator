# WP-037 — Concept-Anchored Evidence for Deterministic Targets

## Context

Read completely:

- docs/MASTER_PROJECT_BRIEF.md
- docs/ARCHITECTURE.md
- docs/PROJECT_STATUS.md
- implementation/WP-035_ARCHITECTURE_INVESTIGATION.md
- implementation/WP-035_ARCHITECTURE_REVIEW.md
- implementation/WP-036_COMPLETION_REPORT.md
- implementation/WP-036_ARCHITECTURE_REVIEW.md

WP-035 established that deterministic concept ownership is feasible for a subset of categories.

WP-036 implemented a three-category pilot and produced an important result:

- deterministic concept selection worked;
- coverage filtering worked;
- selected concepts changed between rounds;
- but generated questions frequently returned to a different, more salient fact in the supplied evidence.

Therefore the current problem is no longer primarily concept selection.

The current problem is:

> The selected concept is not sufficiently anchored to the evidence supplied to the question generator.

WP-037 addresses this problem.

---

# 1. Objective

Improve the handoff between:

```text
Selected Concept
        ↓
Question Generation
```

so that the generated question actually tests the selected concept.

The change must be implemented first as a pilot for the same three WP-036 categories:

- אספקת דם
- מסילות עצביות
- גרעיני הבסיס

Do not expand beyond these categories in this WP.

---

# 2. Core Architectural Change

The pipeline for pilot categories should become:

```text
Evidence Retrieval

↓

Deterministic Concept Inventory

↓

Coverage Filtering

↓

Select Concept

↓

Concept-Anchored Evidence

↓

QuestionTarget

↓

Existing Generation Pipeline

↓

Existing Validation
```

The new component should construct a narrow factual focus around the selected concept.

The purpose is to prevent a nearby but more salient fact from taking over the generation.

---

# 3. Concept-Anchored Evidence

Introduce an internal deterministic component.

Suggested name:

```text
ConceptEvidenceAnchor
```

or:

```text
extract_concept_evidence_focus()
```

The exact name is an implementation decision.

Its responsibility is:

Given:

- selected InventoryConcept
- source evidence chunk containing that concept

produce:

- a narrow factual focus specifically associated with that concept;
- the genuine canonical evidence chunk ID;
- sufficient surrounding context to understand the fact;
- no unnecessary neighboring factual material where avoidable.

---

# 4. Evidence Anchoring Rules

The implementation should prefer the smallest trustworthy evidence unit that preserves the meaning of the selected concept.

Preferred order:

1. sentence containing the selected concept;
2. clause containing the selected concept, when sentence contains multiple independent facts;
3. immediately adjacent sentence only when required to understand the selected fact.

Do NOT simply use the existing fixed-size character window if it causes unrelated or competing facts to enter the generation context.

The goal is:

```text
Selected concept
+
its own factual statement
```

not:

```text
Selected concept
+
everything nearby in the paragraph
```

---

# 5. Deterministic Requirement

Concept anchoring must be deterministic.

Do NOT:

- call an LLM;
- use embeddings;
- use semantic similarity;
- use a new external model;
- ask an LLM to summarize the evidence.

The same evidence and selected concept must produce the same anchored context.

---

# 6. Provenance

The anchored evidence must retain the genuine canonical:

```text
SourceEvidenceChunk.chunk_id
```

Never invent or transform canonical evidence IDs.

The concept anchor is an internal interpretation of an existing evidence chunk.

It must not create new provenance identities.

---

# 7. Generation Contract

Do NOT redesign the generation response schema.

Do NOT redesign the public request/response contracts from WP-033.

Do NOT modify the canonical question schema.

The existing generation pipeline must continue receiving the same fundamental objects.

Only the target's factual focus/supporting evidence should become more precise for pilot categories.

---

# 8. Existing Generation Pipeline

Do NOT modify:

- QuestionGenerator
- QuestionProducer
- OpenAIProvider
- generation retry behavior
- generation-contract recovery
- structured-output recovery
- validation
- acceptance policy

The goal is to improve the information supplied to the existing generator, not to change how the generator operates.

---

# 9. Existing Relationship and Competitor Logic

Preserve:

- WP-030 relationship extraction
- WP-031 competitor discovery

The selected concept may continue to receive a deterministic relationship and competitors.

However, verify that the relationship and competitors remain compatible with the anchored factual focus.

Do not redesign those mechanisms in this WP.

---

# 10. Extraction Artifact Handling

WP-036 identified extraction artifacts such as:

```text
edial Lemniscus Tract
The Basal Gang
```

instead of:

```text
Medial Lemniscus Tract
The Basal Ganglia
```

WP-037 must not silently guess repairs.

Use the following principle:

> Never invent a concept correction when the evidence does not unambiguously support it.

Possible outcomes:

### A. Unambiguous local reconstruction

A deterministic repair may be performed if the source evidence itself provides enough local information to reconstruct the intended text without ambiguity.

### B. Ambiguous or corrupted concept

Reject/exclude the concept from the pilot inventory.

Do not pass a questionable concept to generation.

### C. Clean concept

Use it normally.

Document the exact policy implemented.

---

# 11. Category Self-Restatement

WP-036 also identified a concept that was effectively the category itself:

```text
גרעיני הבסיס
```

producing:

```text
The Basal Gang
```

The pilot must prevent category-level restatements from becoming normal sub-concept targets.

Use deterministic comparison only.

Do NOT introduce semantic similarity in this WP.

If a concept is effectively identical to the category label after deterministic normalization, exclude it from the inventory.

Document the normalization rule.

---

# 12. Target-to-Question Alignment

Introduce a diagnostic concept:

```text
target_alignment
```

For each pilot generation attempt, preserve enough information to determine:

- selected concept;
- anchored factual focus;
- generated question;
- correct answer;
- whether the generated question actually tests the selected concept.

Do not add a new LLM validator.

Do not reject questions solely because of this diagnostic during the first implementation unless required by the existing architecture.

The first objective is measurement.

---

# 13. Alignment Evaluation

For the pilot evaluation, manually or deterministically classify each accepted question as:

```text
ALIGNED
```

or

```text
NOT_ALIGNED
```

The classification must be based on the actual generated question and correct answer compared with the selected concept and anchored evidence.

If an automated deterministic alignment check is unreliable, use manual review for the pilot and document the methodology.

Do not introduce an LLM judge merely to make the measurement convenient.

---

# 14. Pilot Categories

Use exactly the same three categories as WP-036:

1. אספקת דם
2. מסילות עצביות
3. גרעיני הבסיס

Do not add additional categories.

This preserves comparability with WP-036.

---

# 15. Pilot Generation

For each pilot category:

Generate four sequential questions using:

```text
CategoryQuestionSetService
```

The sequence must be:

```text
Question 1
    ↓
existing_questions = [Q1]

Question 2
    ↓
existing_questions = [Q1, Q2]

Question 3
    ↓
existing_questions = [Q1, Q2, Q3]

Question 4
```

No reruns.

No manual replacement.

No skipping failed questions.

Report failures honestly.

---

# 16. Required Measurements

Record for every generation:

- selected concept;
- concept evidence chunk;
- anchored factual focus;
- generated question;
- correct answer;
- acceptance/rejection;
- number of generation attempts;
- target alignment;
- whether the concept was subsequently recognized as covered.

The evaluation output should make it possible to distinguish:

```text
Concept selection failure
```

from:

```text
Concept extraction failure
```

from:

```text
Evidence anchoring failure
```

from:

```text
Generation drift
```

from:

```text
Coverage recognition failure
```

---

# 17. Primary Success Criterion

The primary success criterion is:

> **A deterministically selected concept should result in an accepted question that actually tests that concept.**

Measure:

```text
Target Alignment Rate
=
aligned accepted questions
/
accepted questions
```

Compare with WP-036.

---

# 18. Secondary Success Criteria

Also evaluate:

### Diversity

Does actual tested content become more diverse across sequential questions?

### Reliability

Does acceptance remain comparable to WP-036?

### Coverage

Does the system correctly recognize the selected concept as tested after an aligned question?

### Provenance

Does every anchored context retain genuine canonical evidence provenance?

---

# 19. Failure Interpretation

Do not declare WP-037 successful merely because target selection continues to rotate.

That already worked in WP-036.

The important question is whether the **actual questions** rotate with the targets.

Possible outcomes:

### Outcome A — Successful

Target alignment is high and actual question diversity improves.

Proceed to broader pilot.

### Outcome B — Anchoring improves alignment but extraction remains unreliable

Keep concept anchoring but fix inventory quality before expansion.

### Outcome C — Anchoring does not improve alignment

Investigate whether the generator contract itself permits too much freedom.

Do not immediately add retries or validators.

### Outcome D — Reliability materially deteriorates

Stop expansion and analyze why.

Do not increase attempt budgets merely to make the pilot pass.

---

# 20. No New Diversity Validator

Do NOT implement a diversity validator in WP-037.

The purpose of this WP is to improve generation at the source.

If the generator is properly anchored to the selected concept, the system should not need to repeatedly generate and reject questions for diversity.

A validator may become useful later as a safety net, but it is not the primary solution.

---

# 21. No Generic Retry

Do not add:

- generation retries for target mismatch;
- provider retries;
- validator retries;
- new attempt budgets.

WP-020, WP-021, and WP-019 retry mechanisms remain unchanged.

# 22. Tests

Add unit tests for:

### Concept anchoring

- concept appears in one sentence;
- concept appears in multiple sentences;
- concept appears in a sentence containing another salient entity;
- concept at beginning of evidence;
- concept at end of evidence;
- missing concept;
- malformed evidence;
- multi-line evidence;
- Hebrew/English mixed evidence where relevant.

### Extraction artifacts

- clean concept;
- obvious truncated concept;
- ambiguous fragment;
- category self-restatement.

### Planner integration

- selected concept receives anchored evidence;
- genuine evidence chunk ID preserved;
- pilot behavior enabled;
- non-pilot behavior unchanged.

### Regression

Full existing suite must pass.
