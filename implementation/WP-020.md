# WP-020 — Structured-Output Transient Recovery

## 1. Context

Before implementation, read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-020.md`

WP-001 through WP-019 are complete and approved.

WP-019 added bounded recovery for invalid generation contracts and improved exam-level failure context.

The subsequent real 2-questions-per-category acceptance run requested:

    20 categories × 2 questions = 40 questions

The system successfully completed 16 questions and then failed at:

    question: 17/40
    category: קרומים וסינוסים דוראליים
    generation_mode: STYLE_SIMILAR

Cause:

    pydantic.ValidationError

originating from malformed/truncated structured JSON returned while obtaining:

    GroundingValidationResult

The reported underlying parse problem was an EOF while parsing a string.

This was not:

- a candidate-quality failure;
- invalid generation provenance;
- an authentication failure;
- a retrieval failure;
- a configuration failure.

The candidate existed, but the application could not obtain a valid structured validator response.

WP-020 addresses this specific reliability class.

Implement only WP-020.

Do not introduce unrelated V2 features.

---

## 2. Objective

Add a very small, strictly bounded recovery mechanism for transient malformed/unparseable LLM structured output.

The intended behavior is:

    application operation
          ↓
    structured LLM call
          ↓
    valid structured response?
        /       \
      yes        no
       ↓          ↓
    continue   is failure specifically
               recoverable structured-output
               parsing/validation failure?
                    /       \
                  yes        no
                   ↓          ↓
             retry same      propagate
             operation once
                   ↓
             valid OR fail

The important distinction is:

    RETRY THE SAME LLM OPERATION

not:

    regenerate the candidate

and not:

    retry every operational error

---

## 3. Failure Classes Must Remain Distinct

The architecture now has three different recovery mechanisms.

### A. Candidate-quality failure

Example:

    MCQValidationResult.valid = false

Behavior:

    discard candidate
        ↓
    consume production attempt
        ↓
    generate fresh candidate

Owned by `QuestionProducer`.

Already implemented.

---

### B. Generation-contract failure

Example:

    generated candidate claims an evidence ID
    that was never supplied

Behavior:

    reject entire generated response
        ↓
    consume production attempt
        ↓
    generate fresh candidate

Owned by `QuestionProducer`.

Implemented in WP-019.

---

### C. Transient structured-output failure

Example:

    malformed/truncated JSON
    EOF while parsing response
    structured response cannot be converted
    into the requested Pydantic response model

Behavior:

    keep the same application operation
        ↓
    repeat the structured LLM request once
        ↓
    valid response OR operational failure

WP-020 implements only this third class.

Do not merge these concepts.

---

## 4. Investigate the Exact Failure Path First

Before implementing recovery, reproduce/trace the exact code path that caused the WP-019 acceptance-run failure.

Determine:

- which OpenAI SDK call produced the response;
- where malformed structured output is detected;
- which concrete SDK/Pydantic exception type is raised;
- whether the current `OpenAIProvider.generate_structured()` translates it;
- whether raw `pydantic.ValidationError` currently escapes the provider;
- whether other malformed structured-output cases raise different SDK exception types;
- whether a truncated response caused by token limits can be distinguished from malformed model output;
- whether refusal handling is separate.

Document the findings.

Do not implement:

    except Exception:
        retry

Recovery must be based on explicit, understood failure types.

---

## 5. Define a Provider-Level Structured-Output Error

The application should not need to depend directly on OpenAI/Pydantic parsing implementation details.

If the existing LLM error hierarchy does not already provide an appropriate abstraction, add the smallest necessary provider-independent error type.

Conceptually:

    LLMError
        └── LLMResponseError
                └── LLMStructuredOutputError

Exact hierarchy/name may follow existing project conventions.

The purpose is to represent:

    provider returned a response,
    but the requested structured result
    could not be obtained because the
    response was malformed/unparseable

Do not use this error for:

- authentication;
- rate limiting;
- network connectivity;
- provider HTTP failures;
- refusals;
- application provenance violations;
- prompt/configuration failures.

Preserve the original exception via exception chaining.

---

## 6. Recovery Scope

The retry mechanism should apply only to explicitly recognized transient structured-output failures.

At minimum, investigate and handle the exact failure observed in the 40-question run:

    malformed/truncated structured JSON
        ↓
    Pydantic/SDK structured parsing failure

Do not automatically classify every `ValidationError` as retryable.

For example, distinguish where possible between:

    response could not be parsed into structured output

and:

    application intentionally rejected a successfully parsed
    response because it violated a domain invariant

The latter must not be retried at this layer.

---

## 7. Retry the Same Operation

When a recoverable structured-output failure occurs, retry the same structured request.

For example:

    GroundingValidator.validate_grounding(candidate)

First call:

    same candidate
    same retrieved grounding evidence
    same prompt
    same response model
    same validation profile

Response malformed.

Retry:

    same candidate
    same evidence
    same logical validator operation
    fresh LLM call

Do not:

- regenerate the candidate;
- perform new retrieval merely because parsing failed;
- change category;
- change generation mode;
- change evidence;
- alter the prompt dynamically;
- loosen the schema.

The only intended difference is that the LLM receives another opportunity to return a valid structured response.

---

## 8. Retry Count

Keep the retry budget intentionally small.

For WP-020:

    maximum structured-output retries = 1

Meaning:

    initial call
        +
    at most one retry

Therefore:

    maximum calls for one logical structured operation = 2

Do not create unbounded retries.

Do not increase this value during the acceptance run merely to make the run succeed.

---

## 9. Configuration

Prefer an explicit configuration value rather than a hidden magic number if this fits the existing configuration architecture cleanly.

For example:

    llm:
      structured_output_retries: 1

or the equivalent appropriate location in the existing configuration model.

The semantic meaning must be clear:

    number of retries AFTER the initial call

Thus:

    0 = one call total
    1 = maximum two calls total

Validate:

    integer
    >= 0
    bool rejected

Do not add complex retry-policy configuration.

No:

- backoff settings;
- jitter;
- retry intervals;
- retry matrices.

WP-020 needs one small bounded number.

---

## 10. Retry Ownership

After inspecting the existing architecture, prefer implementing this at the provider/LLM structured-output boundary if the failure genuinely occurs there.

Reason:

The provider owns:

    messages
    + response_model
    + structured API invocation
    + conversion into the requested Pydantic model

It is therefore the narrowest layer that can recognize:

    "the provider call completed, but usable structured output
    was not obtained"

This is intentionally different from WP-019.

WP-019 correctly prohibited provider-level retries for application provenance failures because the provider does not understand provenance.

WP-020 is specifically about a provider structured-output failure, which the provider does understand.

Do not move candidate-quality or provenance retry logic into the provider.

---

## 11. One Logical Operation vs Physical API Calls

Update the architecture documentation to distinguish:

    logical structured-output operation

from:

    physical API call

Before WP-020, these were effectively 1:1.

After WP-020:

    one logical structured operation
        ↓
    physical API call #1
        ↓
    malformed structured output
        ↓
    physical API call #2
        ↓
    valid structured result

This is acceptable because the retry is narrowly scoped and bounded.

Do not describe the second API call as a new candidate-production attempt.

It belongs to the same logical operation.

---

## 12. Generation Calls

The same structured-output transient recovery may apply to the generation LLM call if the generation response itself is malformed/unparseable before a `GeneratedQuestionResponse` can be constructed.

Distinguish carefully:

### Malformed generation structured response

Example:

    truncated JSON
    cannot parse GeneratedQuestionResponse

Behavior:

    retry same generation structured operation once

This does NOT consume a new `QuestionProducer` candidate attempt unless both structured-output calls fail and the error propagates according to existing semantics.

### Successfully parsed but invalid generation provenance

Example:

    evidence_chunk_ids contains invented ID

Behavior:

    WP-019 mechanism
        ↓
    discard candidate response
        ↓
    consume production attempt
        ↓
    fresh generation attempt

Do not confuse these.

---

## 13. Validator Calls

The same structured-output transient recovery should apply consistently to validators using `generate_structured()`:

- grounding;
- MCQ;
- category;
- quality;
- textbook.

Example:

    Quality validator API call
        ↓
    malformed JSON
        ↓
    retry same quality validation once
        ↓
    valid QualityValidationResult
        ↓
    continue

No candidate-production attempt should be consumed merely because the first physical validator API response was malformed.

---

## 14. Errors That Must NOT Be Retried

Do not retry:

- authentication errors;
- invalid/missing API key;
- rate-limit errors;
- API connection errors;
- provider HTTP/status errors;
- configuration errors;
- refusals;
- retrieval errors;
- prompt errors;
- category errors;
- generation provenance violations;
- grounding provenance violations;
- textbook provenance violations;
- candidate-quality FAIL verdicts;
- deterministic duplicated-numbering rejection;
- arbitrary unexpected exceptions.

WP-020 is not a general resilience framework.

---

## 15. Rate Limits

Do not automatically retry rate-limit errors in WP-020.

Although rate limits are often transient in production systems, they require a separate policy involving backoff and timing.

That is explicitly outside this WP.

Existing `LLMRateLimitError` behavior remains unchanged.

---

## 16. Network Errors

Do not automatically retry `LLMProviderError` / connection failures in WP-020.

Network retry policy would require decisions about:

- backoff;
- timeout;
- idempotency;
- total latency;
- rate limiting.

Those are outside the measured problem.

Only malformed structured output is in scope.

---

## 17. Refusals

Existing refusal handling must remain unchanged.

A model refusal is not malformed structured output.

Do not retry a refusal under WP-020's structured-output mechanism.

---

## 18. Retry Observability

The system should make structured-output retries observable enough for evaluation and debugging.

Do not add a large logging framework.

At minimum, make it possible for the evaluation/smoke-test path to determine:

- that a structured-output retry occurred;
- which logical operation/model/profile was involved if practical;
- whether the retry succeeded or exhausted.

Use the smallest mechanism compatible with the existing architecture.

Do not expose secrets or prompt contents.

---

## 19. Audit Semantics

Do not represent a structured-output retry as a separate `QuestionAttempt`.

Example:

    production attempt 2
       generation valid
       grounding physical call #1 malformed
       grounding physical call #2 valid
       MCQ valid
       category valid
       quality valid
       textbook valid
       accepted

This remains:

    QuestionAttempt #2

not:

    QuestionAttempt #2
    QuestionAttempt #3

Structured-output retry is internal to one logical LLM operation.

Do not fabricate validator results for the malformed physical response.

Only the final successfully parsed result belongs in the normal validation result.

If both physical calls fail, the logical operation fails operationally.

---

## 20. Exhaustion

With:

    structured_output_retries = 1

behavior is:

    physical call #1
        ↓
    malformed structured output
        ↓
    physical call #2
        ↓
    malformed structured output
        ↓
    structured-output retry exhausted
        ↓
    operational failure propagates

Do not start another hidden retry sequence.

The original/final underlying cause must remain inspectable through exception chaining.

---

## 22. Unit Tests — Provider Recovery

Add focused tests for:

### Successful first call

    call #1 → valid structured response

Verify:

- exactly one physical provider call;
- no retry.

### Successful retry

    call #1 → recognized malformed structured-output failure
    call #2 → valid result

Verify:

- exactly two physical calls;
- same messages;
- same response model;
- same profile/configuration;
- valid result returned.

### Retry exhaustion

    call #1 → malformed
    call #2 → malformed

Verify:

- exactly two physical calls;
- appropriate LLM structured-output error propagates;
- original cause preserved.

### Retry disabled

With:

    structured_output_retries = 0

verify:

- malformed first call propagates;
- exactly one physical API call.

## 39. Architecture Boundary After WP-020

The intended responsibility split is:

    OpenAIProvider
        structured-output invocation
        narrowly bounded recovery from malformed/unparseable
        structured provider responses
                ↓

    QuestionGenerator
        one logical candidate-generation attempt
        strict generation provenance verification
                ↓

    QuestionProducer
        bounded candidate-production attempts
        generation-contract recovery (WP-019)
        candidate validation/regeneration
                ↓

    ExamOrchestrator
        exam planning
        duplicate handling
        question-level failure context
                ↓

    CLI
        thin adapter
        atomic final output

Keep these responsibilities separate.

## 40. Acceptance Criteria

WP-020 is complete when:

1. The exact malformed structured-output failure from the WP-019 acceptance run is traced and documented.
2. Recoverable structured-output failure types are explicitly identified.
3. No broad `except Exception` retry exists.
4. A provider-independent structured-output error exists if needed.
5. Original exceptions are preserved through chaining.
6. Recognized malformed structured output is retried at most once.
7. The retry repeats the same logical operation.
8. Generation is not regenerated merely because the first physical structured response was malformed.
9. Validator retrieval/context is not changed merely because the first physical response was malformed.
10. Successful first calls make exactly one physical API call.
11. Successful recovery makes exactly two physical API calls.
12. Retry exhaustion makes exactly two physical API calls when configured for one retry.
13. Authentication errors are not retried.
14. Rate-limit errors are not retried.
15. Network/provider errors are not retried.
16. Refusals are not retried.
17. Application provenance violations are not retried by the provider.
18. WP-019 generation-contract recovery remains unchanged.
19. Candidate-quality regeneration remains unchanged.
20. Structured-output retries do not create fake `QuestionAttempt` records.
21. Configuration is explicit and validated if added.
22. Unit tests cover success, recovery, exhaustion, disabled retry, and no-retry cases.
23. Integration tests cover validator recovery, generation recovery, exhaustion, and WP-019 interaction.
24. Full regression suite passes.
25. Small live smoke test is performed if credentials are available.
26. The full 2-questions-per-category acceptance run is attempted exactly once if credentials are available.
27. Full-run results are reported honestly.
28. Atomic final-output behavior remains unchanged.
29. TF-IDF/retrieval remains unchanged.
30. No embeddings/vector DB is introduced.
31. No unrelated V2 feature is introduced.
