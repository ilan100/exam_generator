# WP-034 — Coverage-Aware Target Planning

## Context

Read completely:

- docs/MASTER_PROJECT_BRIEF.md
- docs/ARCHITECTURE.md
- docs/PROJECT_STATUS.md
- implementation/WP-032_ARCHITECTURE_REVIEW.md
- implementation/WP-033_COMPLETION_REPORT.md
- implementation/WP-033_ARCHITECTURE_REVIEW.md

WP-032 introduced the new generation architecture.

WP-033 introduced the permanent Category Question Set contract.

WP-034 is the first work package that actually makes use of the information already available in `existing_questions`.

This is a planner work package.

Generation, validation, retrieval and prompts should remain unchanged.

---

# 1. Objective

Transform the planner from:

"Choose a valid target"

into

"Choose the next uncovered target."

Generation should continue behaving exactly as before.

Only target selection changes.

---

# 2. Scope

The planner may use:

- category
- existing_questions
- every field already present in those questions

The planner must NOT:

- inspect retrieval evidence
- invoke the LLM
- invoke validators
- regenerate previous questions

Planning remains deterministic.

---

# 3. Coverage Model

Introduce a deterministic internal model describing the current coverage of the category.

Suggested name:

CategoryCoverage

This is an internal application model.

Do not expose it through the public API.

Possible responsibilities include:

- tested concepts
- tested relationships
- tested question focus

The exact representation is your design decision.

---

# 4. Coverage Extraction

Implement deterministic extraction of information from existing_questions.

Do NOT use the LLM.

Do NOT summarize with prompts.

Do NOT add embeddings.

Do NOT perform semantic similarity.

Extraction must be deterministic.

If existing fields are insufficient, document exactly why.

---

# 5. Planner Behavior

Target selection should prefer uncovered knowledge.

The planner should avoid selecting:

- identical concepts
- identical relationships
- obvious rephrasings

when reasonable alternatives exist.

This remains a deterministic planning decision.

Generation is unchanged.

---

# 6. Important Constraint

The planner should never reject generation because coverage is incomplete.

Coverage influences target selection.

Coverage does NOT become another validator.

---

# 7. Existing Questions

Use every field already available in the production schema.

Do not add new fields to the request contract.

WP-033 established that contract as stable.

---

# 8. Generation Pipeline

The remaining generation pipeline must remain unchanged.

Specifically:

- QuestionProducer
- QuestionGenerator
- Relationship model
- Competitor discovery
- Validators
- Retry mechanisms
- Acceptance policy

must all remain behaviorally identical.

---

# 9. Tests

Add tests covering:

- empty question set
- one existing question
- two existing questions
- three existing questions
- deterministic extraction
- stable planning decisions
- identical generation pipeline
- backward compatibility

Regression suite must pass.

---

# 10. Evaluation

Use the same category previously used in WP-033.

Generate sequentially:

Question 1

↓

Question 2

↓

Question 3

↓

Question 4

using the CategoryQuestionSetService.

Record:

- selected targets
- selected relationships
- acceptance
- attempts

Compare with WP-033.

The primary observation is whether planning selects more diverse targets before generation begins.

---

# 11. Acceptance Run

Perform one acceptance run.

For every canonical category:

Generate exactly two questions using CategoryQuestionSetService.

No reruns.

No prompt modifications.

No planner tuning after observing results.

---

# 12. Success Criteria

Primary success criterion:

Target diversity improves before generation.

Evidence should show that the planner deliberately selects different knowledge targets rather than repeatedly selecting the same target.

Secondary criteria:

- identical validation behavior
- identical retry behavior
- identical API
- no decrease in acceptance rate

---

# 13. Scope Exclusions

Do NOT:

- redesign prompts
- redesign QuestionGenerator
- redesign validators
- redesign competitors
- redesign relationships
- introduce distinguishing facts
- add embeddings
- add semantic search
- redesign retrieval
- redesign the request contract

---

Did the planner genuinely become coverage-aware?

If not,

identify exactly what information is still missing.

Support conclusions with evidence rather than speculation.
