# 2. Objective

Implement ingestion and querying of the historical exam-question workbook:

    Data/questions_full_export.xlsx

The historical workbook has two roles:

1. It defines the canonical category set.
2. It provides historical questions used later as style/structure/terminology
   references.

Historical questions are NOT factual grounding sources.

This WP should produce:

    Excel workbook
         ↓
    workbook validation
         ↓
    HistoricalStyleReference models
         ↓
    HistoricalQuestionRepository
         ├── all questions
         ├── canonical categories
         └── questions by category

This WP must remain independent of:

- student-summary PDFs;
- course_book.pdf;
- RAG;
- embeddings;
- LLMs;
- question generation;
- factual validation.

---

# 3. Architectural Rule

The historical workbook is:

    STYLE / STRUCTURE / TERMINOLOGY DATA

It is NOT:

    FACTUAL GROUNDING DATA

Nothing implemented in this WP may expose historical questions through the
`SourceEvidenceChunk` factual-evidence interface.

Use the `HistoricalStyleReference` model established in WP-002.

Do not create a second competing historical-question domain model unless a
small ingestion-specific intermediate structure is genuinely necessary.

# 7. Worksheet Selection

Do not silently ingest an arbitrary worksheet.

Inspect the real workbook and determine its worksheet structure.

Use a clear deterministic policy.

Preferred policy:

- if the workbook has exactly one worksheet, use it;
- if it has multiple worksheets, either:
  - select a specifically configured/explicitly named worksheet, or
  - fail clearly rather than guessing.

Do not silently concatenate unrelated worksheets.

If the real workbook has a stable worksheet name and using it as the default is
appropriate, document that decision.

Keep the implementation testable with synthetic workbooks.

---

# 8. Header Validation

The first logical row of the selected worksheet must define the workbook
headers.

Required headers:

    id
    category
    question
    answer1
    answer2
    answer3
    answer4
    correct_answer_id

Requirements:

- all required headers must exist;
- missing required headers must produce a clear domain-specific ingestion error;
- column order must NOT matter;
- extra columns are allowed;
- duplicate required header names must be rejected clearly;
- blank header cells outside required columns may be ignored if harmless;
- do not silently infer renamed required columns.

For example:

    correct_answer

must NOT silently substitute for:

    correct_answer_id

unless a future explicit mapping/configuration says so.

---

# 9. Row Semantics

Each non-empty data row representing a question must be converted into the
WP-002 `HistoricalStyleReference` model.

Map:

    id                -> historical_question_id
    category          -> category
    question          -> question
    answer1           \
    answer2            > answers, preserving order
    answer3            >
    answer4           /
    correct_answer_id -> correct_answer

The answer order must be preserved exactly.

Do not shuffle answers.

Do not translate or rewrite question/answer text.

Hebrew and embedded English anatomical terminology must remain unchanged.

---

# 10. Blank Rows

Completely blank rows may be skipped.

Do not create fake questions from blank rows.

A partially populated row is NOT a blank row and should be validated normally.

For example, a row containing an ID/category but no question must fail rather
than being silently skipped.

If blank rows occur between valid questions, ingestion should continue after
them.

---

# 11. Required Row Validation

Each question row must satisfy the structural rules already established by
`HistoricalStyleReference`.

At minimum:

### id

- required;
- positive integer according to the WP-002 contract;
- bool must not be accepted;
- must be unique within the workbook.

### category

- required;
- non-empty;
- whitespace-only rejected.

### question

- required;
- non-empty;
- whitespace-only rejected.

### answers

All four required.

Each must be:

- textual;
- non-empty;
- whitespace-only rejected.

Do not require answers to be unique.

### correct_answer_id

Must be one of:

    1
    2
    3
    4

Bool must not be accepted.

Do not repair malformed rows.

---

# 12. Excel Numeric Handling

Excel/openpyxl may expose numeric cells in ways that differ from JSON/Python
input.

Handle the actual workbook representation deliberately.

For integer-semantic fields:

    id
    correct_answer_id

Accept a numeric Excel value only when it represents an exact integer.

For example:

    3       -> acceptable
    3.0     -> acceptable if openpyxl supplies it as numeric and it is exactly
               integral
    3.5     -> invalid

Do not truncate fractional numbers.

Do not parse arbitrary text such as:

    "answer 3"

into an integer.

If the real workbook stores these values as numeric strings and supporting that
is required, document the observed format and implement only a conservative,
explicit conversion.

Avoid broad coercion.

---

# 13. Text Preservation

Historical questions are style references.

Their wording therefore matters.

Preserve:

- Hebrew;
- English;
- punctuation;
- anatomical terminology;
- answer ordering.

Do not normalize terminology.

Do not translate English anatomical terms.

Do not lowercase text.

Do not collapse internal whitespace.

If leading/trailing whitespace is removed by the existing WP-002 domain model,
that established behavior is acceptable.

---

# 14. Canonical Categories

The canonical category set comes from the successfully ingested historical
questions.

The repository must expose the categories present in the workbook.

Requirements:

- categories are derived from the `category` field of valid questions;
- duplicate category values collapse to one canonical category;
- category text is preserved;
- do not apply aliases;
- do not fuzzy-match categories;
- do not infer categories from question text;
- do not use student-summary headings;
- do not use `config/category_mapping.yaml` yet.

Expose categories deterministically.

Prefer a stable ordering.

A reasonable V1 policy is first-seen workbook order.

If another deterministic ordering is chosen, document and test it.

Do not use a Python `set` as the public API if doing so makes ordering
unpredictable.

# 15. Repository API

Create a small read-only historical-question repository abstraction.

Suggested package:

    src/exam_generator/historical/
        __init__.py
        errors.py
        loader.py
        repository.py

Exact file separation may vary slightly if justified.

The public API should make future application code simple.

At minimum support:

### Load repository

Conceptually:

    HistoricalQuestionRepository.from_workbook(path)

or equivalent.

### All questions

Return all successfully loaded `HistoricalStyleReference` objects.

### Canonical categories

Return all canonical categories deterministically.

### Questions for category

Conceptually:

    repository.questions_for_category(category)

Requirements:

- exact canonical category matching only;
- no fuzzy matching;
- no alias resolution;
- preserve workbook question order within a category.

For an unknown category, choose and document one clear behavior.

Preferred behavior:

    return an empty immutable/read-only sequence

rather than raising, because future callers may naturally query availability.

However, exam-request validation against canonical categories in a later WP
should still hard-fail unknown requested categories.

Do not implement that later request-validation behavior here.

# 16. Repository Mutability

The historical repository should behave as read-only after construction.

Future generation code should not accidentally mutate the canonical historical
question collection.

You may use tuples or other appropriate immutable/read-only representations.

Do not over-engineer a persistence layer.

No database is required.

# 17. Error Model

Create clear domain-specific exceptions for ingestion failures.

For example, an exception hierarchy such as:

    HistoricalIngestionError
        WorkbookNotFoundError
        WorkbookFormatError
        WorkbookSchemaError
        HistoricalQuestionRowError

Exact names may differ.

Requirements:

- callers should not need to interpret raw openpyxl exceptions for common
  ingestion failures;
- error messages should identify the problem clearly;
- row-validation errors should identify the worksheet row number;
- when useful, identify the field involved;
- do not expose enormous stack traces as the only diagnostic.

Examples:

    Missing required workbook column: correct_answer_id

    Invalid historical question at worksheet row 17:
    correct_answer_id must be between 1 and 4

    Duplicate historical question id 42 at worksheet row 53

Do not silently skip invalid question rows.

Fail closed on malformed historical source data.

---

# 18. Workbook File Errors

Handle at least:

- workbook path does not exist;
- path is not a file;
- unreadable/invalid `.xlsx`;
- required worksheet cannot be selected;
- missing required headers;
- workbook contains no valid question rows.

These should result in clear historical-ingestion failures.

Do not catch every possible exception and convert programming bugs into generic
"ingestion failed" errors.

Catch only expected boundary/library failures where appropriate.

# 19. Empty Workbook

A workbook with headers but no question rows is invalid for this application.

Fail clearly.

Likewise, a workbook containing only blank rows after the header is invalid.
