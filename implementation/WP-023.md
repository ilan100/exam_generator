# WP-023 — Partial Exam Completion and Per-Question Failure Reporting

## 1. Context

Before implementation, read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-023.md`

WP-001 through WP-022 are complete and approved.

The current orchestration behavior is all-or-nothing:

    planned questions
        ↓
    QuestionProducer called sequentially
        ↓
    one question-local production failure
        ↓
    ExamOrchestrator aborts
        ↓
    CLI exits failure
        ↓
    no exam/audit output is written

This behavior was useful during early strict pipeline development, but it is no
longer appropriate for the user-facing product.

The WP-022 acceptance run demonstrated the problem clearly:

    requested: 40
    successfully completed before failure: 37
    question 38 failed
    result: entire exam discarded

The user should receive the valid questions already produced and explicit,
honest information about planned questions that could not be produced.

WP-023 changes orchestration/output semantics.

It must NOT weaken question validation or acceptance.

A failed question remains failed.

---

## 2. Objective

Change exam generation from:

    every planned question must succeed
        OR
    entire exam fails

to:

    attempt every planned question when safe to continue
        ↓
    accepted questions are preserved
        +
    question-local failures are preserved explicitly
        ↓
    final result may be COMPLETE or PARTIAL

Example:

    requested: 40
    accepted: 39
    failed: 1

The clean exam contains only the 39 valid accepted questions.

The audit/result records the failed planned question and why it failed.

Generation continues after that question whenever the failure is classified as
question-local.

---

## 3. Core Safety Rule

WP-023 must distinguish:

### Question-local failure

A failure associated with producing one planned question where continuing with
the next planned question remains meaningful and safe.

These should be recorded and orchestration should continue.

### System-level failure

A failure indicating that continuing the entire exam is unsafe, meaningless,
or likely to fail globally.

These should still abort the exam immediately.

Do NOT convert every exception into a partial result.

Unexpected programming exceptions must still surface normally.

---

## 4. Question-Local Failures

Inspect the existing exception hierarchy and classify from the actual code.

At minimum, evaluate these existing failure classes:

- `QuestionAttemptsExhaustedError`
- exhausted generation-contract recovery from WP-019
- exhausted grounding provenance recovery from WP-021
- exhausted textbook provenance recovery from WP-021
- other known failures that are demonstrably local to one candidate/question

The exact classification must follow the existing hierarchy rather than
string matching.

A question-local failure should produce a structured failure record and allow
the orchestrator to proceed to the next planned question.

Do not silently discard the failure.

---

## 5. System-Level Failures

Failures indicating a system/infrastructure problem must still abort.

At minimum inspect and classify:

- authentication failure;
- missing/invalid API key;
- provider/rate-limit failure;
- connection/provider availability failure;
- configuration failure;
- prompt repository/configuration failure;
- corpus/index initialization failure;
- unrecoverable global retrieval/configuration failure;
- unexpected programming exceptions.

Do not continue generating dozens of questions after discovering, for example,
that the OpenAI API key is invalid.

Use explicit exception types/hierarchy.

Do not classify failures by parsing error-message strings.

---

## 6. Be Conservative About Ambiguous Failures

If an existing exception type can represent both:

- a question-local failure;
- and a global/system failure;

do not guess.

Inspect where it is raised and either:

1. classify it safely based on a more specific existing subtype; or
2. introduce the smallest justified subtype/context needed to make the
   distinction explicit.

Do not create a broad catch-all.

---

## 7. Exam Generation Status

Introduce an explicit exam-generation completion status.

Prefer something conceptually equivalent to:

    COMPLETE
    PARTIAL

A run is:

### COMPLETE

when every planned question produced an accepted question.

### PARTIAL

when orchestration safely reached the end of the plan but one or more planned
questions failed locally.

A system-level fatal failure is not PARTIAL completion; it still aborts.

Use an enum or similarly typed representation consistent with existing models.

---

## 8. Failed Planned Question Model

Introduce a structured model for a planned question that could not be
successfully produced.

Conceptually:

    FailedPlannedQuestion

It should preserve enough context to understand exactly what failed.

At minimum consider:

- original planned position;
- canonical category;
- generation mode;
- failure type;
- failure message;
- attempts performed, when available;
- attempt history, when available;
- underlying failure classification/context.

Reuse existing attempt/result models rather than duplicating them.

Do not fabricate unavailable candidate or validator information.

---

## 9. Preserve Attempt History

When failure occurs after bounded attempts, preserve all available history.

For example:

    planned question 38
        attempt 1
            generation contract failure

        attempt 2
            candidate produced
            MCQ rejected

        attempt 3
            generation contract failure

        final:
            FAILED

That history is valuable diagnostic/audit information.

If a failure occurs before an attempt record exists, preserve only what is
actually known.

Never fabricate a CandidateQuestion or validation result merely to fill the
failure structure.

---

## 10. ExamGenerationResult

Extend or minimally evolve `ExamGenerationResult` so a successfully completed
orchestration run can represent:

- planned question count;
- accepted productions;
- failed planned questions;
- completion status.

Conceptually:

    ExamGenerationResult
        status
        planned_question_count
        successful_productions
        failed_questions

Use naming consistent with the existing code.

Preserve deterministic planned ordering.

A PARTIAL result is a legitimate returned result, not an exception.

---

## 11. Continue After Question-Local Failure

Modify `ExamOrchestrator.generate_exam()` so that:

    for planned_question in plan:
        try production
        if accepted:
            preserve success
        elif known question-local failure:
            preserve structured failure
            continue
        elif system-level failure:
            abort
        elif unexpected exception:
            propagate

Do not rerun a failed planned question beyond the retry/attempt behavior already
owned by existing components.

WP-023 adds continuation, not additional retries.

---

## 12. No Retry Ownership Changes

Do NOT change:

### WP-019

Generation-contract recovery remains owned by `QuestionProducer`.

### WP-020

Malformed structured-output retry remains owned by `OpenAIProvider`.

### WP-021

Validator provenance recovery remains owned by the validators.

### WP-013

Candidate-quality regeneration remains bounded by the existing
`max_generation_attempts`.

WP-023 operates only after those existing mechanisms have reached their normal
outcome.

Do not add another retry layer in `ExamOrchestrator`.

---

## 13. Duplicate Handling

Preserve existing duplicate-question protection.

If duplicate replacement attempts exhaust for one planned question and the
existing semantics make this a question-local failure, record the failed
planned question and continue.

Do not weaken duplicate detection to make partial exams appear more complete.

---

## 14. Clean Exam Semantics

The clean exam must contain:

    accepted questions only

Never include an invalid/unaccepted candidate in the clean exam.

If:

    40 planned
    39 accepted
    1 failed

then the clean exam contains:

    39 questions

The failed question belongs in audit/result metadata, not among usable exam
questions.

---

## 15. Clean Exam Numbering

Accepted questions in the clean exam must be numbered contiguously:

    1
    2
    3
    ...
    N

Do not leave gaps corresponding to failed planned positions.

Example:

    planned 37 → accepted
    planned 38 → failed
    planned 39 → accepted
    planned 40 → accepted

Clean exam numbering should be:

    ...
    37
    38
    39

not:

    ...
    37
    39
    40

The audit must preserve original planned positions so traceability is not lost.

---

## 16. Preserve Planned Position in Audit

The audit/result must distinguish:

    clean exam question number

from:

    original planned position

This is important after failures.

For example:

    planned_position = 39
    final_exam_number = 38

The user/auditor must be able to determine that planned question 38 failed and
planned question 39 became clean exam question 38.

Introduce the smallest model extension necessary.

Do not overload an existing field with two meanings.

---

## 17. Audit Semantics

The audit must represent the whole generation run, not merely successful
questions.

It should contain:

- requested/planned count;
- accepted count;
- failed count;
- COMPLETE/PARTIAL status;
- successful question audit records;
- failed planned-question records;
- original planned positions;
- available attempt histories;
- failure types/messages.

Canonical provenance behavior from WP-022 remains unchanged.

Do not leak local `Evidence N` references.

---

## 18. Clean Exam vs Audit

Maintain the existing separation:

### Clean exam

User-usable exam content.

Contains accepted questions only.

### Audit

Full provenance/production record.

Contains:

- accepted questions;
- failed planned questions;
- attempts;
- validation results;
- failure reasons;
- provenance;
- completion status.

Do not contaminate the clean exam with internal diagnostics unless the existing
clean output contract explicitly has metadata suitable for a simple partial
status/count.

Prefer keeping detailed failures in the audit.

---

## 19. User Visibility of Partial Result

The user must be able to tell that the exam is partial.

Do not write a 39-question exam after a 40-question request without clearly
communicating that one question failed.

At minimum the CLI must report something conceptually equivalent to:

    Exam generation completed with partial results.
    Requested: 40
    Generated: 39
    Failed: 1

    Failed planned questions:
      #38 — תאי מערכת העצבים — INDEPENDENT
      reason: generation attempts exhausted

Exact wording may follow current CLI style.

---

## 20. Output Writing

For COMPLETE and PARTIAL successful orchestration results:

    write exam output
    write audit output

The existing atomic file-writing guarantees should remain.

"Atomic" should now mean:

> once orchestration has completed its full plan safely, write the resulting
> COMPLETE or PARTIAL artifacts atomically.

It should no longer mean:

> refuse all output because one question-local failure occurred.

System-level fatal failures should still produce no normal final exam/audit
output unless existing behavior explicitly says otherwise.

---

## 21. CLI Exit Semantics

Define explicit CLI behavior for PARTIAL success.

Preferred semantics:

    COMPLETE → exit 0
    PARTIAL  → exit 0, with clear warning/status output
    FATAL    → existing non-zero failure code

Rationale:

A partial exam is now an intentional successful product result containing
usable output, not a pipeline crash.

If the existing CLI conventions strongly justify a distinct non-zero partial
exit code, document the tradeoff before choosing it.

Prefer exit 0 unless there is a concrete compatibility reason not to.

Do not classify PARTIAL as the same thing as fatal generation failure.

---

## 22. Edge Case — All Questions Fail Locally

Explicitly decide and document behavior if:

    planned = N
    accepted = 0
    failed = N

Preferred behavior:

- orchestration has technically completed;
- audit is valuable and should be written;
- clean exam contains zero questions only if the existing clean-exam model can
  honestly represent that state.

Inspect the existing `ExamOutput` constraints.

If the clean exam requires at least one question, do not weaken the model
casually.

Choose the smallest honest behavior, for example:

- write audit;
- clearly report zero usable questions;
- handle clean-exam output separately.

Document and test this edge case.

Do not ignore it.

---

## 23. Output Consistency

Update consistency validation so it understands partial results.

For example:

    planned_count =
        accepted_count + failed_count

must hold.

Successful audit entries must correspond exactly to accepted productions.

Failed entries must correspond exactly to failed planned positions.

No planned position may be:

- represented twice;
- missing from both success/failure accounting;
- both accepted and failed.

Clean exam question count must equal accepted count.

---
