WP-037 produced a strong positive result:

- concept-anchored evidence substantially improved target-to-question alignment;
- manually verified alignment increased from approximately 45% in WP-036 to 87.5% in WP-037.

However, WP-037 also exposed a new downstream problem.

The selected concept is often correctly tested, but the generated answer may use a different language/script representation.

Example:

Selected concept:

    Superior cerebellar artery

Generated answer:

    עורק סופריור צרבלרי

WP-034 coverage currently relies on exact textual matching.

Therefore the system fails to recognize that the concept was already tested.

The result is:

```text
Concept selected
    ↓
Concept correctly tested
    ↓
Answer expressed in another language/script
    ↓
Coverage fails to recognize it
    ↓
Same concept selected again
    ↓
Duplicate generation/rejection
    ↓
Possible exhaustion
```

WP-038 must address this specific problem.

---

# 1. Objective

Introduce a deterministic concept-identity mechanism so that coverage can recognize the same concept across safe, explicitly supported language/script representations.

The goal is:

> Recognize genuine identity equivalence without introducing semantic similarity.

The public API must not change.

---

# 2. Core Principle

The following distinction is mandatory.

## Identity equivalence

Two expressions refer to the same named concept.

Example:

```text
Superior cerebellar artery
עורק סופריור צרבלרי
```

when the equivalence can be established deterministically and safely.

## Semantic similarity

Two expressions describe related but potentially different knowledge.

Example:

```text
Superior cerebellar artery
arterial supply of the cerebellum
```

These MUST NOT automatically be treated as the same concept.

Do not implement semantic similarity.

Do not use embeddings.

Do not use an LLM judge.

Do not use fuzzy matching.

---

# 3. Scope

This WP is limited to the three existing pilot categories:

- אספקת דם
- מסילות עצביות
- גרעיני הבסיס

Do not expand the concept-anchored system to additional categories.

The purpose of this WP is to fix the coverage loop before expansion.

---

# 4. Investigate Existing Data First

Before implementing anything, inspect the existing models and live WP-037 data.

Determine exactly what information is available for:

- selected concept;
- source evidence;
- generated question;
- correct answer;
- category;
- concept inventory;
- canonical evidence chunk.

Do not invent additional metadata unless necessary.

Prefer deriving concept identity from existing information.

---

# 5. Concept Identity Model

Introduce an internal concept-identity representation if necessary.

Suggested conceptual structure:

```text
ConceptIdentity
    canonical_form
    normalized_forms
    explicitly_supported_language_forms
```

The exact model is your design decision.

It must remain internal.

Do not modify:

- CategoryQuestionSetRequest
- CategoryQuestionSetResponse
- ExamQuestion
- public schemas

unless absolutely unavoidable.

Prefer no public contract changes.

---

# 6. Deterministic Normalization

Investigate and implement only normalization operations that are demonstrably safe.

Potential examples:

- whitespace normalization;
- punctuation normalization;
- case normalization where appropriate;
- harmless Unicode normalization;
- deterministic handling of known orthographic variations.

Do not implement broad fuzzy matching.

Do not use edit distance as a general equivalence mechanism.

Do not infer meaning from approximate spelling.

---

# 7. Cross-Language / Cross-Script Identity

This is the central question of WP-038.

Determine whether the project already has enough deterministic information to safely recognize cases such as:

```text
Superior cerebellar artery
עורק סופריור צרבלרי
```

without an LLM.

Investigate the existing corpus and generated data.

Possible approaches may include:

- explicit bilingual forms already present in the same evidence;
- deterministic transliteration where technically reliable;
- local evidence-based alias extraction;
- canonical terminology already present in the corpus;
- explicit English/Hebrew pairs already appearing together.

Do NOT introduce a general bilingual dictionary.

Do NOT manually author a large concept mapping table.

Do NOT use an external knowledge base.

If safe deterministic cross-script identity cannot be established, report that honestly rather than guessing.

---

# 8. Preferred Principle: Evidence-Derived Identity

If possible, derive alternate forms from the same canonical evidence used to create the concept.

For example, if the source evidence itself contains:

```text
Superior cerebellar artery (עורק סופריור צרבלרי)
```

then both forms may safely belong to the same ConceptIdentity.

This is fundamentally different from guessing that two arbitrary strings are equivalent.

Prefer:

```text
Evidence-derived identity
```

over:

```text
externally inferred identity
```

---

# 9. Coverage Matching

Refactor coverage so that it compares concept identity rather than raw concept text.

Current conceptual behavior:

```text
concept_text == answer_text
```

Target behavior:

```text
ConceptIdentity(selected_concept)
        ↓
ConceptIdentity(answer)
        ↓
same identity?
```

The matching mechanism must remain deterministic.

---

# 10. Coverage Safety

The matching mechanism must be conservative.

False positive coverage is more dangerous than false negative coverage.

Example:

If the system cannot prove that:

```text
A
```

and

```text
B
```

are the same concept,

they must remain separate.

Do not collapse concepts merely because they are:

- related;
- in the same anatomical system;
- synonyms guessed from context;
- functionally connected.

---

# 11. Generation Must Remain Unchanged

Do NOT modify:

- QuestionGenerator
- QuestionProducer
- OpenAIProvider
- generation prompts
- generation retry behavior
- structured-output recovery
- generation-contract recovery

WP-037 already demonstrated that concept anchoring improves generation alignment.

WP-038 should only fix recognition of the resulting concept.

---

# 12. Anchoring Must Remain Unchanged

Do not redesign the WP-037 concept anchoring algorithm.

Do not widen the evidence window.

Do not change the pilot categories.

If tests reveal a direct incompatibility between anchoring and identity matching, document it separately.

---

# 13. Validators Must Remain Unchanged

Do NOT modify:

- GroundingValidator
- MCQValidator
- CategoryValidator
- QualityValidator
- TextbookValidator

Do not create a new diversity validator.

Coverage identity is a planning concern, not a validation concern.

---

# 14. Attempt / Retry Semantics

Do not introduce a new retry mechanism.

The purpose is to prevent unnecessary duplicate selection before generation.

The system should not:

```text
generate
reject for duplicate
retry
```

when the planner could have recognized the concept as already covered.

---

# 15. Unit Tests

Add comprehensive deterministic tests for:

### Normalization

- whitespace;
- punctuation;
- case;
- Unicode normalization;
- supported orthographic variants.

### Identity

- identical concept;
- explicitly paired bilingual forms;
- unrelated concepts;
- related but non-identical concepts;
- ambiguous forms.

### Coverage

- selected concept recognized from same-language answer;
- selected concept recognized from supported alternate-language answer;
- unsupported alternate representation remains unmatched;
- semantically related but different concept remains unmatched.

### Safety

Explicitly test that the following do NOT become equivalent merely because they are related:

```text
structure
function
source
destination
pathway
general system
```

# 19. Primary Success Criterion

The primary objective is:

> When the generated answer is an explicitly supported representation of the selected concept, coverage must recognize it as already covered.

The critical failure from WP-037:


must be eliminated if the representation can be established deterministically from available evidence.

# 22. No Expansion Yet

Even if WP-038 succeeds:

Do NOT immediately expand to all categories.

First demonstrate that the complete loop works:

```text
Concept Inventory
      ↓
Coverage
      ↓
Concept Selection
      ↓
Concept-Anchored Evidence
      ↓
Question Generation
      ↓
Aligned Question
      ↓
Concept Identity Recognition
      ↓
Coverage Update
      ↓
Next Concept
```

Only after this loop is stable should expansion be considered.

---

# 23. Failure Interpretation

Possible outcomes:

### Outcome A — Strong success

Language/script identity is recognized safely.

Target rotation returns.

Alignment remains high.

Acceptance recovers.

→ Recommend expansion pilot.

### Outcome B — Identity works for some cases only

Some bilingual/orthographic forms can be proven, others cannot.

→ Keep conservative partial identity support and document boundaries.

### Outcome C — Safe deterministic cross-language identity is not feasible

→ Do not guess.

→ Preserve exact matching.

→ Document the architectural limitation and reconsider whether generation language should instead be constrained.

### Outcome D — False-positive matches appear

→ Stop.

Do not expand.

False coverage is a serious architectural failure.
