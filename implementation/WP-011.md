# 2. Objective

Implement the remaining primary candidate-quality validators:

```text
CandidateQuestion
      │
      ├── MCQ validation
      ├── Category validation
      └── Quality validation
```

using the separate WP-008 production prompts and WP-007 validation LLM profile.

WP-011 determines whether a candidate:

1. works as a proper one-best-answer MCQ;
2. genuinely belongs to the requested canonical category;
3. meets general language, clarity, and exam-quality expectations.

These judgments remain separate from factual grounding.

---

# 3. Architectural Boundary

The validation pipeline now conceptually contains:

```text
CandidateQuestion
      │
      ├── GroundingValidator       WP-010
      │       factual support
      │
      ├── MCQValidator             WP-011
      │       MCQ construction
      │
      ├── CategoryValidator        WP-011
      │       semantic category fit
      │
      └── QualityValidator         WP-011
              language / clarity / quality
```

Do not collapse these into a single LLM call or generic validation result.

Each validator must return its existing WP-002 result contract.

This separation is important for future audit and retry decisions: we need to know **why** a candidate failed.

---

# 4. Existing Contracts

Inspect and reuse the actual existing WP-002 models, expected to include:

* `MCQValidationResult`;
* `CategoryValidationResult`;
* `QualityValidationResult`.

Do not redesign these contracts merely for implementation convenience.

Reuse:

* WP-008 candidate formatting;
* WP-008 `mcq`, `category`, and `quality` prompts;
* WP-007 `LLMProvider`;
* `LLMProfile.VALIDATION`.

No OpenAI-specific code belongs in this layer.

---

# 5. Public Interfaces

Create focused validation interfaces conceptually equivalent to:

```python
MCQValidator.validate(candidate) -> MCQValidationResult

CategoryValidator.validate(candidate) -> CategoryValidationResult

QualityValidator.validate(candidate) -> QualityValidationResult
```

Naming may differ slightly if consistent with the existing validation package.

Dependencies should be injectable for deterministic unit testing.

Provide straightforward default construction using existing configuration/provider/prompt infrastructure where appropriate.

Avoid unnecessary generic validator frameworks.

Three small explicit validators are preferable to an abstraction that obscures their different responsibilities.

---

# 6. MCQ Validation

The MCQ validator determines whether the candidate functions as a proper one-best-answer multiple-choice question.

It should assess the semantics already established by the WP-008 MCQ prompt and WP-002 result model, including:

* exactly one clearly best answer;
* distractors are plausible enough to make the question meaningful;
* no second answer is reasonably defensible as equally correct;
* no obvious answer-position or wording clues;
* answers are coherent with the question;
* the question is answerable as written.

Do not make factual grounding its primary responsibility.

A question may therefore be:

```text
grounded = true
MCQ-valid = false
```

For example, the correct answer could be supported by the source while the distractors are obviously absurd.

That distinction must remain possible.

---

# 7. Category Validation

The category validator determines whether the candidate semantically belongs to its canonical category.

Use the category already carried by the `CandidateQuestion`.

This is not category alias resolution.

WP-006 already owns deterministic resolution such as:

```text
input alias
    ↓
canonical category
```

WP-011 instead asks:

```text
Does this actual question really test
the canonical category it claims to test?
```

Use the WP-008 category-validation prompt.

Do not retrieve another category or silently reclassify the candidate.

The validator judges the supplied category/question pairing.

---

# 8. Quality Validation

The quality validator evaluates general exam-question quality according to the existing WP-008 prompt and WP-002 result contract.

It should cover the established concerns such as:

* clarity;
* natural Hebrew;
* appropriate terminology;
* grammatical/readability quality;
* unnecessary ambiguity;
* malformed wording;
* reasonable neuroanatomy exam style.

English/Latin anatomical terminology may appear naturally inside Hebrew questions and answers.

Do not reject a candidate merely because terms such as:

```text
Medulla Oblongata
Vertebral Foramen
Corticospinal tract
```

appear in English/Latin when their use is natural in the course context.

Do not turn this validator into a factual grounding validator or textbook checker.

---

# 9. Validation Execution

Each validator must:

1. format the candidate using the established WP-008 infrastructure;
2. load/render its own production validation prompt;
3. construct the established system + user message sequence;
4. call WP-007 using:

```text
LLMProfile.VALIDATION
```

5. request its corresponding structured Pydantic result;
6. return that result.

Each validator invocation represents exactly one semantic LLM call.

Do not add retries.

---

# 10. Independence of Results

Do not make one validator depend on another validator's verdict.

For example:

```text
MCQValidator
```

must not require grounding to have passed first.

Similarly:

```text
QualityValidator
```

must not automatically fail because category validation failed.

Each validator evaluates its own concern.

Later orchestration will decide which validators must pass for a candidate to be accepted.

This also allows diagnostics such as:

```text
Grounding   PASS
MCQ         FAIL
Category    PASS
Quality     FAIL
```

which is much more useful than a single `valid=false`.

---

# 11. No New Retrieval

WP-011 should not perform factual retrieval.

MCQ, category, and quality validation operate on the candidate itself using their established prompts.

Do not retrieve:

* student-summary chunks;
* course-book chunks;
* historical questions.

Grounding retrieval belongs to WP-010.

Textbook retrieval belongs to WP-012.

If an existing result/prompt contract clearly requires factual evidence contrary to this assumption, stop and report the mismatch rather than inventing a new retrieval path.

---

# 12. Negative Verdict vs Operational Failure

Maintain the distinction established in WP-010:

```text
validator executed successfully
passed = false
```

is a normal validation result.

It must not raise an exception merely because the candidate is poor.

By contrast:

```text
provider failure
prompt failure
invalid structured response
```

is an operational failure and should propagate through the appropriate existing error boundary.

Do not convert operational errors into negative quality verdicts.

---

# 13. Structured Result Integrity

Use the existing Pydantic validation contracts directly as the structured response models unless inspection of the actual models reveals a concrete reason not to.

Unlike WP-009, these results are themselves model judgments, so fields such as:

```text
passed
reason
quality assessment
```

legitimately belong to the LLM response.

Do not silently repair invalid structured results.

---

# 14. Tests

Add focused tests covering all three validators.

At minimum demonstrate:

### MCQ

* good one-best-answer question can pass;
* ambiguous/multiple-defensible-answer question can fail;
* poor distractors can fail;
* MCQ prompt is used;
* `MCQValidationResult` is returned.

### Category

* correctly categorized question can pass;
* semantically mismatched category can fail;
* canonical category from the candidate is supplied to the prompt;
* no alias resolution/reclassification is performed;
* `CategoryValidationResult` is returned.

### Quality

* clear natural question can pass;
* malformed/ambiguous wording can fail;
* mixed Hebrew/English anatomical terminology survives unchanged;
* `QualityValidationResult` is returned.

### Architecture

Also verify:

* all three use `LLMProfile.VALIDATION`;
* each invocation makes one LLM call;
* validators use separate WP-008 prompts;
* validators do not invoke each other;
* no retrieval occurs;
* no course-book or historical source is used;
* `passed=False` returns normally;
* provider/prompt failures remain operational errors;
* candidates are not mutated;
* no retry/regeneration occurs.

Mock all LLM calls in unit tests.

Run the full regression suite offline.
