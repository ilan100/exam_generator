# 3. Architectural Source Roles

The established source hierarchy remains mandatory.

## Student summaries

`SourceType.STUDENT_SUMMARY`

Student-summary chunks are the only factual source type that may later satisfy the project's primary grounding requirement.

WP-006 retrieves candidate evidence.

WP-006 does NOT decide whether retrieved evidence actually grounds a generated question.

## Course book

`SourceType.COURSE_BOOK`

Course-book chunks are secondary reference/check material.

Course-book retrieval must remain structurally or operationally distinguishable from student-summary retrieval.

Do not merge course-book results into student-summary results in a way that could allow future grounding code to treat textbook evidence as primary grounding.

## Historical questions

Historical questions remain style/structure/terminology data.

They must not enter the factual retrieval index.

Do not:

* index `HistoricalStyleReference` as factual content;
* return historical questions from factual retrieval;
* convert historical questions into `SourceEvidenceChunk`.

The historical repository participates in WP-006 only as the authoritative source of canonical category names.

# 5. Why Lexical Retrieval Is the V1 Baseline

The source corpus contains Hebrew, English anatomical terminology, and mixed Hebrew/English text.

The V1 retrieval layer should therefore avoid assumptions requiring English-specific stemming, lemmatization, stop-word lists, or language models.

Prefer Unicode-aware lexical features.

A character n-gram TF-IDF representation is acceptable and may be preferable for V1 because it naturally handles:

* Hebrew;
* English;
* mixed terminology;
* spelling variation;
* punctuation differences;
* inflectional variation;
* anatomical terms embedded in Hebrew text.

A reasonable initial configuration is conceptually:

```text
analyzer: char_wb
ngram_range: [3, 5]
```

or a similarly conservative Unicode-safe configuration.

If inspection/testing demonstrates that a different simple TF-IDF configuration is clearly superior for this corpus, document the choice and rationale.

Do not perform an extensive retrieval-quality optimization exercise in this WP.

# 7. Retrieval Result Contract

Do not modify `SourceEvidenceChunk` to add retrieval-specific metadata.

Introduce a small retrieval-layer result model/value object conceptually equivalent to:

```text
RetrievalResult
    chunk
    score
    rank
```

Requirements:

### chunk

The original `SourceEvidenceChunk`.

Do not duplicate its provenance fields unnecessarily.

### score

A deterministic numeric relevance score.

For cosine similarity / normalized TF-IDF similarity, use a float in the natural `[0.0, 1.0]` range where practical.

Do not invent a confidence interpretation.

The score means retrieval similarity/relevance only.

It is NOT:

* grounding confidence;
* factual confidence;
* LLM confidence;
* probability of correctness.

### rank

1-based positive integer.

Bool rejected if represented through validated models.

Rank must correspond to returned result order.

The result representation should behave as read-only after construction.

# 9. Retrieval API

Provide a small public retrieval API.

Conceptually:

```python
results = index.search(
    query,
    *,
    top_k=None,
)
```

Requirements:

* query must be non-empty;
* whitespace-only query rejected;
* `top_k` must be positive;
* bool rejected;
* default `top_k` comes from configuration/application construction where appropriate;
* return an immutable/read-only ordered sequence;
* results ordered best-first;
* rank starts at 1;
* never return more than `top_k`;
* never return more results than corpus chunks;
* original `SourceEvidenceChunk` instances/data remain unchanged.

Do not print from library code.

# 10. Zero-Similarity Results

Do not fill `top_k` with meaningless zero-score chunks merely to satisfy the requested count.

If the query has no lexical overlap according to the configured representation, return an empty result sequence.

More generally:

```text
only results with score > 0
```

should be returned unless implementation details provide a compelling reason for a tiny deterministic numerical tolerance.

Document any tolerance used.

The number of returned results may therefore be less than `top_k`.

---

# 11. Deterministic Tie Breaking

Retrieval ordering must be deterministic.

When two chunks have equal retrieval scores, use the established corpus order as the secondary ordering criterion.

Conceptually:

```text
score descending
    ↓
original corpus position ascending
```

Do not use random tie breaking.

Repeated construction and retrieval from unchanged corpus/config/query must produce identical:

* chunk IDs;
* scores within normal deterministic floating-point behavior;
* ranks;
* result ordering.

# 12. Source-Type Integrity

A retrieval index must not silently mix incompatible factual roles.

If constructed from the student-summary corpus:

```text
all indexed chunks must be STUDENT_SUMMARY
```

If constructed from the course-book corpus:

```text
all indexed chunks must be COURSE_BOOK
```

A generic single-source-type retrieval index is preferred.

If `FactualSourceCorpus` technically permits multiple source types, the retrieval constructor must either:

1. require exactly one source type; or
2. require an explicit allowed source type and validate every chunk.

Preferred V1 behavior:

```text
one retrieval index = one SourceType
```

This makes the authority boundary difficult to misuse later.

Fail clearly if a mixed-source corpus is supplied.

Do NOT solve weak categories in this WP using guessed mappings, embeddings, or LLM query expansion.

# 30. No Grounding Decision

Retrieval relevance and factual grounding are different concepts.

WP-006 must never expose an API such as:

```text
is_grounded = score > X
```

Do not establish a retrieval-score threshold as factual validation.

A high retrieval score means only:

```text
this chunk is lexically similar to the retrieval query
```

The future grounding validator must independently determine whether supplied evidence supports a candidate question and correct answer.

# 32. No Text Rewriting
