# 1. New Hard Architectural Requirement

The project has an explicit language policy:

> **English is the canonical language whenever an English representation exists. Hebrew may be used only when no English representation exists for that specific item.**

This policy was part of the project's original requirements and is now being explicitly reaffirmed as a hard architectural rule.

The LLM must NOT choose between English and Hebrew based on what sounds natural.

The application must deterministically establish the preferred representation before generation.

---

# 2. The Rule

For every relevant item:

```text
English exists
    ↓
USE ENGLISH

English does not exist
    ↓
Hebrew is allowed
```

Therefore:

```text
English + Hebrew
    → English only

English only
    → English

Hebrew only
    → Hebrew

Neither / unknown
    → do not invent a representation
```

The rule applies even if the surrounding evidence is primarily Hebrew.

---

# 3. Examples

## Example A — Both languages exist

Evidence:

```text
Superior cerebellar artery
עורק צרבלרי עליון
```

Selected/generated representation MUST be:

```text
Superior cerebellar artery
```

Never:

```text
עורק צרבלרי עליון
```

---

## Example B — Both languages exist

Evidence:

```text
Corpos Striatum
קורפוס סטריאטום
```

Use:

```text
Corpos Striatum
```

Never:

```text
קורפוס סטריאטום
```

This is especially important because WP-040 generated correct Hebrew answers such as:

```text
קורפוס סטריאטום
```

which caused the coverage system not to recognize that `Corpos Striatum` had already been tested.

WP-041 should prevent this problem at generation time.

---

## Example C — Hebrew only

If the evidence contains:

```text
מונח רפואי מסוים
```

and no English representation exists anywhere in the relevant available evidence, Hebrew is allowed.

Do not invent an English translation.

Do not ask an LLM to translate it.

---

# 4. Objective

Implement the English-first language policy deterministically so that:

1. English is selected whenever available.
2. Hebrew is used only when English is unavailable.
3. Generation receives the already-selected language representation.
4. The LLM does not independently choose the language.
5. Correct answers follow the selected representation.
6. Coverage can continue using the existing deterministic identity mechanism.
7. No cross-language fuzzy matching is required for bilingual concepts.

The intended result is:

```text
Bilingual evidence
      ↓
English selected
      ↓
English target
      ↓
English target-aware generation
      ↓
English correct answer
      ↓
Coverage recognizes target
      ↓
Next concept
```

---

# 5. Important Architectural Principle

Do NOT solve the previous problem by making coverage smarter.

Do NOT add:

- fuzzy matching;
- semantic matching;
- embeddings;
- LLM identity judges;
- transliteration matching;
- external terminology APIs;
- bilingual similarity scoring.

The preferred architecture is:

```text
Choose canonical representation correctly
        ↓
Generate using that representation
        ↓
Existing deterministic coverage works
```

---

# 6. First Investigate Existing Code

Before implementing anything, inspect:

- concept extraction;
- concept inventory construction;
- concept identity;
- concept selection;
- concept anchoring;
- generation context;
- generation prompts;
- generated answer handling;
- coverage.

Determine where the application already has access to:

- English concept text;
- Hebrew concept text;
- source evidence;
- source page/chunk;
- canonical concept identity.

Do not assume a bilingual representation is available globally.

---

# 7. Critical Question

Determine:

> **How can the application know deterministically that an English representation exists for a specific item?**

Possible existing sources include:

- the same evidence chunk;
- the same source page;
- the same concept extraction result;
- an existing canonical concept representation;
- existing structured metadata.

Use the strongest existing evidence.

Do not introduce an external terminology source in this WP.

---

# 8. Representation Discovery

If the current system already has both:

```text
English representation
Hebrew representation
```

for the same concept, preserve that relationship.

If the evidence itself explicitly contains both forms together, that is the strongest basis.

For example:

```text
Superior cerebellar artery (עורק צרבלרי עליון)
```

clearly provides both representations.

If English and Hebrew appear in unrelated places, do NOT automatically assume they are the same concept.

Do not recreate the cross-language matching problem that WP-038 deliberately refused to solve.

---

# 9. Important Boundary

WP-041 is NOT a general bilingual concept-matching system.

It should only enforce:

> English-first selection when an English representation is already available and deterministically associated with the selected concept.

If such an association cannot be established safely:

```text
do not guess
```

If only Hebrew is available:

```text
Hebrew is allowed
```

---

# 10. Preferred Internal Representation

Investigate whether the existing concept model can represent:

```text
canonical English representation
optional Hebrew representation
language availability
```

Prefer reusing existing structures.

If a small internal model is required, keep it internal.

Do not change public API contracts unless absolutely necessary.

Do not duplicate information already represented by ConceptIdentity.

---

# 11. Concept Identity Interaction

WP-038's ConceptIdentity mechanism remains.

WP-039's truncation recovery remains.

Do not weaken either mechanism.

The desired relationship is:

```text
Concept extraction
      ↓
Concept completeness
      ↓
Concept identity
      ↓
English-first representation selection
      ↓
Concept selection
      ↓
Generation
```

If the architecture naturally requires language selection before ConceptIdentity, explain why and implement the smallest correct change.

---

# 12. Generation Interaction

WP-040 target-aware generation remains fully active.

WP-041 should NOT replace it.

The generation context should now contain something equivalent to:

```text
TARGET CONCEPT:
Corpos Striatum

TARGET LANGUAGE:
English

TARGET ANSWER:
must identify Corpos Striatum
```

The LLM should not have to decide:

```text
English or Hebrew?
```

That decision belongs to the application.

---

# 13. Generation Prompt

Update the generation prompt only as necessary.

The prompt should explicitly communicate the language requirement.

For example, conceptually:

```text
Use English for the target and correct answer whenever an English
representation is provided.

Do not translate the target into Hebrew when an English
representation is available.

Use Hebrew only when no English representation is provided.
```

Use the project's existing prompt style.

Do not perform a large prompt rewrite.

---

# 14. Question Language

The policy applies not only to the correct answer.

When the selected target has an English representation, the generated question should preferably use English terminology for that target.

For example:

```text
Target:
Superior cerebellar artery

Question:
Which artery ...?
```

not:

```text
Which עורק ...?
```

The question may still contain other source material as appropriate, but the selected target terminology should use the canonical English representation.

---

# 15. Correct Answer

If an English target representation exists:

```text
correct answer → English target
```

If only Hebrew exists:

```text
correct answer → Hebrew target
```

Do not allow the model to switch languages merely because the question context contains Hebrew.

---

# 16. Multiple English Forms

Investigate whether the same item can have multiple English representations.

Examples might include:

```text
full term
abbreviation
alternate English naming
```

Do not introduce arbitrary synonym selection.

Determine whether the existing ConceptIdentity mechanism already establishes accepted equivalents.

Prefer one deterministic canonical English form.

If the project already has a canonical English representation, use it.

---

# 17. Symbols and Mixed Representations

The original requirement explicitly includes:

- symbols;
- words;
- terminology;
- labels;
- other mixed Hebrew/English items.

Apply the same rule:

> If an English representation exists, use the English representation.

Do not translate or transliterate an English symbol/term into Hebrew merely because the surrounding sentence is Hebrew.

---

# 18. No Hebrew Unless Necessary

This is a hard requirement:

> **Do not use Hebrew when English exists for the specific item.**

This should be tested explicitly.

Examples:

```text
English exists:
Corpos Striatum
Hebrew exists:
קורפוס סטריאטום

Expected:
Corpos Striatum
```

```text
English exists:
Superior cerebellar artery
Hebrew exists:
עורק צרבלרי עליון

Expected:
Superior cerebellar artery
```

---

# 19. Hebrew-Only Cases

Do not overcorrect.

If the source contains only:

```text
מונח מסוים
```

and no English representation exists:

```text

מונח מסוים
```

Do not invent:

```text
Some Term
```

Do not ask the LLM to create one.

The system must remain source-grounded.
