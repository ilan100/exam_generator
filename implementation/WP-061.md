# WP-061 — Language Policy Architecture Alignment

## 1. Objective

WP-060 established that the next architectural direction is a narrow, evidence-driven expansion of deterministic target planning, while preserving production behavior.

Before proceeding, the project must resolve a separate architectural consistency issue:

> **The project contains multiple historical definitions of the language policy, and they are not all expressed at the same scope.**

The authoritative current policy is:

```text
Questions are written in Hebrew.

For every professional/technical/terminological item,
including symbols, acronyms, abbreviations, named entities,
and domain-specific terminology:

    if an English representation exists:
        English MUST be used.

    if no English representation exists:
        Hebrew MAY be used.

This applies to:
    question-stem terminology
    target names
    correct answers
    distractors
    relevant generated terminology

This does NOT require the entire question to be written in English.
```

The existing `LANGUAGE_POLICY_ARCHITECTURE_ALIGNMENT.md` explicitly states that this broader rule supersedes the narrower interpretation introduced by the WP-058 architecture review.

WP-061 must make this policy **authoritative, discoverable, and consistent across the repository's architecture documents and active implementation instructions**.

This is an architecture/documentation-alignment WP.

It is **not** a new language-generation experiment.

---

# 2. Why WP-061 Is Needed

Earlier WPs already contained the broad rule:

```text
If an English representation exists:
    use English.

Use Hebrew only when no English representation exists.
```

However, the WP-058 architecture review subsequently narrowed the interpretation to target/correct-answer terminology. That wording can incorrectly permit Hebrew professional terminology elsewhere in a question.

The current project-owner requirement is broader:

```text
Hebrew is the question language.

English is mandatory for each specific professional,
technical, scientific, or terminological item whenever
an English representation exists.
```

WP-061 must eliminate this ambiguity.

---

# 3. Architectural Principle

The language policy is a **project-wide invariant**.

It is independent of:

```text
category
target
generation strategy
IDENTITY_FIRST / DEFAULT
target-planning mode
retrieval path
question shape
validator path
```

The invariant is:

```text
For every specific professional/technical item:

English representation exists?
    YES → English MUST be used.
    NO  → Hebrew MAY be used.
```

Strategy selection must never override the language policy.

---

# 4. Critical Distinction: Question Language vs Item Language

Do not reinterpret the policy as whole-question English.

The architecture is:

```text
Question prose
    → Hebrew

Professional/technical item inside that prose
    → English if an English representation exists
```

Therefore:

```text
Hebrew question prose
+
English professional terminology
```

is valid.

But:

```text
Hebrew professional terminology
```

is not valid when the same item has an established English representation.

---

# 5. Scope of the Rule

The policy applies to every applicable specific item, including:

```text
professional terminology
technical terminology
medical terminology
anatomical names
scientific names
symbols
acronyms
abbreviations
named entities
domain-specific labels
target names
correct-answer terminology
distractor terminology
terminology inside the question stem
relevant user-visible generated terminology
```

It is not restricted to the correct answer.

It is not restricted to the target.

It is not restricted to identity-first questions.

---

# 6. English Representation

The policy does not mean:

```text
translate every Hebrew term into English
```

The system must use an **existing English representation**.

Do not invent terminology.

Do not create ad-hoc translations.

Do not use external medical terminology services as part of WP-061.

If an English representation cannot be established safely from the project's existing terminology/evidence architecture:

```text
Do not invent one.
Record the limitation.
```
