# 3. General Modeling Principles

Use Pydantic for externally meaningful and validated domain structures.

Prefer small models with clear responsibilities.

Do not create a single universal model.

Models should reject unexpected fields unless there is a documented reason
otherwise.

Use strict validation where Python's implicit coercion could hide invalid
input.

In particular, remember that Python considers `bool` a subtype of `int`.
A value such as `True` must therefore NOT accidentally pass validation for:

- question number;
- answer ID;
- page number;
- requested question count;
- generation attempt count.

Preserve Unicode text.

Do not translate, normalize, rewrite, lowercase, or otherwise alter meaningful
Hebrew or English terminology as part of domain-model validation.

Whitespace-only required text is invalid.

Trimming leading/trailing whitespace for validation/storage is acceptable if
done consistently and documented, but do not otherwise alter text.

# 5. Generation Mode

Define a string-backed enum representing exactly these generation modes:

    STYLE_SIMILAR
    INDEPENDENT

The enum must serialize cleanly to JSON.

Do not add other generation modes.

Semantic meaning:

### STYLE_SIMILAR

A historical exam question may be used as a style/structure reference.

Historical content does NOT become factual evidence.

### INDEPENDENT

The question is generated without using a particular historical question as
its structural template.

Both modes still require factual grounding in student-summary material in later
WPs.

# 6. Exam Request

Define the typed representation of an exam-generation request.

External JSON contract:

    {
      "categories": {
        "גזע המוח": 5,
        "חומר לבן": 4,
        "המוח הקטן": 3
      }
    }

Requirements:

- `categories` is required.
- At least one category is required.
- Category names must be non-empty.
- Whitespace-only category names are invalid.
- Requested counts must be positive integers.
- Boolean values must not be accepted as integers.
- Unknown categories are NOT checked in this WP.
- Do not silently map or normalize category names.
- Do not use `category_mapping.yaml` here.

Canonical category validation will be implemented after historical Excel
ingestion exists.

This model validates structure only.

# 7. Clean Exam Question

Define the authoritative runtime model for a final exam question.

Contract:

    {
      "number": 1,
      "question": "...",
      "answer1": "...",
      "answer2": "...",
      "answer3": "...",
      "answer4": "...",
      "correct_answer": 2,
      "category": "גזע המוח"
    }

Requirements:

### number

- positive integer;
- bool rejected.

### question

- required;
- non-empty;
- whitespace-only rejected.

### answer1 ... answer4

Each must be:

- required;
- non-empty;
- whitespace-only rejected.

There are always exactly four answer fields.

### correct_answer

- integer;
- exactly one of 1, 2, 3, 4;
- bool rejected.

The project will use **1-based answer IDs**.

### category

- required;
- non-empty;
- whitespace-only rejected.

Do NOT include:

- source information;
- grounding evidence;
- validation information;
- historical references;
- generation mode;
- model information;
- confidence;
- audit diagnostics.

The clean question model is deliberately separate from audit/internal models.

# 8. Candidate Question

Define an internal model representing an LLM-generated candidate before final
acceptance.

Use a clean internal representation rather than duplicating the external
`answer1` ... `answer4` shape.

Recommended conceptual structure:

    CandidateQuestion
        question
        answers
        correct_answer
        category
        generation_mode

Requirements:

### question

Non-empty required string.

### answers

- exactly four entries;
- every answer is a non-empty string;
- whitespace-only answers rejected.

Do NOT require all four answers to be textually unique in this WP.

That is a future quality-validation concern.

### correct_answer

Use the same 1-based convention as the external contract:

    1
    2
    3
    4

Bool must be rejected.

### category

Non-empty required string.

### generation_mode

Required `GenerationMode`.

Do NOT include a trusted field such as:

    grounded = true

A generator's own grounding assertion is not authoritative.

Grounding will be established independently.

# 9. Candidate → Clean Question Conversion

Implement a small deterministic conversion from:

    CandidateQuestion

to:

    ExamQuestion

The conversion receives the final question number from the caller.

It must map:

    answers[0] -> answer1
    answers[1] -> answer2
    answers[2] -> answer3
    answers[3] -> answer4

and preserve:

- question text;
- category;
- correct-answer ID.

Requirements:

- question number must be valid;
- no LLM call;
- no grounding decision;
- no factual validation;
- no translation;
- no answer shuffling;
- no rewriting;
- no category mapping.

The caller is responsible for converting only an accepted candidate.

Keep this conversion simple and deterministic.

# 10. Source Type

Define a string-backed enum representing factual source types:

    STUDENT_SUMMARY
    COURSE_BOOK

Do NOT include historical exam questions in this enum.

This distinction is architectural:

    Student summary
        -> factual grounding authority

    Course book
        -> secondary factual reference/check

    Historical exam
        -> style reference only

Historical questions therefore receive their own separate model.

# 13. Grounding Validation Result

Define the typed result returned by the future independent grounding validator.

At minimum:

    grounded
    correct_answer_supported
    other_answers_not_equally_correct
    evidence_chunk_ids
    evidence_text
    reason
    confidence

### grounded

Strict boolean.

### correct_answer_supported

Strict boolean.

### other_answers_not_equally_correct

Strict boolean.

### evidence_chunk_ids

List of evidence chunk IDs.

It may be empty for a failed grounding result.

### evidence_text

Textual explanation/supporting evidence.

Define sensible optional/empty semantics.

Do not require evidence for a failed result if none exists.

### reason

Human-readable validator explanation.

Require a non-empty reason so audit results remain interpretable.

### confidence

Float between:

    0.0
    1.0

inclusive.

Do not make confidence part of the pass/fail decision in this WP.

## Centralized pass semantics

Implement a clearly named derived property or method such as:

    result.passed

A grounding result passes if and only if:

    grounded
    AND correct_answer_supported
    AND other_answers_not_equally_correct

Do not require future callers to reproduce this expression.

Test every combination relevant to the rule.

# 20. Clean Exam Output

Define the top-level clean exam model.

Use this V1 contract:

    {
      "questions": [
        {
          "number": 1,
          "question": "...",
          "answer1": "...",
          "answer2": "...",
          "answer3": "...",
          "answer4": "...",
          "correct_answer": 2,
          "category": "..."
        }
      ]
    }

Use a top-level object containing `questions`, not a bare JSON array.

This is now an explicit V1 architectural decision.

Requirements:

- questions list must contain at least one question;
- question numbers must be unique;
- question numbers must form exactly the contiguous sequence:

      1..N

Examples:

    [1]             valid
    [1,2,3]         valid
    [2,3]           invalid
    [1,3]           invalid
    [1,2,2]         invalid

Do not require questions to be grouped or sorted by category.

Do not include audit information.

Requirements:

- string enums serialize using their string values;
- datetimes serialize using standard ISO-8601-compatible representation;
- Hebrew must survive round-trip serialization unchanged;
- embedded English anatomical terminology must survive unchanged.

Example conceptually:

    "המסילה עוברת דרך ה-Corona radiata"

must not become translated or otherwise rewritten by serialization.
