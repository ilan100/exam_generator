# 2. Objective

Implement the external prompt infrastructure required by the generation and validation pipeline.

The architectural boundary becomes:

```text
external prompt files
        ↓
PromptRepository / loader
        ↓
validated template
        ↓
deterministic rendering
        ↓
LLMMessage sequence
        ↓
LLMProvider                 WP-007
```

WP-008 establishes:

* external prompt files;
* prompt identification;
* deterministic prompt loading;
* explicit template-variable declarations;
* strict template rendering;
* provider-independent conversion to `LLMMessage`;
* prompt metadata/version identity for future auditability;
* initial production prompt templates for:

  * question generation;
  * grounding validation;
  * MCQ validation;
  * category validation;
  * general quality validation;
  * textbook consistency validation;
* tests ensuring prompt/source-role boundaries remain explicit.

WP-008 does NOT:

* call an LLM;
* retrieve evidence;
* select historical references;
* generate questions;
* validate questions;
* implement retry logic;
* orchestrate exams.

---

# 3. Core Architectural Rule

Prompt wording is application policy and must remain outside Python application logic.

Do not embed large production prompt strings in:

* generation code;
* validation code;
* provider code;
* orchestration code.

Python owns:

```text
loading
validation
rendering
message construction
```

External prompt files own:

```text
instructions
task wording
source-role explanations
behavioral constraints
```

Later prompt changes should normally require editing prompt files, not Python application logic.

Use that structure.

```text
prompts/
```

Do not create separate prompts for `STYLE_SIMILAR` and `INDEPENDENT` unless implementation demonstrates that separate files are necessary.

Prefer one generation template with explicit mode-dependent variables.

# 5. Prompt File Format

Use plain UTF-8 text files.

Do not introduce:

* Jinja2;
* Mustache;
* YAML prompt DSLs;
* JSON prompt definitions;
* Markdown parsing;
* LangChain prompt templates;
* another templating dependency.

Prompt files are ordinary text containing explicit placeholders.

Use Python's standard-library formatting infrastructure or another minimal standard-library mechanism.

No new production dependency should be required for WP-008.

---

# 6. Placeholder Syntax

Use a clear placeholder syntax such as:

```text
{category}
{source_evidence}
{historical_reference}
```

Do not support:

* expressions;
* conditionals;
* loops;
* function calls;
* nested templates.

The template system is deliberately simple.

A prompt template is:

```text
static text + named placeholders
```

---

# 7. Strict Rendering

Prompt rendering must be strict.

If a template requires:

```text
{category}
{source_evidence}
```

and the caller provides only:

```text
category
```

rendering must fail.

Likewise, unexpected variables should fail rather than being silently ignored.

Conceptually:

```text
required variables == supplied variables
```

This protects future generation/validation code from prompt drift.

Do not silently substitute missing values with empty strings.

---

# 8. Prompt Identity

Introduce a provider-independent prompt identifier.

Conceptually:

```python
class PromptId(str, Enum):
    QUESTION_GENERATION = ...
    GROUNDING_VALIDATION = ...
    MCQ_VALIDATION = ...
    CATEGORY_VALIDATION = ...
    QUALITY_VALIDATION = ...
    TEXTBOOK_VALIDATION = ...
```

Exact naming may vary.

Do not use arbitrary filesystem paths throughout application code.

Future code should request:

```python
repository.get(PromptId.GROUNDING_VALIDATION)
```

rather than know:

```text
prompts/validation/grounding.txt
```

Filesystem mapping belongs to the prompt infrastructure.

---

# 9. Prompt Template Contract

Introduce a small immutable/read-only representation conceptually equivalent to:

```text
PromptTemplate
    prompt_id
    text
    required_variables
    version
```

Requirements:

### prompt_id

Stable logical identity.

### text

Exact UTF-8 template contents.

### required_variables

Deterministically derived from the actual template placeholders.

Do not maintain a second manually duplicated list if it can be reliably derived from the template itself.

### version

A deterministic identity of the prompt contents suitable for future audit/debugging.

---

# 10. Prompt Version Identity

Future audit records should be able to determine which prompt content was used.

Implement a deterministic content identity.

Preferred:

```text
SHA-256 of the exact prompt-file bytes/content
```

Expose either:

```text
full SHA-256
```

or a clearly documented stable representation.

Do not use:

* modification timestamps;
* random UUIDs;
* process-dependent hashes;
* Git commit lookup;
* filesystem inode metadata.

Changing prompt content must change its version identity.

Unchanged prompt content must reproduce the same identity.

This is prompt identity/audit metadata, not a security mechanism.

# 13. Prompt Loading

Repository construction must:

1. locate each required production prompt;
2. read it explicitly as UTF-8;
3. reject missing required files;
4. reject empty files;
5. reject whitespace-only files;
6. parse/validate placeholders;
7. calculate deterministic version identity;
8. return immutable/read-only prompt representations.

Fail early during repository construction where practical.

Do not wait until an exam is being generated to discover that `grounding.txt` is missing.

---

# 14. Unknown Prompt

Requesting an unsupported/unknown prompt identifier must fail clearly.

Do not silently return another prompt.

Do not use a default/fallback prompt.

---

# 15. Invalid Template Syntax

Malformed placeholder syntax must fail clearly.

Examples include templates that cannot be parsed by the selected formatting mechanism.

Do not allow raw Python formatting exceptions to be the only diagnostic.

Wrap expected template-format errors in focused prompt-domain errors.

---

# 16. Literal Braces

Because neuroanatomy prompts may eventually contain examples or structured-looking content, document and test the selected escaping mechanism for literal braces.

If Python format syntax is used:

```text

```

should represent literal braces.

Do not implement custom escaping if the standard formatter already provides it.

# 17. Rendered Prompt

Rendering should return a plain Unicode string.

Requirements:

* preserve Hebrew;
* preserve English;
* preserve mixed Hebrew/English;
* preserve supplied evidence text;
* do not normalize whitespace globally;
* do not translate;
* do not alter source wording.

The renderer substitutes caller-supplied values into the template and nothing more.

```text
prompts/system/exam_generator.txt
```

# 25. STYLE_SIMILAR Prompt Behavior

When:

```text
generation_mode = STYLE_SIMILAR
```

the generation prompt must instruct the model to use the supplied historical question as a reference for aspects such as:

* style;
* structure;
* difficulty;
* terminology;
* answer-choice style.

But it must explicitly prohibit treating the historical reference as factual evidence.

The generated question's factual content must come from supplied student-summary evidence.

Similarity is allowed.

Exact copying should not be required.

---

# 26. INDEPENDENT Prompt Behavior

When:

```text
generation_mode = INDEPENDENT
```

the generated question should be based on supplied factual evidence without using a historical question as a style anchor.

The prompt infrastructure must support an explicit representation of:

```text
no historical reference
```

without pretending one exists.

A simple sentinel rendering such as:

```text
No historical style reference is supplied for this generation mode.
```

is acceptable.

Do not use a fake historical question.

---

# 27. Generation Factual Authority

The generation prompt must clearly state:

* student-summary evidence is the authoritative factual basis;
* the generated question and correct answer must be supported by supplied student-summary evidence;
* unsupported factual additions are prohibited;
* historical reference is not factual evidence;
* textbook evidence is not part of primary generation grounding in this WP's generation prompt.

Do not tell the generator that the textbook can rescue unsupported student-summary content.

# 29. No Self-Validation

# 30. Grounding Validation Prompt


```text

```

and instruct the validator to determine whether:

1. the question's factual premise is supported;
2. the intended correct answer is supported;
3. the supplied evidence makes that answer the best answer;
4. unsupported factual claims exist.

The authoritative evidence is student-summary evidence.

* do not trust the generator's claimed evidence IDs as proof;
* do not assume the candidate is correct because it was generated by another LLM operation;

This is a core project architecture requirement.

# 41. Prompt Injection / Source Delimiting

Retrieved PDF text and historical questions are untrusted data relative to prompt instructions.

Prompt formatting must clearly delimit inserted source content.

Use deterministic section markers, for example:

```text
--- BEGIN FACTUAL EVIDENCE ---
...
--- END FACTUAL EVIDENCE ---
```

and:

```text
--- BEGIN HISTORICAL STYLE REFERENCE ---
...
--- END HISTORICAL STYLE REFERENCE ---
```

The system/task prompts should make clear that text inside source-data sections is evidence/reference content, not instructions.

Do not implement an elaborate security framework.

But do establish this boundary now.

---

# 42. Evidence Ordering

Evidence formatting must preserve caller-supplied order.

Do not:

* re-rank;
* sort by source filename;
* sort by page;
* deduplicate;
* retrieve additional chunks.

Selection/ranking belongs to retrieval/generation logic.

WP-008 formats what it is given.

---

# 43. Empty Evidence

For prompts that require factual evidence, rendering with no evidence should fail clearly at the formatting/rendering boundary where practical.

Do not produce:

```text

(none)
```

for question generation or grounding validation and then call an LLM later.

Primary factual evidence is mandatory for those operations.

For textbook validation, behavior may differ because future textbook retrieval could legitimately be insufficient.

The template infrastructure itself remains generic; task-specific formatting helpers may enforce these stronger rules.
