# 2. Objective

Implement the first real question-generation path.

WP-009 connects the infrastructure already built:

```text
canonical category
       ↓
student-summary retrieval          WP-006
       ↓
historical style reference         WP-003 (STYLE_SIMILAR only)
       ↓
prompt construction                WP-008
       ↓
structured LLM call                WP-007
       ↓
CandidateQuestion                  WP-002
```

At the end of this WP the system must be able to generate **one structured neuroanatomy candidate question** for a requested canonical category.

This is generation only.

The generated candidate is **not yet considered validated or exam-ready**.

---

# 3. Architectural Boundaries

Preserve these existing rules.

### Factual authority

Student-summary evidence is the factual basis for generation.

Historical questions are **style references only** and must never become factual evidence.

Course-book material is not used for primary generation.

### Generation is not validation

The generator may report which supplied evidence it used, but that claim is not authoritative.

WP-009 must not decide that a generated question is factually grounded.

Independent grounding validation belongs to WP-010.

### Existing infrastructure

Reuse:

* category resolution/retrieval from WP-006;
* `LLMProvider` and `LLMProfile.GENERATION` from WP-007;
* prompt repository/rendering/context/formatting from WP-008;
* existing WP-002 domain models.

Do not create competing versions of these abstractions.

---

# 4. Generation Response Boundary

Before coding, inspect the exact current WP-002 `CandidateQuestion` contract.

Do **not** automatically use `CandidateQuestion` as the direct LLM response model merely because it exists.

Prefer this boundary if it fits the existing domain contracts cleanly:

```text
LLM
 ↓
GenerationResponse / generated-candidate DTO
 ↓
deterministic application validation/conversion
 ↓
CandidateQuestion
```

The LLM should only be responsible for fields it can legitimately produce.

Application-owned provenance should be assigned or verified deterministically by Python where possible.

For example, do not blindly trust an LLM to invent:

* category identity;
* generation mode;
* source IDs;
* historical-reference IDs.

If a small LLM-facing Pydantic model is needed, add it to the appropriate existing domain/model layer and document the decision.

Do not weaken `CandidateQuestion` validation to accommodate LLM output.

---

# 5. Public Generation Interface

Create a focused generation layer with a small application-facing API.

Conceptually:

```python
generate_candidate_question(
    *,
    category: str,
    generation_mode: GenerationMode,
    ...
) -> CandidateQuestion
```

The exact constructor/dependency-injection design is Claude's engineering decision.

Dependencies such as retrieval index, prompt repository, historical-question source, and LLM provider should be injectable/testable rather than hidden global state.

The normal application path should nevertheless be straightforward to construct from existing project configuration.

---

# 6. Generation Flow

For one requested question:

1. require/resolve a canonical category using the established category infrastructure;
2. retrieve student-summary evidence for that category;
3. require usable factual evidence;
4. handle the requested generation mode;
5. build the established WP-008 generation prompt/context;
6. call the LLM through WP-007 using `LLMProfile.GENERATION`;
7. receive validated structured output;
8. deterministically construct a valid `CandidateQuestion`;
9. return it without performing downstream validation.

Do not bypass the existing prompt or LLM abstractions.

---

# 7. Generation Modes

Support exactly the established modes:

```text
STYLE_SIMILAR
INDEPENDENT
```

## STYLE_SIMILAR

Use one historical question from the requested category as a style reference.

The selection must be deterministic for identical inputs/state in WP-009.

Do not introduce random selection yet.

The historical reference:

* influences style;
* is included through WP-008's established style-reference boundary;
* is not factual evidence.

## INDEPENDENT

Do not supply a historical reference.

Do not fabricate one.

Use only retrieved student-summary evidence plus the established generation instructions.

---

# 8. Historical Reference Selection

Reuse WP-003's historical-question data and existing interfaces.

If no suitable historical reference exists for `STYLE_SIMILAR`, fail clearly.

Do not silently switch to `INDEPENDENT`.

Do not implement diversity-aware or retry-aware historical selection yet; WP-013 owns those concerns.

A simple deterministic selection policy is sufficient and must be documented.

---

# 9. Evidence Retrieval

Use WP-006's student-summary retrieval index.

Retrieval should be driven by the canonical category using the established category-aware retrieval path.

Use the configured/default retrieval `top_k` rather than introducing another generation-specific retrieval constant without need.

The selected chunks must remain unchanged and retain their provenance.

If no usable student-summary evidence is returned, generation must fail before the LLM call.

Do not retrieve course-book evidence in WP-009.

---

# 10. Provenance

A returned `CandidateQuestion` must contain correct generation provenance according to its existing contract.

Application-owned provenance must correspond to the actual generation operation.

In particular:

* category must be the canonical requested category;
* generation mode must match the requested mode;
* evidence IDs must refer only to student-summary chunks actually supplied to the generation prompt;
* historical reference ID must correspond to the actual supplied historical reference when `STYLE_SIMILAR`;
* `INDEPENDENT` must not claim a historical reference.

If the LLM returns provenance claims, validate them against the actual supplied context before constructing the candidate.

Never accept invented source IDs.

---

# 11. LLM Call

Use:

```text
LLMProfile.GENERATION
```

and the WP-008 production system + generation prompts.

There should be one semantic LLM call per invocation of the WP-009 generation operation.

Do not add semantic retry loops.

A failed provider call or invalid structured response should surface through a clear generation/LLM error path.

WP-013 will own generation retry policy.

---

# 12. Errors

Introduce only the focused generation-domain errors needed for this layer.

Expected failures should clearly distinguish at least:

* invalid/unresolvable generation context;
* missing factual evidence;
* missing historical style reference when required;
* invalid/inconsistent generated provenance or output.

Reuse existing category, retrieval, prompt, LLM, and Pydantic errors where appropriate rather than wrapping everything unnecessarily.

Preserve useful exception causes.

---

# 13. Tests

Add focused unit tests covering the generation behavior.

At minimum demonstrate:

* successful `INDEPENDENT` generation;
* successful `STYLE_SIMILAR` generation;
* canonical category/retrieval integration;
* factual evidence passed to the prompt comes from student-summary retrieval;
* `STYLE_SIMILAR` supplies a real historical reference;
* `INDEPENDENT` supplies none;
* historical reference is never treated as factual evidence;
* LLM is called through `LLMProfile.GENERATION`;
* structured LLM output becomes a valid `CandidateQuestion`;
* canonical category and generation mode cannot be falsified by LLM output;
* invented/unknown evidence IDs are rejected;
* wrong historical-reference provenance is rejected;
* no factual evidence fails before an LLM call;
* missing style reference fails clearly;
* no course-book retrieval occurs;
* no grounding/MCQ/category/textbook validation occurs;
* no retry loop occurs;
* Hebrew and mixed anatomical terminology survive the path unchanged.

All normal unit tests must mock the LLM and make zero network calls.

Run the full regression suite.

---

# 14. Live Generation Smoke Test

After unit/regression tests pass, perform **one small live generation smoke test** if `OPENAI_API_KEY` is available.

Use:

* the configured OpenAI provider/model;
* one real canonical category;
* real student-summary retrieval;
* one generation mode;
* the real WP-008 production prompts.

Generate exactly one candidate.

Verify structurally:

* a valid `CandidateQuestion` is returned;
* Hebrew question text exists;
* exactly four answers exist;
* correct-answer position is valid;
* category/mode provenance is correct;
* evidence IDs correspond to supplied chunks;
* historical-reference provenance is correct for the chosen mode.

Do **not** claim the question is factually correct merely because generation succeeded.

That is WP-010's job.

Report the generated question and answers in the completion report so the architect/user can inspect the first real system output.

Do not make repeated live calls trying to improve the question.

If the live call exposes a genuine API/model compatibility problem, stop and report it rather than redesigning the architecture ad hoc.

If no API key is available, report the live smoke test as skipped.

# 15. Scope Exclusions

Do not implement:

* grounding validation;
* MCQ validation;
* semantic category validation;
* quality validation;
* textbook checking;
* generation retries;
* diversity management;
* duplicate-question detection;
* exam orchestration;
* multiple-question generation;
* exam/audit output;
* CLI behavior.

Do not modify production prompts merely because a generated question could be better unless the live smoke test exposes a clear correctness/contract defect.

Prompt quality tuning should be deliberate, not ad hoc during generation implementation.

# 17. Acceptance Criteria

WP-009 is complete when:

1. One candidate question can be generated for a canonical category.
2. Both established generation modes work.
3. Student-summary retrieval is the only factual generation source.
4. Historical questions remain style-only.
5. `STYLE_SIMILAR` uses a real deterministic historical reference.
6. `INDEPENDENT` uses no historical reference.
7. WP-008 production prompts are used.
8. WP-007 provider abstraction is used with `LLMProfile.GENERATION`.
9. Structured output is validated before becoming a `CandidateQuestion`.
10. Application-owned provenance cannot be fabricated by the LLM.
11. Evidence IDs correspond only to chunks actually supplied.
12. No course-book evidence is used.
13. No downstream validation is performed.
14. No semantic retry loop exists.
15. Unit tests make zero network calls.
16. Full regression suite passes.
17. One live generation is performed if an API key is available, without treating generation success as grounding proof.
18. Documentation/status is updated.
19. WP-010 has not been started.
