# WP-016 — CLI and Application Entry Point

## 1. Context

Before implementation, read completely:

* `docs/MASTER_PROJECT_BRIEF.md`
* `docs/ARCHITECTURE.md`
* `docs/PROJECT_STATUS.md`
* `implementation/WP-016.md`

WP-001 through WP-015 are complete and approved.

Inspect the existing domain/config/orchestration/output interfaces before implementation. Consult previous WP specifications only when necessary.

Implement only WP-016.

Do not start WP-017.

---

# 2. Objective

Provide a practical command-line interface for running the completed exam-generation pipeline.

The CLI should expose the existing architecture:

```text
CLI
 ↓
load configuration
 ↓
construct ExamRequest
 ↓
ExamOrchestrator
 ↓
ExamGenerationResult
 ↓
WP-015 output layer
 ↓
exam JSON + audit JSON
```

The CLI is an adapter around existing application functionality.

It must not become a second orchestration layer.

---

# 3. Main Command

Provide one primary command for generating an exam.

A reasonable interface is conceptually:

```bash
exam-generator generate \
    --request request.json \
    --exam-output exam.json \
    --audit-output audit.json
```

Exact naming may follow the project's existing packaging conventions.

The request file should map directly onto the existing `ExamRequest` contract.

Do not create a separate CLI-specific exam-request schema unless technically necessary.

---

# 4. Request Input

Accept the exam request as UTF-8 JSON.

Example shape should follow the **actual current `ExamRequest` model**, not assumptions in this WP.

Conceptually:

```json
{
  "categories": {
    "category_a": 2,
    "category_b": 1
  }
}
```

or whatever structure WP-002 actually defines.

Use Pydantic/domain validation already provided by the project.

Malformed JSON and invalid requests must produce clear user-facing errors.

Do not manually duplicate all `ExamRequest` validation inside the CLI.

---

# 5. Output

On successful generation, produce two separate files:

```text
exam.json
audit.json
```

Use WP-015's existing output/serialization functionality.

Do not manually rebuild either JSON structure in the CLI.

The exam output remains clean/student-facing.

The audit output remains internal.

Both must be UTF-8 and preserve readable Hebrew.

---

# 6. Default Output Paths

Support explicit caller-provided output paths.

It is also reasonable to provide simple deterministic defaults, for example:

```text
exam.json
exam_audit.json
```

if output paths are omitted.

Do not generate timestamp-, UUID-, or random-based filenames in WP-016.

Do not create complex output-directory management.

---

# 7. Overwrite Policy

Do not silently overwrite existing output files.

If an output target already exists, fail clearly unless the user explicitly supplies a force/overwrite option.

A simple option such as:

```bash
--force
```

is appropriate.

When `--force` is absent:

```text
existing output file
        ↓
clear error
        ↓
no overwrite
```

Avoid ending with one new file and one stale file where reasonably possible.

---

# 8. Configuration

Use the existing configuration infrastructure.

Do not duplicate:

* application configuration;
* LLM configuration;
* category mappings;
* retrieval configuration;
* generation attempt limits;
* duplicate-replacement limits

as CLI-specific settings.

The CLI should construct the application using the established default configuration path.

---

# 9. API Key

The OpenAI API key must continue to come from:

```text
OPENAI_API_KEY
```

Do not accept the key as a normal command-line argument such as:

```bash
--api-key ...
```

because command-line arguments may be visible through shell history or process inspection.

If `OPENAI_API_KEY` is missing, fail clearly before attempting exam generation where practical.

Never print the key.

Never write it into:

* logs;
* audit output;
* exam output;
* exception messages.

---

# 10. Application Construction

Reuse existing default constructors where appropriate.

The CLI should ultimately invoke the established orchestration path, conceptually:

```python
orchestrator = ExamOrchestrator.from_default_configuration()

result = orchestrator.generate_exam(request)
```

then:

```python
bundle = build_exam_output_bundle(result)
```

Use the actual current interfaces.

Do not manually construct:

* corpora;
* retrieval indexes;
* generator;
* five validators;
* producer

inside CLI code if existing composition/default-construction infrastructure already provides that.

If one small composition helper is genuinely missing, add the smallest appropriate application factory rather than placing substantial dependency wiring in the CLI command.

---

# 11. Progress Reporting

Exam generation can involve many LLM calls, so the CLI must not appear frozen.

Provide simple human-readable progress.

At minimum communicate meaningful stages such as:

```text
Loading request...
Initializing exam generator...
Generating exam...
Writing exam output...
Writing audit output...
Done.
```

If existing architecture makes per-question progress available without invasive changes, showing:

```text
Question 1/10
Question 2/10
...
```

is useful.

However, do not refactor WP-014 merely to implement a sophisticated progress system.

No progress bar library is required.

---

# 12. Successful Completion

Successful execution should clearly report:

* exam generation succeeded;
* number of questions generated;
* exam output path;
* audit output path.

Exit with status:

```text
0
```

Do not dump the entire audit to the terminal by default.

A concise success message is sufficient.

---

# 13. Error Handling

Translate expected application failures into concise CLI messages.

Important cases include:

### Input errors

* request file missing;
* invalid JSON;
* invalid `ExamRequest`;
* unknown category.

### Configuration errors

* missing/invalid configuration;
* missing `OPENAI_API_KEY`.

### Generation failures

* `QuestionAttemptsExhaustedError`;
* exam-level `QuestionProductionFailedError`;
* duplicate replacement exhaustion.

### Provider/operational failures

* authentication failure;
* rate limit;
* provider connection/API failure;
* invalid structured response;
* prompt/retrieval failure.

### Output failures

* existing output file without `--force`;
* unwritable output location;
* serialization/write failure.

Use project-specific exceptions where they already exist.

Do not expose large Python tracebacks for normal expected CLI failures.

Unexpected programming errors may still be diagnosable during development; do not implement a giant catch-all that hides defects.

---

# 14. Exit Codes

Keep exit-code policy simple and documented.

At minimum:

```text
0 = success
non-zero = failure
```

A small stable distinction is useful, for example:

```text
1 = application/generation failure
2 = request/usage/configuration error
```

but do not create a large taxonomy of exit codes.

Use whatever is most natural for the chosen CLI framework.

---

# 15. CLI Framework

First inspect the existing dependencies/project conventions.

If no CLI framework is already present, prefer the Python standard library:

```text
argparse
```

unless there is a strong project reason for Typer/Click.

Avoid adding a dependency solely for a very small CLI.

The CLI should remain easy to run and test.

---

# 16. Package Entry Point

Provide an installed console entry point through `pyproject.toml`.

Conceptually:

```toml
[project.scripts]
exam-generator = "exam_generator.cli:main"
```

Use the actual module layout chosen during implementation.

The intended user experience should be:

```bash
exam-generator generate ...
```

after the project is installed.

Also preserve a straightforward development invocation if useful:

```bash
python -m exam_generator.cli generate ...
```

---

# 17. Optional Validation-Only Command

Do **not** add extra CLI commands merely because they might eventually be useful.

WP-016 only requires the generation workflow.

Commands such as:

```text
validate
inspect-corpus
search
show-config
rebuild-index
```

are outside scope unless already required by the master brief.

Keep the public CLI small.

---

# 18. Output Atomicity

Avoid leaving misleading partial output when generation or serialization fails.

The CLI must not write a completed-looking `exam.json` before exam generation itself succeeds.

Preferred sequence:

```text
generate complete exam
        ↓
build complete output bundle
        ↓
serialize/validate both outputs
        ↓
write outputs
```

Where practical, use temporary files + atomic replacement so failure while writing the second output does not leave an inconsistent exam/audit pair.

Keep the implementation simple and local.

---

# 19. No New Domain Policy

WP-016 must not change:

* retrieval strategy;
* TF-IDF configuration;
* generation prompts;
* generation modes;
* validator prompts;
* acceptance policy;
* attempt limits;
* textbook semantics;
* duplicate policy;
* exam planning;
* audit semantics.

If the CLI reveals a domain-quality issue, document it.

Do not tune the system from inside this WP merely to make the CLI demo succeed.

# 20. Tests

Add focused CLI tests covering at minimum:

### Input

* valid request JSON is parsed into the established `ExamRequest`;
* malformed JSON fails clearly;
* missing request file fails clearly;
* invalid request fails clearly;
* Unicode/Hebrew input survives parsing.

### Execution

* CLI invokes the established exam orchestration path;
* successful generation invokes WP-015 output construction;
* successful generation writes separate exam/audit outputs;
* clean output remains clean;
* audit output remains separate.

### Files

* explicit output paths work;
* default output paths work if implemented;
* existing output without `--force` fails;
* `--force` allows replacement;
* failure before successful generation writes no completed output;
* output is valid UTF-8 JSON.

### Errors

* missing API key produces a clear error in real/default construction path;
* expected generation exhaustion produces non-zero exit;
* provider failure produces non-zero exit;
* expected failures do not emit an unnecessary traceback.

### Security

* API key is never printed;
* API key never appears in generated files;
* CLI does not accept an `--api-key` argument.

Mock the orchestration/application boundary for normal CLI unit tests.

No network/API key should be required by the unit suite.

Run the full regression suite.

# 21. CLI Smoke Test

If `OPENAI_API_KEY` is available, perform one real end-to-end CLI smoke test.

Use a small valid request, preferably:

```text

```

to limit cost.

Run the actual installed/development CLI command.

Verify:

```text
request.json
      ↓
CLI
      ↓

      ↓

```

Check:

* exit code 0 if generation succeeds;
* both files exist;
* both contain valid JSON;
* Hebrew is readable;
* clean exam contains no audit internals;
* audit corresponds to the generated question.

If bounded candidate production exhausts, report the CLI failure honestly rather than repeatedly rerunning until successful.

One real invocation is enough.
