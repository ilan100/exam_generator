# WP-036 — Deterministic Concept Inventory Pilot

## Context

Read completely:

- docs/MASTER_PROJECT_BRIEF.md
- docs/ARCHITECTURE.md
- docs/PROJECT_STATUS.md
- implementation/WP-035_ARCHITECTURE_INVESTIGATION.md
- implementation/WP-035_ARCHITECTURE_REVIEW.md

WP-035 concluded that deterministic concept ownership is technically feasible for a subset of categories whose evidence exhibits strong structural patterns.

WP-036 implements a limited pilot.

This is **not** a system-wide rollout.

The purpose is to determine whether deterministic concept inventories improve diversity without reducing generation reliability.

---

# 1. Objective

Implement deterministic concept extraction for a small number of categories.

Use the extracted inventory only as a planning constraint.

Everything else in the generation pipeline remains unchanged.

---

# 2. Scope

Limit implementation to **three categories**.

Choose categories supported by WP-035's investigation.

Suggested candidates:

- אספקת דם
- מסילות עצביות
- one additional category with similarly structured evidence

Do not attempt to support all categories.

---

# 3. Concept Inventory

Implement a new internal deterministic component.

Suggested name:

ConceptInventoryExtractor

Responsibilities:

- receive retrieved evidence
- extract candidate concepts
- produce deterministic concept inventory

No LLM calls.

No embeddings.

No semantic search.

Extraction must follow WP-035's recommended hybrid strategy:

- structure-first
- marker-based
- honest fallback

Never guess.

---

# 4. Inventory Model

Introduce an internal immutable model.

Suggested fields:

- concept
- evidence references
- confidence/source type
- extraction reason

The exact design is your decision.

This model is internal.

Do not expose it through the public API.

---

# 5. Planner Integration

Modify planning only for the pilot categories.

Planning should:

- build inventory
- remove concepts already tested
- choose only from remaining concepts

Outside the pilot categories:

Behavior must remain unchanged.

---

# 6. Existing Questions

Reuse WP-034 coverage.

Determine tested concepts deterministically.

Use exact matching only.

Do not implement synonym handling.

Do not implement semantic matching.

Those belong to future work.

---

# 7. Generation

Question generation remains unchanged.

The LLM receives:

- selected concept
- relationship
- competitors
- evidence

The LLM no longer decides which concept to test for pilot categories.

---

# 8. Validators

No validator changes.

No retry changes.

No retrieval changes.

No prompt redesign.

---

# 9. Tests

Add tests covering:

- inventory extraction
- malformed evidence
- empty inventory
- inventory filtering
- coverage filtering
- planner integration
- fallback behavior
- unchanged non-pilot behavior

Regression suite must pass.

---

---

# 11. Acceptance Run

Generate four sequential questions for each pilot category.

Do not rerun.

Do not manually adjust inventories.

If the inventory becomes exhausted, report it honestly.

Do not invent concepts.

---

# 12. Success Criteria

Primary success criterion:

Question diversity improves because concept selection changes.

Secondary success criterion:

Acceptance rate does not materially decrease.

If diversity improves while acceptance significantly decreases, report that trade-off honestly.

---

# 13. Scope Exclusions

Do NOT:

- support all categories
- add synonym resolution
- redesign prompts
- redesign validators
- redesign retrieval
- redesign competitors
- redesign relationships
- redesign request contracts

Keep the implementation intentionally small.

---

# 14. Architectural Evaluation

Answer explicitly:

- Was deterministic inventory extraction reliable?
- Did concept-constrained planning improve diversity?
- Did reliability regress?
- Which implementation difficulties appeared?
- Should this approach expand beyond the pilot?

Support conclusions with evidence.
