# WP-044 Completion Report — Structural Generation Constraints for Evidence Shape and Target Role

## 1. Objective

WP-043 built two individually-correct, thoroughly-tested deterministic mechanisms (evidence sufficiency + broad fallback; source-role detection), but its own live pilot's acceptance regressed further (5/12, down from WP-041's 9/12). WP-043's own architecture review reframed the problem precisely: both mechanisms correctly recover genuine evidence/relationship information, but "surfacing genuine evidence/relationship information is not, by itself, sufficient to make generation construct a compliant question." WP-044's objective is to determine whether the existing generation blueprint architecture can represent these two specific relationships (evidence shape; target semantic role) **structurally** rather than as increasingly elaborate prompt prose, and to verify - via one fresh live pilot - whether doing so actually changes generation's behavior.

## 2. WP-043 Findings (Recap, OBSERVED from WP-043's own completion report and architecture review)

- `Corpos Striatum`'s recovered evidence (WP-043's own anchoring fix) is genuine but is an **enumeration-introduction sentence** ("basal nuclei contain several sub-structures") - a shape every sibling in the same list would equally anchor to, never distinguishing this one member. Combined with WP-040's mandatory single-entity answer requirement, this actively encourages a generic, ambiguous "which is a member of X" question - the exact shape the pre-existing "testing enumeration targets" prompt guidance already warns against, but does not reliably prevent.
- `Basillar artery`'s source-role detector (`detect_source_evidence_role()`) correctly identifies the role, but the resulting free-text prompt note ("this target is a source, not a downstream entity") was found, via WP-043's own supplementary diagnostic capture, not to reliably change generation's actual question-construction behavior - it continued predominantly asking "which artery supplies X," a question whose evidence-supported answer is the *other*, downstream entity.
- The architecture review's explicit recommendation: retain both primitives, but move the fix to the generation-constraint boundary - encode a **concrete relationship**, not merely a role label, and prefer a structural (deterministic, Python-owned) constraint over more prompt prose.

## 3. Existing Blueprint Analysis (Section 5/6 Investigation, Before Any Change)

Inspected `planning/`, `models/`, `prompts/`, `generation/`, `validation/` before writing any code. The existing architecture already has:

- `QuestionTarget` (`models/target.py`) - WHAT to test, plus WP-040/041/043's `named_entity_target`/`is_source_role` boolean signals.
- `QuestionRelationship` (`models/relationship.py`) + `extract_relationship()` (`generation/relationship.py`) - a deterministic, keyword-classified `relationship_type` (e.g. `SUPPLIES`, `CONTAINS`), derived purely from `target.factual_focus`, already rendered into the generation prompt as "Tested relationship type."
- `QuestionBlueprint`/`GeneratedQuestionResponse.blueprint` (`models/question.py`) - the LLM's own structured internal reasoning (`tested_relationship: NonBlankStr`, `correct_answer_role: NonBlankStr`, plus three `DistractorDesign`s), constructed inside the same generation call, discarded after use, **never independently validated beyond Pydantic schema presence** - `_validate_generated_provenance()` (`generation/generator.py`) checks `evidence_refs`/`historical_reference_id` claims, but nothing about the blueprint's own content.

**Architectural answer to WP-044's own question (section 6)**: yes, the existing blueprint can represent the required relationship structurally, without a new abstraction - by (a) extending `QuestionTarget` with two small, narrowly-scoped fields (the same precedent as `named_entity_target`/`is_source_role`), and (b) adding one new deterministic **pre-validator** check (in the same place, and of the same kind, as the existing provenance check) that inspects the *final candidate's own answer text* against a deterministically-known fact - never the LLM's own free-text blueprint reasoning, which is too unconstrained to match safely against. This was chosen over inventing a new `GenerationPlan`/`tested_relationship`-as-a-model abstraction (WP-044 section 19: "do not blindly add all these fields... only introduce fields that are genuinely necessary").

## 4. Architectural Decision

- **Part A (enumeration-shaped evidence)**: a **skip**, not a generation-time constraint. Investigation of the real `Corpos Striatum` corpus text (`STUDENT_SUMMARY:student_summary_2.pdf:0036:0001`) found that the genuinely distinguishing content about `Corpos Striatum` specifically (a division-into-sub-structures explanation) sits several list items further down the same passage, past multiple sibling candidate-concept lines `anchor_concept_evidence()` already, correctly, refuses to cross (WP-037's own "avoid unnecessarily including neighboring facts" rule). Reaching that content would require either relaxing the sibling-line stop rule (rejected - would reintroduce the WP-036 "salient neighbor" problem this whole line of work exists to prevent) or a new, separate evidence-retrieval mechanism (out of scope, and explicitly the kind of complexity WP-044 section 9 forbids: "do not build a generic NLP classifier"). Given the explicit "prefer missing over wrong" principle (section 11), skipping the concept is the correct, narrow, deterministic answer for the one demonstrated real shape.
- **Part B (source-role evidence)**: a **concrete, named relationship**, not merely a role label - `extract_source_relationship_entity()` deterministically identifies the specific downstream entity, reusing the existing `is_source_role` boolean's own precedent rather than inventing a new relationship model. This is backed by a **deterministic post-generation consistency check** (not a new validator, not an LLM judgment) as a structural safety net.

## 5. Enumeration Constraint Implementation

- **`is_enumeration_evidence_insufficient(*, factual_focus, concept)`** (new, `planning/concept_anchor.py`): splits the already-built `factual_focus` back into its backward/forward portions around the concept's own anchored line (`_split_anchored_focus()`, a purely structural line-index lookup, no new evidence access). Returns `True` only when an enumeration-introduction cue phrase (`_ENUMERATION_INTRO_CUE_PHRASES`: `"מספר תתי"`, `"תתי מבנים"`, `"כוללים"`, `"כוללת"`, `"כולל "`, `"מורכב מ"`, `"מורכבת מ"`, `"several"`, `"the following"`, `"consists of"`, `"includes"`) appears in the backward portion **and** the forward portion carries fewer than 2 alphabetic characters (`_MIN_ENUMERATION_DISTINGUISHING_ALPHA_CHARS`, reusing `concept_inventory._MIN_ALPHA_CHARS`'s own precedent for "not layout noise"). This is the exact real corpus shape: shared list-intro sentence, then a bare bullet marker, nothing member-specific.
- **`detect_enumeration_member_shape(*, factual_focus, concept)`** (new, same module): the same cue-phrase check, without the forward-content gate - used only for a concept that already passed the insufficiency check (i.e. genuinely has distinguishing content), to mark `QuestionTarget.is_enumeration_member=True`.
- **`_plan_targets_from_concept_inventory()`** (`planning/planner.py`) now calls `is_enumeration_evidence_insufficient()` immediately after the existing WP-043 sufficiency/broad-fallback check, and `continue`s (skips this concept, tries the next remaining one) if it fires - the identical control-flow shape as WP-043's own insufficiency skip, one `if` block added.
- **`QuestionTarget.is_enumeration_member`** (new field, default `False`) and **`format_target_enumeration_requirement()`** (new, `prompts/formatting.py`) surface this into a new "Enumeration-member requirement" prompt section - a target-specific reinforcement of the pre-existing general "testing enumeration or classification targets" guidance, mirroring WP-043's own `is_source_role`/`format_target_evidence_role()` precedent exactly.
- **No enumeration detection was performed by inspecting the LLM's own output** - purely a pre-generation, deterministic, Python-side decision over already-anchored evidence text.

## 6. Source-Role Constraint Implementation

- **`extract_source_relationship_entity(chunk_text, concept)`** (new, `planning/target_role.py`): when `detect_source_evidence_role()` is true, deterministically identifies the *other* entity by scanning backward from the target's own raw line for the nearest `_is_candidate_concept_line()` match (the same structural "standalone capitalized ASCII line" signal `extract_concept_inventory()` itself uses to recognize a named entity), skipping the intervening cue/bullet-marker lines, within a small fixed bound (`_SOURCE_RELATIONSHIP_MAX_BACKWARD_SCAN_LINES = 6`). Verified directly against the real corpus chunk (`STUDENT_SUMMARY:student_summary_2.pdf:0128:0001`): returns exactly `"Superior cerebellar artery"` for `"Basillar artery"` - the exact pairing this pilot's live target actually used. A second, independent check against the same chunk's third sibling entry found a real, disclosed limitation (see section 17) rather than a second clean confirmation.
- **`QuestionTarget.source_relationship_entity`** (new field, `str | None`, only ever non-`None` when `is_source_role=True` and extraction succeeded) is set in `_plan_targets_from_concept_inventory()` alongside `is_source_role`.
- **`format_target_evidence_role()`** (extended, `prompts/formatting.py`) now names the downstream entity explicitly when known (`"...describes TARGET CONCEPT (Basillar artery) as the source/origin of a separately-named entity: Superior cerebellar artery..."`), falling back to WP-043's original generic prose (`"...another, separately-named entity..."`) when `is_source_role=True` but no entity could be identified - the same fail-honest-sentinel convention every prior WP-040/041/043 formatting function already established.
- **`_validate_target_role_consistency(response, *, target)`** (new, `generation/generator.py`): a deterministic pre-validator check, called immediately after the existing `_validate_generated_provenance()` inside `generate_candidate_question()`. When `target.is_source_role` and `target.source_relationship_entity` is known, rejects (raises `InvalidGeneratedOutputError`, the identical exception category/attempt-consumption behavior as the existing provenance check) any candidate whose own correct-answer text contains the downstream entity's (normalized) text. Deterministic text comparison only (a small, local, byte-identical-in-behavior copy of `concept_inventory.normalize_concept_text()`, not imported directly - `exam_generator.planning` already imports from `exam_generator.generation`, so the reverse import would be circular, the same reasoning `prompts.formatting._is_english_representable()`'s own docstring already documents). Never inspects the LLM's own free-text `blueprint.tested_relationship`/`correct_answer_role` reasoning - too unconstrained to match safely; only the final, structural, already-untrusted-until-verified `answers`/`correct_answer` fields.

## 7. Target-Identity Interaction (Section 18)

Documented here per section 18's explicit instruction, not expanded further.

## 17. Failures and Limitations

**OBSERVED**: `Globus Pallidus` (`גרעיני הבסיס`, rounds 3-4, both `QuestionAttemptsExhaustedError` after 3 attempts each) and `Corticospinal Tract` (`מסילות עצביות`, rounds 3-4, identical failure shape) were never accepted. Every one of the 12 individual attempt-level rejections across these two targets cited grounding's `other_answers_not_equally_correct=false` explicitly - e.g. `"...multiple answer choices (1, 3, and 4) are supported as correct based on the evidence provided..."`, `"...all four answer choices are supported as they are all recognized components of the Basal Nuclei..."` - a generic, overly-broad question (e.g. "which of the following is part of the basal nuclei," "which motor tract is responsible for innervating skeletal muscles") to which multiple real, evidence-supported entities are equally correct answers. Both targets' own `evidence_shape` was recorded as `ORDINARY` (Part A's `is_enumeration_member` did not fire) for every attempt.

**INFERENCE**: this is structurally the same underlying failure category Part A was built to prevent (a classification/membership question with more than one equally-correct answer), but occurring for two targets whose own narrow anchored evidence does not happen to contain an enumeration-introduction cue phrase within the bounded backward-anchor window Part A inspects - direct offline confirmation: `Globus Pallidus`'s recorded `factual_focus` this run was `"utamen\nP\no\nGlobus Pallidus\n"` (a bullet-marker fragment from an adjacent sibling, not an enumeration-intro sentence at all), and `Corticospinal Tract`'s own evidence describes a *classification* ("motor tracts starting from the cortex") without the specific lexical cue phrases this WP's narrow detector looks for. This is not a defect in Part A's own implementation - it behaves exactly as designed, tested, and verified against the one demonstrated real corpus shape it targets - but it is direct, live evidence that the underlying "generic classification/membership ambiguity" problem is broader than that one narrow, deterministic signal can catch.

**HYPOTHESIS, not confirmed**: a broader cue-phrase vocabulary, or a structural signal based on "how many sibling candidate-concept lines share the same immediate list context" rather than a specific introductory phrase, might catch these two additional cases - but this was not attempted in WP-044, per section 9's explicit "do not overgeneralize enumeration detection... if a safe deterministic signal cannot be established, record that limitation instead of introducing a complex mechanism." This limitation is recorded, not silently patched.

**Also disclosed**: `Globus Pallidus` round 4 attempt 2 additionally showed a *different*-shaped ambiguity (`Globus Pallidus` vs. `Globus Pallidus Internus`, a parent/child hierarchy confusion, not an enumeration/classification one) - noted for completeness, not further investigated, since it is a single occurrence and a different failure shape from the WP-044 scope.

**A further, genuine limitation found during this WP's own verification (not encountered by the live pilot, but real and disclosed rather than hidden)**: `extract_source_relationship_entity()` scans **raw** `chunk_text` lines directly, never the WP-037/039-repaired inventory - so if the downstream entity's own raw source line happens to be leading/trailing-truncated (the same PDF bidi-extraction phenomenon WP-037/039 already repair for concept extraction), the extracted downstream-entity name can itself be truncated. Direct verification against the same real corpus chunk's third sibling entry (`Anterior Inferior Cerebellar Artery (AICA)`, whose "מקור:" value is also `"Basillar Artery"`) found exactly this: the function returns `"nterior Inferior Cerebellar Artery (AICA)"` (missing the leading "A" - the raw line itself is truncated one line before its own repair-eligible orphan letter). This did not affect this pilot's own live result (the `Superior cerebellar artery` pairing the pilot actually exercised is not truncated in the raw text), but it is a real, demonstrated limitation of the current implementation, not merely a hypothetical one - `extract_source_relationship_entity()` would benefit from reusing `refine_concept_inventory()`'s already-repaired concept text rather than re-scanning raw lines, a natural, narrow follow-up for whichever future WP next touches this function. Not fixed here, since it was discovered during this WP's own post-implementation verification, after the pilot had already run, and does not affect any result reported above.

## 18. Architectural Conclusion

Both structural mechanisms (Part A's enumeration-shape skip; Part B's concrete source-role naming plus deterministic consistency check) are individually correct, safely scoped, and - unlike WP-043's own mechanisms - **directly demonstrated live to change generation's actual behavior for the two specific targets they were built for**: `Corpos Striatum` was never selected (Part A working exactly as intended, by never letting a known-ambiguous target reach generation at all), and `Basillar artery` was reliably framed correctly and accepted (Part B working exactly as intended, by giving generation a concrete fact to construct the question around instead of only a role label). This is a materially different, more positive outcome than WP-043's own finding that surfacing correct information was "not sufficient, by itself" - here, the more *structural*, more *specific* form of that same information demonstrably was sufficient, for these two targets.

At the same time, the pilot's own honest, unfiltered results show the underlying architectural principle from WP-043's review remains true in general: a narrow, deterministic signal only ever solves the specific, demonstrated shape it targets, and the broader "classification ambiguity" problem family evidently has more members than the one WP-043/WP-044 diagnosed and fixed.
