# WP-025 — Evidence-Grounded Question Target Planning and Within-Category Diversity

## Context

Read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-025.md`

WP-001 through WP-024 are complete.

WP-024 achieved the first successful real acceptance run:

    20 canonical categories
    × 2 questions/category
    = 40 planned

    40 accepted
    0 failed
    COMPLETE

However, human review of the resulting exam revealed a significant
exam-level quality problem:

questions within the same category are often too similar.

Examples observed in the WP-024 exam include pairs such as:

- 1–2
- 3–4
- 13–14
- 17–18
- 19–20
- 21–22

Some pairs test essentially the same fact using different wording or by
reversing question and answer.

Additional category pairs also showed substantial conceptual overlap.

Individually these questions may pass grounding, MCQ, category, quality, and
textbook validation.

The problem is therefore not primarily candidate validity.

It is exam construction.

---

# Objective

Introduce evidence-grounded question-target planning so multiple questions
requested from the same category are designed to test distinct concepts or
subtopics BEFORE question generation begins.

Change the conceptual flow from:

    category
        ↓
    generate question
        ↓
    validate

    category
        ↓
    independently generate another question
        ↓
    validate

to:

    category
        ↓
    retrieve factual evidence
        ↓
    plan N distinct evidence-supported question targets
        ↓
        ├── target 1 → generate → existing validators
        ├── target 2 → generate → existing validators
        └── ...
    
Diversity should be achieved primarily BY CONSTRUCTION.

Do not implement a design that repeatedly generates arbitrary questions and
uses the existing three-attempt budget primarily to reject duplicates.

---

# 1. Question Target

Introduce a small typed model representing the intended factual focus of one
question.

Use naming consistent with the project, conceptually similar to:

    QuestionTarget

It should contain only information necessary to guide generation.

For example:

    target_id
    category
    topic/subtopic
    factual_focus
    supporting_evidence_refs

Exact fields should follow the existing model style.

The target is NOT:

- a generated question;
- a validator verdict;
- an accepted exam question.

It is a generation plan.

---

# 2. Evidence-Grounded Planning

Planning must be grounded in student-summary evidence.

For each category:

    retrieve relevant student-summary evidence
        ↓
    identify N distinct question targets
        ↓
    verify every target refers only to supplied evidence

The planner must not invent unsupported subtopics merely to create diversity.

Student-summary evidence remains the primary factual authority.

Course-book evidence remains secondary and should not become the factual
source for target planning.

---

# 3. Planner

Introduce a focused component, conceptually:

    QuestionTargetPlanner

with an interface similar to:

    plan_targets(
        *,
        category,
        count
    ) -> list[QuestionTarget]

Use explicit dependency injection consistent with the rest of the project.

The planner may use:

- student-summary retrieval;
- prompt repository;
- LLM provider.

Do not make it responsible for:

- generating final MCQs;
- validating candidates;
- accepting questions;
- orchestration;
- output.

---

# 4. Planner LLM Contract

Use a dedicated structured-output response model.

The planner should return exactly the requested number of targets when the
evidence supports doing so.

Each target should identify a distinct factual/conceptual focus.

Use WP-022/WP-024's proven local-reference principle for evidence provenance:

    LLM returns local evidence refs
        ↓
    application validates/bounds-checks
        ↓
    application resolves to canonical chunk IDs

Do NOT ask the planner LLM to reproduce canonical chunk IDs.

Invalid evidence references fail closed.

---

# 5. Diversity Definition

The planning prompt must explicitly distinguish genuine diversity from
superficial wording differences.

The following are NOT sufficiently distinct:

### Rewording

    What does the spinothalamic tract transmit?

vs.

    Which sensory modalities are carried by the spinothalamic tract?

### Question/answer inversion

    Which tract carries pain and temperature?

vs.

    What does the spinothalamic tract carry?

### Same structure + same property

Two questions both testing:

    hippocampus → memory

even if phrased differently.

### Same narrow fact from different directions

For example:

    Where is structure X located?

and:

    Which structure is located at Y?

when both test exactly the same relationship.

The planner should prefer different:

- concepts;
- structures;
- functions;
- pathways;
- relationships;
- mechanisms;
- anatomical properties;
- clinically/anatomically relevant distinctions;

when those are actually supported by the category evidence.

---

# 6. Example

For category:

    מסילות עצביות

BAD target plan:

    Target 1:
        spinothalamic tract → pain and temperature

    Target 2:
        identify which tract carries pain and temperature

These test the same fact.

GOOD target plan, if supported by evidence:

    Target 1:
        spinothalamic tract → sensory modalities

    Target 2:
        corticospinal tract → pathway/decussation

The generated questions may use different forms, but their underlying factual
targets must be distinct.

---

# 7. Generation Must Receive the Target

Modify generation minimally so `QuestionGenerator` can generate toward a
specific `QuestionTarget`.

The generation prompt must receive the target explicitly.

Conceptually:

    category
    question_target
    source_evidence
    generation_mode
    historical_reference

The model should be instructed:

    Generate a question testing THIS target.

Do not silently switch to another easier fact from the category.

Do not broaden the target merely to produce a question.

Existing generation provenance behavior from WP-024 remains unchanged.

---

# 8. Historical STYLE_SIMILAR Behavior

STYLE_SIMILAR still means:

    use historical question as style/form inspiration

It must NOT override the planned factual target.

Historical references remain:

    style evidence

not:

    factual evidence

If a historical reference focuses on a different fact, the generated question
must still follow the planned target.

Preserve the existing factual/style authority boundary.

---

# 9. Orchestration

Modify exam orchestration so target planning happens once per category for the
number of questions requested from that category.

Conceptually:

    category requires 2 questions

        ↓

    plan_targets(category, 2)

        ↓

    target A
    target B

        ↓

    produce question for target A
    produce question for target B

The target assignment must remain stable throughout retries.

If generation of target B needs another WP-013/WP-019 attempt, it retries
TARGET B.

It must not ask the planner for a new target simply because candidate
generation failed.

This prevents target planning itself from becoming another hidden retry loop.

---

# 10. Preserve Existing Attempt Budget

This requirement is critical.

Do NOT make diversity rejection routinely consume:

    generation.max_generation_attempts

The existing attempt budget remains responsible for candidate-production
problems such as:

- generation-contract failure;
- grounding failure;
- MCQ failure;
- category failure;
- quality failure;
- textbook conflict.

Diversity should primarily have been decided before these attempts begin.

Do not increase `max_generation_attempts`.

Do not add category-specific attempt budgets.

---

# 11. Diversity Verification

A small post-generation diversity safeguard MAY be introduced if justified,
but it must not become the primary mechanism.

Its purpose would only be to detect cases where generation clearly ignored
different planned targets.

Before adding an LLM-based diversity validator, determine whether target
identity and existing generation constraints are sufficient.

Prefer the simpler design.

If a post-generation diversity check is introduced:

- keep it separate from existing validators;
- do not redefine grounding/MCQ/category/quality/textbook;
- document its retry/budget semantics explicitly;
- do not create an unbounded generation loop.

Do not add it merely because it seems architecturally symmetric.

---

# 12. Limited-Content Categories

The planner must handle categories whose evidence does not support the
requested number of genuinely distinct targets.

This is especially relevant to the previous diagnostic finding for:

    מבוא

Do not fabricate artificial target diversity.

Introduce an explicit failure/result for:

    insufficient distinct evidence-supported targets

Use the smallest appropriate model/error.

This should be distinguishable from:

    LLM/provider failure
    candidate-generation failure
    validation failure

With WP-023, if one planned question cannot be produced because the category
does not support enough distinct targets, the system should preserve honest
partial-result semantics rather than inventing a weak duplicate.

Do NOT special-case `מבוא` by name.

The behavior must be general.

---

# 13. Count Generality

Do not design this specifically around count=2.

It must support:

    1
    2
    3
    4
    ...

subject to available evidence and existing request constraints.

This is important because production may later return to 4 questions per
category.

For count=4, prefer:

    plan four targets once

rather than:

    generate Q1
    generate Q2 avoiding Q1
    generate Q3 avoiding Q1/Q2
    generate Q4 avoiding Q1/Q2/Q3

---

# 14. No Cross-Category Diversity Requirement

WP-025 concerns diversity WITHIN a canonical category.

Do not introduce a global semantic deduplication system across unrelated
categories.

Existing exact duplicate protection may remain unchanged.

Cross-category overlap can be investigated separately if future evidence
shows it is a problem.

---

# 15. Existing Validators Remain Independent

Do not modify the responsibilities of:

- GroundingValidator
- MCQValidator
- CategoryValidator
- QualityValidator
- TextbookValidator

A question can be:

    individually valid

while still being:

    redundant within an exam

That is why diversity belongs to planning/exam construction rather than these
validators.

Do not put "different from previous question" into QualityValidator.

---

# 16. Tests

Add focused tests for at least:

### Planning

- count=1 returns one target;
- count=2 returns two targets;
- count>2 supported structurally;
- targets preserve canonical category;
- every target is grounded in supplied evidence;
- local evidence refs resolve correctly;
- zero/negative/out-of-range refs fail closed;
- planner returns exactly requested count when evidence supports it.

### Diversity

Use explicit examples based on the WP-024 failure patterns.

Reject/avoid target plans equivalent to:

    spinothalamic tract → pain/temp
    spinothalamic tract → pain/temp reworded

and:

    hippocampus → memory
    hippocampus → memory phrased differently

Verify genuinely different factual targets are accepted.

### Generation

Verify:

    target A → generation prompt contains target A
    target B → generation prompt contains target B

Verify retries for target B continue using target B.

Verify STYLE_SIMILAR historical reference cannot replace target B's factual
focus.

### Limited evidence

Verify insufficient distinct supported targets produce an honest typed
failure/result.

No fabricated target should be produced merely to satisfy requested count.

### Regression

Verify WP-019 through WP-024 behavior remains intact.

# 25. Acceptance Criteria

WP-025 is complete when:

1. Multiple questions in one category are planned before generation.
2. Each question receives a distinct evidence-supported target.
3. Superficial rewording does not count as target diversity.
4. Question/answer inversion does not count as diversity.
5. Planner provenance uses local evidence references.
6. Local references resolve deterministically to supplied evidence.
7. Invalid planner provenance fails closed.
8. Generation receives its assigned target explicitly.
9. Retries retain the same target.
10. STYLE_SIMILAR cannot override the factual target.
11. Existing validators remain independent and unchanged in responsibility.
12. Diversity does not routinely consume the three-attempt candidate budget.
13. No attempt-limit increase is introduced.
14. Insufficient evidence for N distinct targets is represented honestly.
15. No category is special-cased.
16. Count is not hard-coded to 2.
17. WP-019/020/021/022/023/024 behavior remains intact.
18. Full regression passes.
19. Live diversity smoke test is performed if credentials are available.
20. One full 2-per-category acceptance run is performed if credentials are available.
21. Every resulting same-category pair is manually/semantically reviewed.
22. Diversity metrics are reported.
23. Retrieval/TF-IDF remains unchanged.
24. No embeddings/vector DB is introduced.
