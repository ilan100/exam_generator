OBJECTIVE

Establish the clean Python project skeleton and configuration infrastructure
for the Exam Generator.

This WP must NOT implement ingestion, PDF processing, Excel processing,
retrieval, embeddings, LLM calls, prompting, question generation, validation,
or exam generation.

The result should be a minimal, testable foundation for future WPs.

The project already has a local .venv created with Python 3.14.

Do not recreate or commit the virtual environment.

Before adding dependencies, verify that each dependency introduced in this WP
supports the installed Python 3.14 environment.

CONFIGURATION REQUIREMENTS

A. config/app.yaml

Must contain application-level configuration only.

At minimum support paths for:
- data directory
- output directory
- index directory
- prompts directory
- schemas directory

Paths must NOT contain machine-specific absolute paths such as
/home/ilan/... or \\wsl.localhost\...

Use project-relative configuration.

Also include configuration sections/placeholders for generation behavior that
are already architecturally defined, including:

- initial diversity target
- minimum diversity target
- diversity relaxation step
- maximum generation attempts per question

Choose conservative defaults, but do not implement their behavior yet.

B. config/llm.yaml

LLM configuration must be external.

At minimum represent:

provider: openai
model: <a configurable model string>

and separate parameter sections for:
- generation
- validation

Do not hard-code the provider/model in Python application logic.

The model value is configuration data and must be easy to replace later.

Use conservative/default values for parameters such as temperature where
appropriate.

Do not make any LLM/API call in this WP.

C. config/category_mapping.yaml

Create the configuration structure for future manual aliases/overrides.

Do NOT populate guessed category mappings.

It may initially contain an empty mapping plus explanatory comments/example
comments.

Canonical categories will later come from the historical Excel file.

D. .env.example

Document the expected secret environment variable for the OpenAI API key.

Example conceptually:

OPENAI_API_KEY=

Do not create a real .env.
Do not put any secret into configuration files.

CONFIGURATION MODELS

Use typed validation for configuration.

Pydantic is acceptable/preferred if compatible with Python 3.14 in the current
environment.

Define models representing the configuration actually introduced in this WP.

Requirements:

- invalid configuration should fail clearly;
- diversity values must be validated to sensible numeric ranges;
- minimum diversity cannot exceed initial diversity;
- diversity relaxation step must be positive;
- maximum attempts must be positive;
- provider/model strings cannot be empty;
- required paths cannot be empty.

Do not over-engineer a generic configuration framework.

CONFIGURATION LOADER

Implement a small configuration loader that:

- reads YAML configuration from the config directory;
- constructs validated typed configuration models;
- exposes a clean API future application code can use;
- does not depend on the process being launched from the repository root if a
  robust project-root/config resolution can reasonably be implemented;
- reports missing/malformed configuration clearly.

Do NOT load or validate OPENAI_API_KEY as a mandatory requirement during normal
configuration loading.

Reason:
many future commands/tests (ingestion, inspection, configuration validation)
should be able to run without an API key.

Secret/API-key validation belongs at the point where an LLM provider actually
needs it in a later WP.
