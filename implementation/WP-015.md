# 2. Objective

Implement the final output boundary for a successfully generated exam.

WP-014 currently produces an `ExamGenerationResult` containing:

* the clean exam;
* production history;
* candidate attempts;
* validation results;
* provenance needed for audit.

WP-015 transforms that into two clearly separated outputs:

```text
ExamGenerationResult
        │
        ├──────────→ Clean Exam Output
        │             student-facing
        │
        └──────────→ Audit Output
                      internal
                      generation provenance
                      validation results
                      attempts
                      acceptance decisions
```

The audit must explain how the exam was produced without contaminating the clean exam with internal metadata.

---

# 3. Core Boundary

Maintain strict separation between:

### Clean exam

Contains only information required to use the generated exam.

Conceptually:

```text
question number
question text
four answers
correct answer
category
```

Use the actual existing `Exam` / `ExamQuestion` contract.

### Audit

Contains internal production information such as:

```text
generation mode
generation attempts
source provenance
historical reference
validation results
textbook check
acceptance decisions
model/prompt metadata where available
```

Do not add audit fields to the clean exam models merely to simplify serialization.

---

# 4. Existing Contracts

Inspect and reuse the WP-002 audit/output contracts before implementing anything new.

The project already established top-level and per-question audit models in WP-002.

Use those contracts if they can represent the production history created by WP-013/014.

Do not create parallel audit models merely because the current orchestration models have different shapes.

If a genuine gap exists between the WP-002 audit contract and the information now available from WP-014, make the smallest justified model extension and document it.

Do not weaken existing validation.

---

# 5. Audit Construction

Create a deterministic transformation from a successful:

```text
ExamGenerationResult
```

into the existing final audit representation.

Conceptually:

```python
build_exam_audit(
    generation_result: ExamGenerationResult,
    ...
) -> ExamAudit
```

Exact naming is an engineering decision.

Audit construction must not call an LLM.

It is a deterministic application transformation over information already produced by the system.

---

# 6. Per-Question Audit

Every accepted exam question must have a corresponding audit record.

The audit should preserve, according to the existing contract:

* final question identity/number;
* canonical category;
* generation mode;
* accepted candidate provenance;
* student-summary evidence used during generation;
* historical reference ID when applicable;
* all production attempts;
* validation outcomes for each attempt;
* accepted/rejected status of each attempt;
* final grounding result;
* final MCQ result;
* final category result;
* final quality result;
* final textbook result.

Do not report rejected attempts as accepted questions.

---

# 7. Attempt History

Preserve the full WP-013 attempt history for each successfully produced question.

For example:

```text
Question 3

Attempt 1
  Grounding: PASS
  MCQ:       FAIL
  Category:  PASS
  Quality:   FAIL
  Textbook:  NOT_FOUND
  Accepted:  NO

Attempt 2
  Grounding: PASS
  MCQ:       PASS
  Category:  PASS
  Quality:   PASS
  Textbook:  CONSISTENT
  Accepted:  YES
```

The audit should make it possible to reconstruct:

```text
why was this candidate rejected?
why was the final candidate accepted?
how many attempts were required?
```

Do not discard rejected candidate history merely because it is absent from the clean exam.

---

# 8. Source Provenance

Preserve factual provenance without inventing new evidence.

Where available, audit should distinguish:

```text
Generation evidence
    STUDENT_SUMMARY chunks supplied to generator

Grounding evidence
    STUDENT_SUMMARY chunks independently supplied to validator

Historical reference
    style-only historical question

Textbook evidence
    COURSE_BOOK material used for secondary check
```

Do not merge these into a generic `sources` list if doing so would erase their different authority roles.

The distinction between factual evidence and historical style reference remains mandatory.

---

# 9. Provenance Trust

Audit construction must use the provenance already validated by the application.

Do not ask the LLM again what evidence it used.

Do not infer missing evidence IDs from question text.

Do not fabricate provenance for completeness.

If information is genuinely unavailable and the existing audit contract allows absence, represent it honestly.

If the audit contract requires information that cannot be derived from the actual production history, fail clearly rather than inventing it.

---

# 10. Prompt Provenance

Where the existing models/infrastructure make it available, preserve prompt identity/version information relevant to generation and validation.

WP-008 established deterministic prompt versions using SHA-256 hashes.

The audit should ideally make it possible to determine which prompt version produced each LLM-mediated decision.

Do not duplicate entire prompt text into every audit record.

Prefer:

```text
prompt ID
prompt version/hash
```

If current WP-013/014 production history does not retain enough information to recover prompt versions reliably, do not fabricate them.

Make the smallest architectural addition needed to capture them at execution time, or explicitly document the gap if the existing audit contract does not require them.

Avoid broad refactoring of previous WPs.

---

# 11. Model Provenance

Where reliably available through the existing LLM abstraction/configuration, preserve relevant model metadata such as:

```text
provider
model
profile
```

Do not include:

* API keys;
* authorization headers;
* secrets;
* environment values.

The audit must never serialize `OPENAI_API_KEY`.

Do not inspect or dump environment variables into audit output.

---

# 12. Clean Output Serialization

Provide deterministic serialization of the clean exam using the established Pydantic/domain model.

JSON is sufficient for WP-015.

The serialized clean output must contain only the public exam contract.

Do not expose:

* evidence chunks;
* prompt versions;
* model metadata;
* validation reasoning;
* failed candidates;
* historical-reference metadata

inside the clean exam output.

Use UTF-8 / Unicode-preserving serialization so Hebrew remains readable.

Do not unnecessarily escape Hebrew into `\uXXXX` sequences if the project's chosen serialization path allows readable Unicode.

---

# 13. Audit Serialization

Provide deterministic JSON-compatible serialization of the audit.

Requirements:

* stable structure;
* valid JSON;
* Hebrew preserved;
* enums serialized consistently;
* no arbitrary Python object representations;
* no secrets;
* no raw provider/client objects.

Prefer established Pydantic serialization rather than hand-built recursive JSON conversion when possible.

---

# 14. Output Bundle

Provide a focused application-facing output representation that associates:

```text
clean exam
audit
```

without merging them.

Conceptually:

```python
ExamOutputBundle(
    exam=...,
    audit=...,
)
```

or an equivalent established contract.

The exact name is flexible.

The important invariant is:

```text
one successful ExamGenerationResult
          ↓
one clean exam
+
one matching audit
```

---

# 15. Cross-Consistency

Audit and clean exam must correspond exactly.

Verify deterministically that:

* number of clean questions equals number of accepted question audit records;
* question numbers correspond;
* categories correspond;
* accepted candidate text/answers correspond to the clean converted question;
* correct-answer information corresponds;
* every clean question has exactly one final accepted production;
* no rejected candidate appears as a clean exam question.

Fail clearly if these invariants are violated.

Do not silently repair mismatched orchestration data.

---

# 16. Failed Exam Generation

WP-015 primarily handles a successful `ExamGenerationResult`.

Do not turn WP-014 failures into fake completed output bundles.

A failed or partial orchestration may contain useful diagnostics, but it is not a valid completed exam.

If useful and already supported by the domain models, provide deterministic serialization of failure diagnostics separately.

Do not broaden WP-015 into a general exception-reporting framework.

---

# 17. File Writing

Keep file-system concerns minimal.

It is acceptable to provide small deterministic helpers such as:

```python
write_exam_json(...)
write_audit_json(...)
```

if this fits the existing architecture.

However, the core WP must remain:

```text
domain result → output models → serialization
```

not:

```text
CLI/file management
```

If file writing is added:

* use UTF-8;
* do not overwrite unrelated files;
* do not create timestamp/random-name policies;
* keep paths caller-controlled;
* write clean exam and audit separately.

WP-016 will own user-facing CLI behavior.

---

# 18. No New LLM Calls

WP-015 must make:

```text
ZERO LLM calls
```

Audit/output construction is deterministic.

Do not use an LLM to:

* summarize validation reasons;
* rewrite audit text;
* produce JSON;
* generate filenames;
* explain provenance.

Use the structured results already available.

---

# 19. Tests

Add focused tests covering at minimum:

### Clean output

* successful generation result produces clean exam output;
* clean output contains expected question fields;
* clean output contains no validation metadata;
* clean output contains no evidence provenance;
* Hebrew survives serialization;
* exactly four answers remain intact;
* correct-answer information remains correct.

### Audit

* every clean question has one accepted audit record;
* all production attempts are preserved;
* rejected attempts remain visible in audit;
* all five validator results are preserved per attempt;
* generation mode is preserved;
* generation evidence provenance is preserved where available;
* grounding evidence is distinct from generation evidence;
* historical reference remains style-only metadata;
* textbook result/provenance is preserved;
* final accepted attempt is identifiable.

### Consistency

* question numbers match;
* categories match;
* question/answer content matches;
* mismatched generation/audit data fails clearly;
* rejected candidates never appear in clean exam;
* attempt ordering is deterministic.

### Security

* API key/secrets never appear in output;
* provider objects are not serialized;
* output does not dump environment variables.

### Serialization

* clean exam serializes to valid JSON;
* audit serializes to valid JSON;
* serialization is deterministic for identical input;
* Unicode/Hebrew remains readable.

All tests must be offline.

Run the full regression suite.

# 22. Acceptance Criteria

WP-015 is complete when:

1. A successful `ExamGenerationResult` can be transformed into final output structures.
2. Clean exam and audit remain separate.
3. Clean exam exposes no internal generation/validation metadata.
4. Every clean question has corresponding audit information.
5. Full production attempt history is preserved.
6. All five validation outcomes are preserved for every completed attempt.
7. Generation and grounding evidence remain distinguishable.
8. Historical references remain distinguishable from factual evidence.
9. Textbook information remains secondary-source metadata.
10. No provenance is invented.
11. Prompt/model provenance is preserved where reliably available.
12. Audit and clean exam are deterministically cross-checked.
13. Clean exam serializes to valid readable-Unicode JSON.
14. Audit serializes to valid readable-Unicode JSON.
15. No secret/API key can enter either output.
16. WP-015 makes zero LLM calls.
17. Unit tests are offline.
18. Full regression suite passes.
19. Real-data or realistic-fixture smoke verification succeeds.
20. Documentation/status is updated.
21. WP-016 has not been started.
