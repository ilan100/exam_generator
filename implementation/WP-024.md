# WP-024 — Generation-Side Local Evidence References

## Context

Read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-024.md`

WP-001 through WP-023 are complete.

WP-022 successfully removed fragile canonical chunk-ID reproduction from
grounding/textbook validation by having the LLM return small call-local
evidence references (`[Evidence N]`) and deterministically resolving those
references to canonical `SourceEvidenceChunk.chunk_id` values inside the
application.

Generation still uses the older mechanism: the LLM must reproduce canonical
student-summary chunk IDs verbatim.

The targeted post-WP-022 diagnostic showed this is now a dominant remaining
generation reliability problem: repeated generation-contract failures involved
the model inventing a canonical chunk ID rather than selecting one actually
supplied.

WP-023 now ensures an isolated question-local failure produces a PARTIAL exam
instead of destroying the rest of the exam. Do not change that behavior.

---

## Objective

Apply the proven WP-022 local-reference pattern to QUESTION GENERATION only.

Instead of asking the generation LLM to return:

    evidence_chunk_ids:
      - STUDENT_SUMMARY:student_summary_1.pdf:0002:0001

ask it to return call-local references corresponding to the already-rendered:

    [Evidence 1]
    [Evidence 2]
    ...

Conceptually:

    LLM
        evidence_refs = [1, 3]
             ↓
    QuestionGenerator
        bounds-checks refs
             ↓
        resolves them against the exact evidence supplied to this call
             ↓
        canonical chunk IDs
             ↓
    CandidateQuestion

The LLM must never be trusted to manufacture canonical provenance.

---

## Required Implementation

### 1. LLM-facing generation model

Evolve `GeneratedQuestionResponse` or introduce the smallest appropriate
generation-response model so the LLM-facing contract uses:

    evidence_refs: list[int]

instead of:

    evidence_chunk_ids: ...

Keep the rest of the generation response contract unchanged unless a very
small related adjustment is required.

Do not change `CandidateQuestion`'s canonical provenance contract.

The application-facing candidate must still contain genuine canonical
`evidence_chunk_ids`.

### 2. Prompt

Update the generation prompt so the model is explicitly instructed to cite
only the numbered evidence blocks supplied in the prompt.

For example, conceptually:

    evidence_refs must contain only the integer N from [Evidence N]
    that actually supports the generated question.

    Do not output canonical chunk IDs.
    Do not invent references.
    Leave the list empty if no supplied evidence supports the claim.

Use wording consistent with the successful WP-022 grounding/textbook prompts.

Do not redesign unrelated generation instructions.

### 3. Deterministic resolution

Inside `QuestionGenerator`, after the structured response returns:

- interpret each `evidence_refs` value as a 1-based index into the exact
  retrieved evidence sequence supplied to that generation call;
- reject `0`;
- reject negative values;
- reject values greater than the number of supplied chunks;
- deterministically resolve valid references to the corresponding canonical
  `SourceEvidenceChunk.chunk_id`;
- construct `CandidateQuestion` using those canonical IDs.

Do not fuzzy-match, repair, guess, or substitute references.

Invalid local references must remain fail-closed.

Reuse the existing `InvalidGeneratedOutputError` unless the current hierarchy
strongly justifies a narrower subtype.

### 4. Duplicate references

Choose deterministic semantics for repeated references such as:

    [1, 1, 3]

Prefer preserving first occurrence while deduplicating canonical provenance,
if consistent with existing model semantics.

Document and test the decision.

### 5. Historical reference

Do NOT generalize this change to `historical_reference_id`.

The previous diagnostic already established that historical-reference IDs are
small integers and have not been a reliability problem.

Keep existing historical-reference validation unchanged.

### 6. Canonical IDs in prompt

Do not perform a broad rewrite of the shared evidence formatter merely to hide
canonical IDs if other existing consumers still rely on it.

The important contract is:

    generation LLM cites [Evidence N]
    application resolves N
    downstream receives canonical ID

If canonical IDs remain visible as informational text in the rendered evidence
because of the shared formatter, explicitly instruct the generation model not
to reproduce them.

## Interaction With Existing WPs

### WP-019

Generation-contract recovery remains unchanged.

An invalid local reference is still an `InvalidGeneratedOutputError`, so the
existing bounded recovery mechanism should continue to work automatically.

Do not add another generation retry.

### WP-020

Structured-output retry remains unchanged and independent.

Malformed JSON is still a provider-level concern.

A syntactically valid but out-of-range `evidence_ref` is not a WP-020 failure.

### WP-021 / WP-022

Grounding/textbook validation behavior must remain unchanged.

Do not refactor their local-reference implementation merely to share code
unless an extremely small existing utility naturally applies.

Avoid premature abstraction.

### WP-023

PARTIAL exam behavior must remain unchanged.

A generation failure that exhausts the existing WP-019/WP-013 budget should
still become the appropriate question-local failure and allow the exam to
continue.
