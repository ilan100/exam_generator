# WP-017 — V1 Integration and Quality Evaluation

## 1. Context

Before implementation/evaluation, read completely:

* `docs/MASTER_PROJECT_BRIEF.md`
* `docs/ARCHITECTURE.md`
* `docs/PROJECT_STATUS.md`
* `implementation/WP-017.md`

WP-001 through WP-016 are complete and approved.

WP-017 is primarily an **evaluation and integration-hardening WP**, not a feature WP.

Implement only WP-017.

Do not start WP-018.

---

# 2. Objective

Evaluate the completed V1 system systematically and determine where its real quality/reliability bottlenecks are.

We want evidence about the full pipeline:

```text
ExamRequest
    ↓
retrieval
    ↓
generation
    ↓
Grounding
MCQ
Category
Quality
Textbook
    ↓
acceptance / regeneration
    ↓
exam orchestration
    ↓
clean output + audit
```

WP-017 should answer:

1. Does the complete pipeline work reliably?
2. How often are generated candidates accepted?
3. Which validators reject candidates most often?
4. Which categories are difficult?
5. Is retrieval supplying relevant factual evidence?
6. Are provenance/structured-output failures still occurring?
7. Is generated exam quality acceptable?
8. What should be improved next?

---

# 3. Critical Rule — Measure Before Improving

During the baseline evaluation, do **not** change:

* retrieval algorithm;
* TF-IDF parameters;
* chunking;
* generation prompts;
* validation prompts;
* acceptance policy;
* retry limits;
* model;
* temperature;
* category mappings.

Do not add:

* embeddings;
* vector database;
* reranking;
* validator-feedback regeneration;
* semantic duplicate detection.

First establish a trustworthy baseline.

If evaluation exposes a defect that prevents measurement entirely, report it before changing behavior.

A narrowly scoped correctness/instrumentation fix may be made only when necessary to obtain valid measurements, and it must be explicitly documented.

---

# 4. Evaluation Runner

Add a small evaluation layer/script that exercises the existing application programmatically.

Conceptually:

```text
evaluation plan
      ↓
existing production pipeline
      ↓
structured evaluation records
      ↓
aggregate metrics/report
```

A reasonable location is:

```text
scripts/
```

or:

```text
src/exam_generator/evaluation/
```

depending on whether reusable evaluation models/logic are needed.

Do not put evaluation logic into production orchestration.

---

# 5. Evaluation Categories

Use the project's actual canonical categories from the established category configuration.

The evaluation should cover **all canonical categories**, not only categories that happened to perform well during previous smoke tests.

For each category, attempt enough generation to reveal obvious failures while keeping live API cost reasonable.

Recommended baseline:

```text
2 requested questions per canonical category
```

If the project still has the previously reported 20 canonical categories, this means approximately:

```text
20 categories × 2 questions
= 40 requested accepted questions
```

Do not hard-code the number 20. Discover the actual canonical category set from the existing configuration.

If cost/runtime makes the full run impractical, implement the runner so the complete evaluation is supported, execute a representative subset, and clearly report the reduced sample.

---

# 6. Generation Modes

The evaluation must exercise both:

```text
STYLE_SIMILAR
INDEPENDENT
```

Use the existing deterministic generation-mode policy where practical.

Ensure both modes actually appear in the evaluated sample.

Do not invent a new production mode allocation policy just for evaluation.

Metrics should distinguish generation mode where useful.

# 7. Candidate-Level Metrics

For every generated candidate attempt, record at least:

```text
category
generation mode
attempt number
accepted / rejected
```

and the five validation outcomes:

```text
Grounding
MCQ
Category
Quality
Textbook
```

Do not rely only on the final accepted question.

Failed candidates are some of the most useful evaluation data.

---

# 8. Acceptance Metrics

Calculate at least:

### Candidate acceptance rate

```text
accepted candidates
-------------------
generated candidates
```

### First-attempt acceptance rate

```text
questions accepted on attempt 1
-------------------------------
successfully produced questions
```

### Attempts per accepted question

Report:

```text
mean
minimum
maximum
```

Median is useful if simple to provide.

### Exhaustion rate

How often does WP-013 reach its configured maximum generation attempts without finding an acceptable candidate?

---

# 9. Validator Failure Metrics

For rejected candidates, count how often each primary validator fails:

```text
Grounding
MCQ
Category
Quality
```

and how often textbook returns:

```text
CONSISTENT
POTENTIAL_CONFLICT
NOT_FOUND
```

A candidate may fail more than one validator, so these percentages need not sum to 100%.

Report both counts and percentages.

The purpose is to determine whether our bottleneck is primarily:

```text
factual grounding
MCQ construction
category fit
language/quality
textbook consistency
```

---

# 10. Category-Level Metrics

Report results by canonical category.

At minimum:

```text
requested questions
successfully produced questions
candidate attempts
accepted candidates
rejected candidates
attempt exhaustion
```

Also report validator-failure counts per category where the sample size supports useful interpretation.

Highlight categories with:

* unusually high attempt counts;
* repeated grounding failures;
* repeated MCQ failures;
* repeated category failures;
* repeated quality failures.

Do not draw strong conclusions from tiny samples without saying so.

# 11. Retrieval Evaluation

This section is especially important because we have intentionally kept TF-IDF rather than switching to embeddings.

Evaluate the existing retrieval layer independently from final generation quality.

Use representative queries across the canonical categories against the **student-summary index**.

At minimum verify:

```text
query
 ↓
top-k retrieved chunks
 ↓
does the returned evidence appear topically relevant?
```

Where practical, use factual phrases/concepts known to exist in the source corpus.

Record:

```text
category/query
top-k chunk IDs
scores
source file/page
```

Do not modify retrieval during this evaluation.

---

# 12. Retrieval Recall Dataset

Create a small deterministic retrieval-evaluation fixture.

Target approximately:

```text
20–40 queries
```

covering Hebrew, English, and mixed terminology.

For each query, identify one or more expected relevant chunks/pages based on actual corpus content.

Store only what is needed for deterministic evaluation, such as:

```text
query
expected chunk/page/source
```

Do not fabricate expected answers from general neuroanatomy knowledge.

Expected relevance must be grounded in the actual project corpus.

---

# 13. Retrieval Metrics

For the retrieval fixture, calculate at least:

```text
Recall@3
Recall@5
Recall@8
```

Conceptually:

```text
Did at least one expected relevant source appear
within the first K retrieval results?
```

Also report queries for which retrieval completely misses the expected evidence.

This is the primary evidence we will use to decide whether TF-IDF remains sufficient.

---

# 14. Embedding Decision Gate

Do **not** implement embeddings in WP-017.

Instead, conclude from the retrieval evaluation whether there is evidence that semantic retrieval is needed.

A reasonable interpretation is:

```text
high Recall@5/@8
        ↓
TF-IDF is probably sufficient for V1

repeated semantic misses despite relevant corpus evidence
        ↓
hybrid/embedding retrieval deserves investigation
```

Do not define an arbitrary pass/fail percentage solely to justify one technology.

Report the actual numbers and examples of misses.

---

# 15. Provenance Reliability

Track operational failures involving model-produced provenance.

We have already observed examples such as:

```text
dropped STUDENT_SUMMARY prefix
invented evidence ID
non-verbatim textbook reference_text
```

Count how often live evaluation encounters:

* invalid generation evidence IDs;
* invalid grounding evidence IDs;
* invalid textbook provenance;
* other structured-output/provenance failures.

These are **operational failures**, not validator failures.

Keep them separate in the metrics.

---


* STYLE_SIMILAR and INDEPENDENT paths;

# 19. Human Quality Review

Automated validators are not sufficient to establish that the generated exam is genuinely useful.

Perform a small manual review of accepted questions from the live evaluation.

Sample approximately:

```text
10 accepted questions
```

if enough successful questions are available.

Review and record, without modifying the questions:

* question clarity;
* Hebrew quality;
* anatomical terminology;
* plausibility of distractors;
* obvious ambiguity;
* apparent category fit;
* obvious duplication/repetition;
* whether the question looks suitable for the intended course exam.

This is an evaluation record, not another LLM validator.

If the evaluator cannot responsibly judge specialized factual correctness manually, rely on the project's source/grounding evidence for that dimension rather than inventing expertise.

# 20. Exam-Level Quality Observations

Inspect accepted questions collectively for issues individual validators may miss:

* repeated question patterns;
* repeated distractor patterns;
* excessive use of the same anatomical structure;
* near-duplicate questions;
* answer-position concentration;
* unnatural generation artifacts;
* STYLE_SIMILAR questions being excessively close to historical questions.

Record observations.

Do not implement corrective diversity logic yet.


# 25. No Quality Tuning During Baseline

This rule is important.

If the live run reveals:

```text
MCQ failure rate = high
```

do not immediately edit `generation/question.txt`.

If retrieval recall is poor, do not immediately install an embedding model.

If provenance failures occur, record them.

Complete and report the baseline first.

The purpose of WP-017 is to determine **what WP-018 or later hardening should actually address**.

---

# 26. Findings Classification

At the end, classify findings into:

### Blocking defect

System cannot reliably perform its intended V1 function.

### Reliability issue

System works, but operational/model-contract failures occur too frequently.

### Quality issue

Pipeline works, but accepted/generated content quality needs improvement.

### Enhancement

Would improve the system but is not necessary for V1 correctness.

Examples:

```text
TF-IDF Recall@8 = strong
→ embeddings likely enhancement

frequent MCQ rejection
→ generation-quality issue

frequent invented evidence IDs
→ reliability issue

audit/exam mismatch
→ blocking defect
```

Do not automatically implement the fixes.

# 29. Acceptance Criteria

WP-017 is complete when:

1. A reusable evaluation runner exists.
2. Candidate attempts and validator outcomes can be measured.
3. Acceptance rate is reported.
4. First-attempt acceptance rate is reported.
5. Attempts-per-question metrics are reported.
6. Exhaustion rate is reported.
7. Validator failure frequencies are reported.
8. Category-level performance is reported.
9. A corpus-grounded retrieval evaluation fixture exists.
10. Recall@3, Recall@5, and Recall@8 are measured.
11. Retrieval misses are inspectable.
12. Provenance failures are measured separately from validator failures.
13. Operational failures are measured.
14. Both generation modes are exercised.
15. End-to-end offline integration tests exist.
16. Full regression suite passes.
17. A live baseline is run if an API key is available.
18. Accepted questions receive a small human quality review where practical.
19. No embeddings/retrieval replacement is implemented.
20. No generation/validation tuning occurs during the baseline.
21. Findings are classified by severity/type.
22. WP-018 scope is recommended from evidence.
23. Documentation/status is updated.
24. WP-018 has not been started.
