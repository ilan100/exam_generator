# WP-019 — Bounded Generation-Contract Recovery and Failure Context

## 1. Context

Before implementation, read completely:

- `docs/MASTER_PROJECT_BRIEF.md`
- `docs/ARCHITECTURE.md`
- `docs/PROJECT_STATUS.md`
- `implementation/WP-019.md`

WP-001 through WP-018 are complete and approved.

WP-018 accepted V1 with a known residual limitation: occasional model-generated invalid provenance.

A subsequent real full-exam acceptance run requested 4 questions per canonical category. The run failed after approximately 62 seconds with:

    InvalidGeneratedOutputError:
    Generated response claims evidence chunk id(s) that were not supplied:
    ['STUDENT_SUMMARY:student_summary_2.pdf:0071:0001']

The application correctly rejected the fabricated provenance and wrote no partial output.

However, because `InvalidGeneratedOutputError` currently propagates as an operational failure, one malformed generation response terminates the entire exam.

For a large exam, a low per-attempt failure rate therefore becomes an unacceptable exam-level reliability problem.

WP-019 addresses this specific issue.

Implement only WP-019.

Do not introduce unrelated V2 features.

---

## 2. Objective

Add a strictly bounded recovery mechanism for **recoverable generation-contract failures** while preserving the existing fail-closed provenance policy.

Also improve exam-level failure context so that a failure identifies the planned question that was being produced.

The intended behavior is:

    generation LLM call
            ↓
    structured response
            ↓
    generation contract/provenance valid?
          /   \
        yes    no
        ↓       ↓
    validators  discard candidate completely
                ↓
          bounded fresh generation attempt
                ↓
          success OR exhaustion

The critical principle is:

    RETRY INVALID CANDIDATE
    NEVER ACCEPT INVALID PROVENANCE

WP-019 must not repair, normalize, guess, or accept fabricated provenance.

---

## 3. Problem Being Solved

The current WP-013 production cycle distinguishes:

### Candidate-quality rejection

A valid generated candidate reaches the validators but fails one or more validation checks.

Existing behavior:

    generate
       ↓
    validate
       ↓
    rejected
       ↓
    bounded regeneration

This already works correctly.

### Generation-contract failure

The generation LLM returns output that cannot safely become a `CandidateQuestion`, for example because it claims an evidence chunk ID that was never supplied.

Current behavior:

    generate
       ↓
    invalid provenance
       ↓
    InvalidGeneratedOutputError
       ↓
    entire exam aborts

WP-019 changes only the second case for specifically recoverable generation-contract failures.

---

## 4. Preserve Strict Provenance

The following behavior must remain unchanged:

- generation evidence IDs must correspond exactly to evidence actually supplied;
- fabricated IDs must never be accepted;
- shortened IDs must never be accepted;
- missing prefixes must never be silently restored;
- fuzzy matching is forbidden;
- invalid IDs must never be replaced with "probably intended" IDs;
- provenance checks must remain deterministic and application-side.

A failed generation response is discarded completely.

Nothing from it may reach:

- grounding validation;
- MCQ validation;
- category validation;
- quality validation;
- textbook validation;
- exam output;
- audit as an accepted candidate.

---

## 5. Recoverable Generation-Contract Failures

Inspect the existing generation error hierarchy before implementation.

At minimum, the observed:

    InvalidGeneratedOutputError

should be treated as a recoverable **candidate-generation contract failure** when it represents invalid model-produced output such as invalid claimed provenance.

Review other existing generation exceptions carefully.

Only failures caused by the model returning an unusable candidate contract should be considered for bounded recovery.

Do not broadly catch every `GenerationError` unless inspection proves that every subtype represents the same recoverable condition.

Prefer explicit exception handling.

---

## 6. Failures That Must NOT Be Retried Here

Do not use this mechanism for failures such as:

- missing `OPENAI_API_KEY`;
- authentication failure;
- configuration failure;
- rate-limit failure;
- API/network/provider failure;
- prompt repository/configuration failure;
- missing factual corpus;
- retrieval infrastructure failure;
- unknown category;
- programming errors;
- unexpected exceptions.

These remain operational failures and should propagate immediately.

The rule is:

    bad candidate contract from otherwise successful LLM response
        → bounded candidate-generation recovery

    infrastructure / configuration / provider failure
        → propagate

Do not create a generic retry mechanism.

---

## 7. Retry Ownership

Place recovery at the narrowest existing layer that owns candidate production attempts.

Prefer extending `QuestionProducer` rather than:

- the CLI;
- `ExamOrchestrator`;
- the OpenAI provider;
- `QuestionGenerator`.

Reasoning:

- `QuestionGenerator` should remain one logical generation attempt;
- the provider should remain one logical LLM call;
- the CLI should remain a thin adapter;
- the orchestrator should remain responsible for exam planning, not low-level generation recovery;
- `QuestionProducer` already owns bounded candidate-generation/validation attempts.

Use the actual existing architecture after inspection, but preserve these boundaries unless there is a compelling implementation reason not to.

---

## 8. Attempt Semantics

A recoverable generation-contract failure must consume a bounded production attempt.

For example:

    Attempt 1
      generation response has invented evidence ID
      → discarded

    Attempt 2
      valid candidate
      validators reject MCQ
      → discarded

    Attempt 3
      valid candidate
      validators accept
      → question accepted

All three are real attempts.

This prevents contract failures from creating an unbounded hidden retry loop.

Use the existing:

    generation.max_generation_attempts

if its current semantics can cleanly represent the total number of candidate-production attempts.

Do not add another retry configuration field unless genuinely necessary.

Prefer one clear bounded attempt budget over nested retry budgets.

---

## 9. Attempt History

The existing audit architecture preserves candidate validation attempts.

WP-019 must determine how generation-contract failures should appear in attempt history.

The audit should be honest enough to explain why extra generation calls occurred.

Do not fabricate a `CandidateQuestion` or fake validator results for a generation response that never became a valid candidate.

If the existing `QuestionAttempt` model cannot represent a pre-candidate generation-contract failure, make the smallest justified extension.

A reasonable conceptual representation is:

    attempt_number
    outcome
    failure_type
    failure_message

with candidate/validation data present only when a valid candidate existed.

Use the project's existing modeling conventions rather than blindly adopting these exact field names.

Avoid a broad audit redesign.

---

## 10. Exhaustion

If all configured production attempts are consumed without producing an accepted question, the existing bounded failure semantics must remain.

Conceptually:

    max_generation_attempts = 3

    attempt 1 → invalid generation provenance
    attempt 2 → invalid generation provenance
    attempt 3 → MCQ rejected
            ↓
    exhaustion
            ↓
    question production fails

The failure must preserve the complete attempt history, including recoverable generation-contract failures.

Do not automatically start a new attempt budget.

---

## 11. Validator Behavior

When generation-contract validation fails:

    validators must not run

This is important.

For a malformed/fabricated generation response:

- GroundingValidator: 0 calls
- MCQValidator: 0 calls
- CategoryValidator: 0 calls
- QualityValidator: 0 calls
- TextbookValidator: 0 calls

The response is discarded before validation.

When a subsequent valid candidate is generated, the existing five-validator flow proceeds unchanged.

---

## 12. No Provider-Level Retry

Do not modify:

    OpenAIProvider.generate_structured()

to automatically retry invalid generation provenance.

The provider does not understand application provenance semantics and must remain provider/application independent.

One call to:

    generate_structured()

must continue to represent one logical LLM call.

---

## 13. No Generator-Level Hidden Retry

Do not put a retry loop inside:

    QuestionGenerator.generate_candidate_question()

That method should continue to represent one candidate-generation attempt.

It may either:

    return CandidateQuestion

or:

    raise an appropriate generation error

Retry policy belongs outside the generator.

---

## 14. Failure Context Gap

The failed full-exam run exposed a second issue.

When `InvalidGeneratedOutputError` propagated directly, the CLI could report the reason but not:

- planned question position;
- category;
- generation mode;
- number of completed exam questions.

This must be improved.

At the exam-orchestration boundary, a question-production failure should preserve contextual information.

At minimum:

    planned position
    category
    generation mode
    completed production count
    underlying cause

Use the existing `QuestionProductionFailedError` or the closest appropriate existing error model if possible.

Do not create parallel error hierarchies unnecessarily.

---

## 15. Preserve Original Cause

When contextualizing a failure, preserve exception chaining.

Conceptually:

    raise QuestionProductionFailedError(...) from original_error

The underlying error must remain inspectable.

Do not convert:

    InvalidGeneratedOutputError

into a generic string-only error that loses its type/cause.

---

## 16. CLI Error Reporting

The CLI should remain thin.

If a question ultimately fails, the user-facing error should now contain useful context such as:

    Exam generation failed at question 17/80
    Category: <category>
    Generation mode: STYLE_SIMILAR
    Completed questions: 16
    Cause: generation attempts exhausted

Exact wording is implementation-dependent.

Do not dump full attempt histories to normal CLI output.

The detailed history belongs in the exception/audit/evaluation structures where appropriate.

Expected failures should still return a non-zero exit code without an unnecessary traceback.

---

## 17. Atomic Output Remains Unchanged

WP-016 behavior must remain:

    complete successful exam
            ↓
    write exam.json + audit.json

If the exam fails at question 79/80:

- no completed-looking `exam.json`;
- no completed-looking `audit.json`;
- no silently partial exam.

Do not change this behavior in WP-019.

---

## 18. Determinism and Safety

The recovery policy itself must be deterministic.

Given:

    max_generation_attempts = N

there may be at most N candidate-generation attempts for that planned question under the existing production budget.

Do not introduce:

- unbounded loops;
- random retry counts;
- sleep/backoff logic;
- provider retries;
- fuzzy provenance correction.

LLM output remains stochastic, but application control flow must remain bounded and deterministic.

---

## 19. Unit Tests

Add focused tests covering at minimum:

### Recoverable generation-contract failure

- first generation attempt raises `InvalidGeneratedOutputError`;
- no validators run for that attempt;
- second generation attempt succeeds;
- validators run normally;
- accepted question is returned.

### Multiple contract failures

- attempt 1 invalid provenance;
- attempt 2 invalid provenance;
- attempt 3 succeeds;
- exactly three generation calls occur.

### Mixed failure types

Example:

    attempt 1 → invalid provenance
    attempt 2 → valid candidate but MCQ rejected
    attempt 3 → accepted

Verify one shared bounded attempt budget.

### Exhaustion

- all attempts invalid provenance;
- production exhausts;
- correct exhaustion error raised;
- all attempt failures preserved.

### Non-recoverable errors

Verify no retry for:

- authentication error;
- provider error;
- rate-limit error;
- retrieval/configuration error where applicable.

Exactly one generation attempt should occur before propagation.

### Validators

Verify validators are never called for generation-contract-invalid attempts.

## 31. Architecture Boundary After WP-019

The intended final responsibility split should be:

    OpenAIProvider
        one structured LLM call
              ↓
    QuestionGenerator
        one candidate-generation attempt
        + strict provenance verification
              ↓
    QuestionProducer
        bounded candidate-production attempts
        handles recoverable candidate-contract failures
        runs validators for valid candidates
              ↓
    ExamOrchestrator
        exam planning
        duplicate handling
        question-level context
              ↓
    CLI
        thin user-facing adapter
        atomic output

Preserve this separation.

## 32. Acceptance Criteria

WP-019 is complete when:

1. `InvalidGeneratedOutputError` from model-produced invalid generation provenance can be recovered from within the bounded question-production attempt budget.
2. Invalid provenance is never accepted, repaired, normalized, or guessed.
3. A generation-contract-invalid attempt consumes an attempt.
4. Validators do not run for invalid generation-contract attempts.
5. Subsequent attempts can generate a fresh candidate.
6. Existing candidate-quality regeneration continues to work.
7. Contract failures and quality rejections share one bounded attempt budget unless existing architecture proves this inappropriate.
8. Exhaustion preserves the complete attempt history.
9. Provider/authentication/configuration/infrastructure failures are not generically retried.
10. `QuestionGenerator` still represents one generation attempt.
11. `OpenAIProvider` still represents one logical LLM call.
12. No generic retry mechanism is introduced.
13. Exam-level failure reports planned question position.
14. Exam-level failure reports category and generation mode.
15. Completed-question count is preserved.
16. Original exception cause is preserved.
17. CLI remains thin.
18. Atomic no-partial-output behavior remains unchanged.
19. Unit tests cover recovery, exhaustion, mixed failures, and non-recoverable failures.
20. Integration tests cover the new flow.
21. Audit/attempt history remains honest and serializable if extended.
22. Full regression suite passes.
23. A small live smoke test is performed if credentials are available.
24. The full 2-questions-per-category exam is attempted once after completion if credentials are available.
25. Full-exam results are reported honestly.
26. No retrieval/embedding/vector-DB changes are introduced.
27. No unrelated V2 feature is introduced.
