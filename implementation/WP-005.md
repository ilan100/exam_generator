WP-004.

WP-004 produces:

```

    ↓

```

```

```

# 3. Architectural Source Roles

The source distinction established in WP-002 remains mandatory.

## Student summaries

Chunks derived from student-summary PDFs use:

```
SourceType.STUDENT_SUMMARY
```

These chunks will later provide the primary factual grounding authority.

## Course book

Chunks derived from `course_book.pdf` use:

```
SourceType.COURSE_BOOK
```

These chunks will later provide secondary factual reference/check material.

Course-book chunks must remain distinguishable from student-summary chunks.

A future grounding process must not accidentally treat course-book evidence as
satisfying the student-summary grounding requirement.

## Historical questions

Historical questions remain:

```
STYLE / STRUCTURE / TERMINOLOGY DATA
```

They must not enter either factual corpus.

Do not chunk historical questions.

Do not convert `HistoricalStyleReference` into `SourceEvidenceChunk`.

# 6. Fundamental Page-Provenance Rule

Every `SourceEvidenceChunk` has exactly one:

```
page
```

Therefore, in V1:

```
A chunk MUST NOT span multiple physical PDF pages.
```

This is an explicit architectural decision.

Chunking occurs independently within each non-empty `ExtractedPage`.

This guarantees that:

```
chunk.page
```

always identifies the physical PDF page containing all text in that chunk.

Do not combine the end of page N with the beginning of page N+1.

This may produce a smaller final chunk on each page.

That is acceptable.

Reliable factual provenance is more important than maximizing chunk-size
uniformity.

# 7. Blank Pages

WP-004 preserves legitimate blank pages.

WP-005 must not create evidence chunks for pages whose extracted text is empty
or whitespace-only.

Requirements:

* blank pages produce zero chunks;
* later pages retain their original physical page numbers;
* blank pages do not cause renumbering;
* blank pages do not cause corpus construction to fail when other usable pages
  exist.

A document containing no chunks after chunking is invalid for corpus
construction and must fail clearly.

# 8. Chunking Strategy

Use a deterministic character-based V1 chunking strategy.

Do NOT add a tokenizer dependency solely for chunking.

The goal is to create chunks large enough to preserve useful local factual
context while avoiding very large retrieval units.

Use configuration for:

```
chunk_size
chunk_overlap
```

Recommended initial defaults:

```
chunk_size: 1800
chunk_overlap: 300
```

These values are measured in Python Unicode characters, not model tokens.

The exact defaults may be adjusted slightly only if inspection of the real
student-summary corpus demonstrates a clear problem.

If changed, document:

* observed issue;
* chosen values;
* rationale.

Do not tune chunk size against future generated-question performance in this WP.

Add explicit typed chunking configuration through the existing configuration
system.

A reasonable structure in `config/app.yaml` is:

```
chunking:
  chunk_size: 1800
  chunk_overlap: 300
```

or an equivalently clear configuration location consistent with the existing

Requirements:

### chunk_size

* positive integer;
* bool rejected.

### chunk_overlap

* non-negative integer;
* bool rejected;
* must be strictly less than `chunk_size`.

Invalid configuration must fail through the existing typed configuration
mechanism.

Do not bury chunk-size constants inside chunking code.

Do not introduce model-specific token limits.

# 10. Boundary-Aware Splitting

Do not blindly cut text every N characters when a reasonable nearby textual
boundary exists.

Use a small deterministic boundary-aware algorithm.

For each page:

1. establish the maximum chunk end using `chunk_size`;
2. if the remaining page text fits, emit it as the final chunk;
3. otherwise search backward within a limited boundary-search window for a
   useful natural separator;
4. prefer stronger textual boundaries over weaker ones;
5. if no acceptable separator exists, hard-split at the maximum size;
6. continue with the configured overlap.

A reasonable separator preference is:

```
paragraph/newline boundary
    ↓
sentence-ending punctuation
    ↓
whitespace
    ↓
hard character boundary
```

Support punctuation relevant to both Hebrew and English, such as:

```
.
?
!
```

Do not build a language parser.

Do not add NLP libraries.

The algorithm must remain understandable and deterministic.

---

# 11. Boundary Search Discipline

Boundary-aware splitting must not create pathological tiny chunks merely
because an early separator exists.

Search for a natural boundary only near the intended chunk end.

Use a small deterministic search window, either:

* derived from `chunk_size`; or
* represented by a clearly named constant/private policy.

Do not expose a large configuration surface unless necessary.

The final chunk of a page may naturally be smaller.

Avoid producing empty chunks.

Avoid producing chunks consisting only of whitespace.

---

# 12. Overlap Semantics

Adjacent chunks from the same page should overlap approximately according to:

```
chunk_overlap
```

The overlap exists to reduce factual context loss near chunk boundaries.

Requirements:

* overlap must never equal or exceed chunk size;
* chunking must always make forward progress;
* no infinite loops;
* no duplicate identical chunks caused by overlap logic;
* a page shorter than `chunk_size` produces exactly one chunk;
* overlap never crosses physical page boundaries.

Because boundary-aware splitting may move the chunk end backward, exact overlap
length may vary slightly.

Document the exact algorithm.

---

# 13. Text Preservation

Chunking must preserve source wording.

Do not:

* translate;
* summarize;
* lowercase;
* stem;
* remove anatomical terminology;
* rewrite Hebrew;
* rewrite English;
* semantically normalize text.

Minimal boundary handling is allowed.

For example, trimming whitespace from the beginning/end of emitted chunks is
acceptable if done consistently.

Do not collapse meaningful internal whitespace broadly.

Do not modify the underlying `ExtractedPage`.

---

# 14. Chunk IDs

Every chunk must have a stable deterministic `chunk_id`.

Do not use:

* random UUIDs;
* database-generated IDs;
* Python `hash()`;
* process-dependent identifiers.

The same unchanged:

```
source_file
source_type
page
chunk position
text
```

must produce the same chunk ID across repeated runs.

A readable deterministic V1 format is preferred.

For example, conceptually:

```
student_summary_1.pdf:p0001:c0001
```

or:

```
STUDENT_SUMMARY:student_summary_1.pdf:1:1
```

Exact formatting may differ.

Requirements:

* source identity represented;
* physical page represented;
* chunk ordinal within page represented;
* deterministic;
* unique within the constructed corpus;
* safe for normal JSON serialization.

Do not embed absolute machine paths in chunk IDs.

If filenames can contain problematic characters, handle them conservatively
and deterministically.

Do not introduce cryptographic hashing unless it provides a clear benefit.

---

# 15. Chunk Ordinals

Internally, chunk creation should use a deterministic 1-based chunk ordinal
within each physical page.

For example:

```
page 12:
    chunk 1
    chunk 2
    chunk 3
```

This ordinal does not need to be added to `SourceEvidenceChunk` as another
public field.

It may be represented through the chunk ID.

Do not modify the established WP-002 model solely to expose an ordinal.


Do not implement separate chunking algorithms for the two source types.
