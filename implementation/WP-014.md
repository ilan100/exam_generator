# 2. Objective

Implement orchestration of a complete exam from an `ExamRequest`.

The flow becomes:

```text
ExamRequest
     ↓
resolve requested categories/counts
     ↓
build deterministic question plan
     ↓
QuestionProducer × requested questions
     ↓
accepted CandidateQuestions
     ↓
CleanQuestion conversion
     ↓
Exam
```

WP-014 owns:

* interpreting the complete exam request;
* creating the question-production plan;
* invoking WP-013 once per required question;
* preserving category/count requirements;
* assigning generation modes according to established project policy;
* preventing obvious duplicate questions within the produced exam;
* producing the existing clean exam domain model.

WP-014 does not yet own file output, final audit serialization, or CLI behavior.

# 4. Exam Request Resolution

The orchestrator receives an `ExamRequest`.

Resolve requested categories using the existing deterministic category resolver before production.

Aliases must collapse into their canonical categories exactly as established in WP-006.

For example, if two request entries resolve to the same canonical category, their counts must be combined rather than treated as separate exam categories.

The total requested question count must be preserved.

Do not silently drop or add questions.

---

# 5. Question Plan

Before calling the LLM, create a deterministic question-production plan.

Each planned item should identify at least:

```text
canonical category
generation mode
```

and, if useful internally:

```text
question position / ordinal
```

For identical request/configuration, the plan must be identical.

Keep the planning representation small and immutable/read-only where practical.

---

# 6. Generation-Mode Allocation

Inspect the master brief and existing configuration/domain contracts for the established policy governing:

```text
STYLE_SIMILAR
INDEPENDENT
```

across an exam.

Use that existing policy.

Do not invent a new percentage if one is already defined.

If the existing project specification gives a ratio or count rule, convert it deterministically into per-question modes.

The allocation must preserve the required total number of questions.

If rounding is necessary, use a simple deterministic rule and document it.

Do not randomly assign modes in V1.

---

# 7. Category Distribution

For every canonical category requested:

```text
requested count = number of accepted questions
                  ultimately produced for that category
```

Do not compensate for failure in one category by producing extra questions in another.

For example:

```text
Brainstem       3
Cerebellum      2
```

must not become:

```text
Brainstem       2
Cerebellum      3
```

because one Brainstem question was difficult to produce.

Category requirements are part of the exam contract.

---

# 8. Question Production

For each planned question, invoke WP-013's existing `QuestionProducer`.

Do not duplicate:

* generation;
* validation;
* acceptance;
* bounded per-question regeneration

inside the exam orchestrator.

Conceptually:

```text
for planned_question in plan:
    result = producer.produce_question(
        category=planned_question.category,
        generation_mode=planned_question.generation_mode,
    )
```

Only an accepted candidate from a successful production result may enter the exam.

---

# 9. Exam-Level Failure

If WP-013 exhausts its allowed attempts for any required question, exam construction cannot silently continue with fewer questions.

Fail clearly.

Preserve useful context such as:

* which planned question failed;
* canonical category;
* generation mode;
* completed question-production results;
* exhausted-attempt history from the failed production.

Do not return a partial exam as though it were complete.

A partial internal result may be preserved for diagnostics/audit, but it is not a valid completed `Exam`.

---

# 10. Candidate → Clean Conversion

Once a candidate has been accepted by WP-013, convert it using the deterministic conversion established in WP-002.

Do not manually reconstruct `CleanQuestion` if an established conversion already exists.

The clean exam question should not expose internal generation/validation metadata that belongs in future audit output.

This boundary remains:

```text
CandidateQuestion
      ↓
validated / accepted
      ↓
deterministic conversion
      ↓
CleanQuestion
```

---

# 11. Exam Ordering

Preserve deterministic exam ordering.

The simplest V1 rule is to use the question-plan order.

Do not randomly shuffle the final exam unless an existing requirement explicitly requires it.

If the master brief establishes a different ordering policy, follow it.

The same successful production inputs should produce the same structural ordering policy even though LLM-generated text itself may vary between runs.

---

# 12. Duplicate Protection

WP-014 now has visibility into multiple accepted questions, so add **simple deterministic duplicate protection**.

At minimum, reject an accepted candidate if its normalized question text is exactly identical to a question already accepted into the current exam.

Normalization may reasonably include:

* trim leading/trailing whitespace;
* collapse repeated whitespace;
* case normalization where meaningful.

Do not implement embeddings, semantic similarity, or another LLM call for duplicate detection.

The goal is to prevent obvious duplicate leakage, not solve semantic diversity comprehensively.

---

# 13. Duplicate Replacement

If WP-013 returns an otherwise accepted candidate that duplicates an already accepted exam question, it cannot enter the exam.

The orchestrator may request another production cycle for that same planned question.

This exam-level duplicate replacement must itself be bounded.

Do not create an infinite loop around WP-013.

Use a small configuration-controlled or clearly bounded duplicate-replacement limit. Prefer an existing suitable setting if one exists.

If no such configuration exists, add the smallest appropriate configuration surface.

Document the distinction:

```text
WP-013 max_generation_attempts
    = attempts to make one acceptable candidate

WP-014 duplicate replacement
    = accepted candidate rejected because exam already contains it
```

Do not silently increase WP-013's internal attempt limit.

---

# 14. Diversity Scope

WP-014 should enforce only basic structural diversity that can be implemented deterministically and safely.

Required:

* no exact normalized duplicate question text.

Do not yet implement:

* embedding similarity;
* semantic duplicate detection;
* LLM-based diversity scoring;
* topic-subtopic inference;
* forced historical-reference rotation;
* complex distractor-diversity analysis.

If live testing shows obvious near-duplicate behavior, record it for later improvement rather than expanding WP-014 ad hoc.

---

# 15. Correct-Answer Position

Inspect the master brief/current architecture for any established exam-level answer-position policy.

If a balancing policy already exists, implement it.

If none exists, do **not** rewrite accepted questions merely to force equal answer-position distribution in WP-014.

In particular, do not swap answers after validation unless the architecture explicitly guarantees that such transformation preserves all validation/provenance semantics.

Record observed answer-position distribution for diagnostics instead.

---

# 16. Production History

Preserve the WP-013 `QuestionProductionResult` for every successfully produced exam question.

The orchestrator should therefore have enough information for WP-015 to build a full audit trail later.

Conceptually, an internal orchestration result may contain:

```text
Exam
+
question production results
+
plan
```

Do not throw away attempt/validation history after converting accepted candidates into clean questions.

However, do not implement final audit serialization yet.

# 17. Public Interface

Create a focused exam orchestration interface conceptually similar to:

```python
ExamOrchestrator.generate_exam(
    request: ExamRequest
) -> ExamGenerationResult
```

where the result contains at least:

```text
completed Exam
production history needed for future audit
```

The exact naming/model decomposition is Claude's engineering decision.

Dependencies should be injectable, especially:

* category resolver;
* `QuestionProducer`.

Provide a straightforward default-construction path using existing project configuration.

---

# 18. Operational Failure Semantics

Keep three cases distinct.

### Candidate rejection

Handled internally by WP-013's bounded attempts.

### Duplicate accepted candidate

Handled by WP-014's bounded duplicate replacement.

### Operational failure

Examples:

```text
provider/API failure
retrieval infrastructure failure
prompt failure
invalid configuration
```

Propagate immediately.

Do not restart the entire exam automatically.

Do not treat infrastructure failure as candidate-quality failure.

---

# 19. Tests

Add focused tests covering at minimum:

### Planning

* canonical category resolution;
* aliases combine counts correctly;
* total requested count preserved;
* generation-mode allocation follows established policy;
* plan is deterministic.

### Orchestration

* one requested question produces one clean question;
* multiple categories/counts produce exact requested distribution;
* `QuestionProducer` receives correct category and generation mode;
* only accepted candidates enter the exam;
* established candidate → clean conversion is used;
* final exam ordering follows plan order.

### Failure

* per-question attempt exhaustion fails exam generation;
* partial exam is not returned as complete;
* failure identifies planned question/category/mode;
* operational failures propagate immediately.

### Duplicate protection

* exact duplicate accepted question is rejected at exam level;
* normalized whitespace duplicate is detected;
* replacement production is requested for the same category/mode;
* unique replacement is accepted;
* duplicate replacement is bounded;
* duplicate exhaustion fails clearly;
* no semantic/LLM duplicate detector is introduced.

### History

* production history is retained for every accepted question;
* failed production diagnostics remain available where appropriate;
* clean exam does not expose internal validation metadata.

All unit tests must mock/fake LLM-dependent production behavior.

Run the complete regression suite offline.

# 23. Acceptance Criteria

WP-014 is complete when:

1. A valid `ExamRequest` can be converted into a deterministic question plan.
2. Request categories resolve through the established canonical resolver.
3. Canonicalized category counts exactly match the request.
4. Generation modes follow the established project policy.
5. WP-013 `QuestionProducer` is reused rather than duplicated.
6. Every completed exam question comes from an accepted candidate.
7. Accepted candidates use the established deterministic clean conversion.
8. Final exam contains exactly the requested number of questions.
9. Final category distribution exactly matches the canonicalized request.
10. Exam ordering is deterministic.
11. Exact normalized duplicate questions cannot enter the exam.
12. Duplicate replacement is bounded.
13. Duplicate replacement preserves category and generation mode.
14. Per-question attempt exhaustion prevents a falsely complete exam.
15. Operational failures propagate immediately.
16. Production/attempt history is retained for future audit.
17. No semantic/LLM diversity system is introduced.
18. No final output/audit serialization is implemented.
19. Unit tests are offline.
20. Full regression suite passes.
21. One small live exam smoke test is executed if an API key is available.
22. Documentation/status is updated.
23. WP-015 has not been started.
