# 2. Objective

Implement independent textbook consistency checking for a `CandidateQuestion`.

The system already has primary factual grounding against student summaries:

```text
CandidateQuestion
      ↓
student-summary evidence
      ↓
GroundingValidator
      ↓
GroundingValidationResult
```

WP-012 adds a separate secondary check:

```text
CandidateQuestion
      ↓
course-book retrieval
      ↓
WP-008 textbook prompt
      ↓
LLMProfile.VALIDATION
      ↓
TextbookCheckResult
```

The purpose is to determine whether available course-book evidence supports, contradicts, or is insufficient to assess the candidate according to the existing WP-002 contract.

---

# 3. Authority Boundary

This is the central rule of WP-012:

```text
Student summaries = primary factual grounding authority

Course book       = secondary consistency evidence
```

Textbook validation must never replace WP-010 grounding.

Therefore:

```text
Grounding FAIL
Textbook SUPPORTS
```

does **not** make the candidate grounded.

Likewise, WP-012 must not modify a `GroundingValidationResult`.

The two judgments remain independent for later orchestration.

---

# 4. Existing Infrastructure

Reuse the existing:

* `CandidateQuestion`;
* `TextbookCheckResult` and its established status/result semantics;
* WP-005 course-book corpus;
* WP-006 course-book retrieval index;
* WP-008 textbook prompt and formatting infrastructure;
* WP-007 `LLMProvider`;
* `LLMProfile.VALIDATION`.

Inspect the actual current `TextbookCheckResult` model and enum/status fields before implementation.

Do not redesign the existing contract merely to fit preferred terminology such as `SUPPORTED`, `CONTRADICTED`, or `INSUFFICIENT` if the current model uses different names.

---

# 5. Public Interface

Create a focused validator consistent with the existing validation package.

Conceptually:

```python
TextbookValidator.validate(
    candidate: CandidateQuestion
) -> TextbookCheckResult
```

Dependencies should be injectable, particularly:

* course-book retrieval index;
* prompt repository;
* LLM provider.

Provide normal default construction using the established configuration infrastructure.

Keep this as another explicit validator rather than introducing a generic validation framework.

---

# 6. Independent Textbook Retrieval

The validator must retrieve relevant evidence from the **course-book index**.

Construct a deterministic query from the candidate content.

A reasonable V1 query is based on:

```text
category
+ question
+ intended correct-answer text
```

This mirrors the general independent-evidence principle established in WP-010.

The precise query construction is an engineering decision, but document it.

Do not retrieve textbook evidence using only the candidate's generation evidence IDs; those IDs refer to student-summary evidence and are irrelevant to course-book retrieval.

---

# 7. Retrieval Source Isolation

WP-012 textbook retrieval must use only:

```text
SourceType.COURSE_BOOK
```

Do not retrieve:

* student-summary chunks;
* historical questions.

Do not modify WP-010's student-summary grounding retrieval.

The two factual evidence paths must remain visibly separate:

```text
STUDENT_SUMMARY index
        ↓
GroundingValidator


COURSE_BOOK index
        ↓
TextbookValidator
```

---

# 8. Empty / Weak Textbook Evidence

Unlike primary grounding, absence of useful textbook evidence is not necessarily an operational failure.

The course book may simply not contain enough material to evaluate a particular candidate.

Therefore, inspect the existing `TextbookCheckResult` contract and use its established insufficient/unclear/not-found semantics where applicable.

Conceptually:

```text
no useful textbook support found
        ↓
INSUFFICIENT / UNCLEAR
```

rather than automatically:

```text
candidate contradicted
```

Do not invent factual contradiction from absence of evidence.

If the existing result contract cannot represent this distinction, stop and report the mismatch rather than silently redesigning it.

---

# 9. Textbook Prompt

Use the production:

```text
PromptId.TEXTBOOK_VALIDATION
```

established in WP-008.

Supply:

* formatted candidate question;
* independently retrieved course-book evidence.

Use WP-008's existing course-book evidence formatter and source delimiters.

Do not embed another textbook-validation prompt in Python.

The prompt must continue to make clear that textbook evidence is secondary and cannot establish primary grounding.

---

# 10. LLM Execution

Use:

```text
LLMProfile.VALIDATION
```

and request the existing:

```text
TextbookCheckResult
```

as structured output.

One validator invocation should make at most one semantic LLM validation call.

Do not add retry logic.

Operational failures remain operational failures; they must not be converted into textbook verdicts.

---

# 11. Textbook Verdict Semantics

The validator should determine, according to the existing result model, whether retrieved course-book evidence:

* supports the candidate's factual premise/correct answer;
* contradicts it;
* or is insufficient/unclear to decide.

The textbook validator does **not** decide:

* whether student-summary grounding passed;
* whether the MCQ is well constructed;
* whether the category is correct;
* whether the Hebrew is good;
* whether the candidate should ultimately be accepted.

Those remain separate concerns.

---

# 12. Provenance Integrity

If `TextbookCheckResult` contains supporting/reference evidence IDs, verify them deterministically.

Any evidence ID returned by the LLM must correspond to a course-book chunk actually supplied to the textbook validator.

Reject invented or unknown chunk IDs.

Do not silently repair:

```text
COURSE_BOOK:...
```

identifiers returned incorrectly by the model.

The strict provenance behavior established in WP-009 and WP-010 should remain consistent here.

---

# 13. Independence From Other Validators

`TextbookValidator` must not invoke:

* `GroundingValidator`;
* `MCQValidator`;
* `CategoryValidator`;
* `QualityValidator`.

It receives a candidate and produces its own independent result.

Later orchestration will combine results.

This allows states such as:

```text
Grounding    PASS
MCQ          PASS
Category     PASS
Quality      PASS
Textbook     CONTRADICTS
```

or:

```text
Grounding    FAIL
Textbook     SUPPORTS
```

without WP-012 deciding what the final system should do.

---

# 14. Tests

Add focused tests covering at minimum:

* course-book evidence is independently retrieved;
* only the course-book index is used;
* candidate question/correct answer participate in the retrieval query;
* textbook production prompt is used;
* course-book evidence is formatted through WP-008;
* `LLMProfile.VALIDATION` is used;
* valid support verdict is returned normally;
* valid contradiction verdict is returned normally;
* insufficient/unclear evidence is represented according to the existing contract;
* absence of evidence is not treated as contradiction;
* returned evidence IDs must belong to supplied course-book chunks;
* invented evidence IDs are rejected;
* candidate generation evidence IDs are not used as textbook provenance;
* historical references are not used;
* validator does not invoke other validators;
* candidate is not mutated;
* one invocation makes no more than one LLM call;
* no retry/regeneration occurs;
* provider/prompt failures remain operational failures.

Mock the LLM in unit tests.

Run the complete regression suite offline.

```text

```

is perfectly valid.

---

# 16. No Overall Acceptance Yet

WP-012 completes the individual validation capabilities, but it must **not** introduce a rule such as:

```python
accepted = (
    grounding.passed
    and mcq.passed
    and category.passed
    and quality.passed
    and textbook.supported
)
```

That would prematurely encode orchestration policy.

In particular, do not assume that textbook `INSUFFICIENT` should reject a candidate.

The acceptance/retry policy belongs to the next control-layer work.

# 19. Acceptance Criteria

WP-012 is complete when:

1. `CandidateQuestion` can be checked against course-book evidence.
2. Course-book evidence is independently retrieved.
3. Only the course-book retrieval index is used.
4. Existing WP-008 textbook prompt/formatting is reused.
5. WP-007 is used with `LLMProfile.VALIDATION`.
6. Existing `TextbookCheckResult` semantics are preserved.
7. Support, contradiction, and insufficient/unclear evidence remain distinguishishable where supported by the existing contract.
8. Absence of evidence is not interpreted as contradiction.
9. Textbook evidence IDs are verified against chunks actually supplied.
10. Textbook support cannot replace student-summary grounding.
11. No other validator is invoked.
12. No overall candidate-acceptance policy is implemented.
13. No retry/regeneration logic is implemented.
14. Unit tests require no API key/network.
15. Full regression suite passes.
16. One live textbook check is executed if an API key is available.
17. Documentation/status is updated.
18. WP-013 has not been started.
