WP-018 through WP-022's full acceptance runs each aborted before writing any output (the CLI only writes files after the full plan completes, or — since WP-023 — safely reaches the end with a mix of accepted/failed questions), so no output pairs exist for those.

WP-032's acceptance run deliberately does **not** produce an `exam.json`/`exam_audit.json` pair - the whole point of its methodology (WP-032 section 11) is to bypass `ExamOrchestrator`/the CLI/the WP-015 output boundary entirely, calling `CategoryGenerationService.generate_next()` directly instead, to verify the new architecture can completely replace the old orchestration on its own. `wp032_acceptance_records.json` is the equivalent raw record (one entry per planned question, including full per-attempt validation detail) captured directly from the service's own `CategoryGenerationResponse` objects. WP-033 has no full-scale acceptance run of its own (see `implementation/WP-033_COMPLETION_REPORT.md` for why) - only the four-scenario evaluation above. WP-034's `wp034_acceptance_records.json` follows the same raw-record methodology as WP-032's, via `CategoryQuestionSetService` instead. WP-035 produced no live-run artifact (investigation only, no code). WP-036's `wp036_pilot_records.json` is scoped to only the 3 pilot categories (not all 20), recording each round's deterministically-selected concept alongside the actually-generated question/answer - the field that made the target-selection-vs-tested-content divergence visible. WP-037's `wp037_pilot_records.json` follows the same per-round record shape, additionally recording the anchored `factual_focus` actually used and a deterministic (text-exact) alignment pre-classification - manually re-verified afterward, per the completion report's own methodology section. WP-038's `wp038_pilot_records.json` follows the same per-round record shape again, additionally recording each selected concept's deterministic `ConceptIdentity` (`concept_normalized_forms`/`concept_explicitly_supported_language_forms`) and whether that identity recognized the actually-generated correct-answer text (`identity_recognized_generated_answer`) - the field that shows, per round, whether WP-038's coverage-recognition mechanism fired at all.

The `wp025_*_targets.json`/`wp026_*_targets.json`/`wp027_*_targets.json`/`wp028_*_targets.json`/`wp030_*_targets.json`/`wp031_*_targets.json`/`wp032_*_targets.json` files are an addition specific to WP-025 through WP-032: `QuestionTargetPlanner.plan_history`, captured by running the same production wiring the CLI itself uses (not a shortcut) via a small script, since the real CLI does not expose planned-target data - needed to review planned-target-vs-generated-question diversity honestly rather than guessing from question text alone. WP-034's raw records already embed the planned target/relationship per question directly (read from the same `plan_history` property at call time), so no separate `_targets.json` file was needed - WP-036/WP-037 follow the same pattern.
