WP-042 produced no pilot artifact - `wp042_diagnostic.json` is a one-shot, per-attempt validator-level capture for exactly the targets WP-041's own pilot showed regressing, structured very differently from every other file here (one entry per real generation attempt, including every validator's own `valid`/`passed`/`reason`), since the whole point was to see *why* attempts were rejected, not merely whether the round as a whole was accepted. WP-043's `wp043_pilot_records.json` follows the same flat per-round shape as WP-036/037/040/041, additionally carrying `is_source_role` (WP-043 Part B's own deterministic detection result), `factual_focus_before_fallback`/`factual_focus_after_fallback`/`fallback_occurred` (WP-043 Part A's own sufficiency-check outcome, recomputed read-only for observability from the same refined inventory the real planning call itself used - never a second decision path). WP-044's `wp044_pilot_records.json` is structured differently from every prior pilot file: each round's record carries `target_role`/`evidence_shape`/`tested_relationship_downstream_entity` (the new WP-044 fields actually set on the real `QuestionTarget` for that round) plus a nested `attempts` list with **every** attempt's own full per-validator breakdown (`grounding`/`mcq`/`category`/`quality`/`textbook`, each with its own pass/fail and `reason`) and, for a rejected attempt, an explicit `rejection_reasons` list - not just the final round-level accept/reject, since WP-044's own required evaluation (sections 29-31) is specifically about whether the new structural constraints changed *which question forms* generation attempted, which requires seeing every attempt, not only the one that succeeded or the fact that all three failed. WP-045's `wp045_pilot_records.json` follows the same nested per-attempt shape as WP-044's, additionally carrying all four answer choices per attempt (not only the correct one) and the diagnostic-only `has_named_child` annotation described above - since the whole point of this WP was determining *why* specific attempts failed, at a level of detail even WP-044's own record shape did not need. WP-046's `wp046_pilot_records.json` follows the identical shape to WP-045's own file - a generation-contract failure attempt (the new WP-046 check firing, or any other pre-validator rejection) is distinguishable from an ordinary validator rejection by the presence of `generation_failure_type`/`generation_failure_message` instead of `answers`/`validations`, exactly mirroring `QuestionAttempt`'s own real structure (`production/models.py`) rather than a bespoke pilot-only shape.

WP-034's raw records already embed the planned target/relationship per question directly (read from the same `plan_history` property at call time), so no separate `_targets.json` file was needed - WP-036/WP-037 follow the same pattern.
