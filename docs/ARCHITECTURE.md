# Exam Generator — Architecture Record

## Purpose
This file records enduring technical architecture and interface decisions. It is not a work log. Update it only when an accepted architectural decision changes or a Work Package establishes a new durable interface.

## System Context
The application generates Hebrew neuroanatomy MCQ exams using:
- Hebrew student-summary PDFs as authoritative factual grounding.
- `course_book.pdf` as secondary validation/reference.
- `questions_full_export.xlsx` as historical style/structure reference.
- A JSON exam request specifying question counts per category.

## High-Level Flow
### Ingestion
`PDFs -> text extraction -> page-preserving chunks -> metadata -> embeddings/index`

Ingestion is separate from exam generation and should be rerun only when relevant source material/index configuration changes.

### Generation
`exam request -> category validation -> retrieval -> mode selection -> candidate generation -> independent validation -> retry/diversity controller -> exam assembly -> exam JSON + audit JSON`

## Source Authority Boundary
1. Student summaries: authoritative factual evidence.
2. Course book: secondary consistency/reference check only.
3. Historical questions: style/structure/difficulty/terminology reference only.

The code and prompts must preserve this distinction explicitly.

## Retrieval
- Use a local searchable index for V1.
- Preserve at minimum: `chunk_id`, `source_file`, `page`, `text`, and `source_type`.
- `source_type` (`SourceType`, WP-002) is exactly `STUDENT_SUMMARY` or `COURSE_BOOK`; historical exam questions are never a `SourceType` value.
- `page` uses human-readable, 1-based PDF page numbering (frozen by WP-002's `SourceEvidenceChunk` domain model).
- Retrieval must be semantic enough to handle category/chapter wording differences.
- Support external category aliases/manual overrides via configuration.
- Historical exam questions are represented by a structurally separate domain model (`HistoricalStyleReference`, WP-002) and must never be exposed as, or mixed into, factual grounding evidence (`SourceEvidenceChunk`).

## Canonical Categories
Canonical categories are derived from the historical workbook's `category` column rather than duplicated as Python constants where avoidable.

## Historical Question Ingestion (WP-003)
`src/exam_generator/historical/` loads `data/questions_full_export.xlsx` (via `openpyxl`, not pandas) into WP-002 `HistoricalStyleReference` objects, exposed through a read-only `HistoricalQuestionRepository`.

- **V1 workbook contract**: only `id`, `category`, `question`, `answer1..4`, `correct_answer_id` are required headers; column order does not matter; extra columns (`categories_json`, `accuracy_values`, `distinction_values`, `source`, `uploaded_at`, `created_at`, `updated_at`, or any future addition) are ignored by this subsystem rather than part of the contract.
- Row-level structural validation is delegated to `HistoricalStyleReference` itself (not re-implemented at the ingestion boundary), so ingestion cannot silently diverge from the WP-002 domain contract. Ingestion fails closed: a malformed/partially-populated row raises a `HistoricalQuestionRowError` identifying the worksheet row rather than being skipped or repaired.
- Canonical categories are derived only from successfully ingested historical questions' `category` values, in **first-seen workbook order** (not alphabetical, not a `set`). Duplicate category text collapses to one canonical category; category text is preserved verbatim (no aliasing, no fuzzy matching at this layer).
- `HistoricalQuestionRepository.questions_for_category()` does exact string matching only; an unknown category returns an empty tuple rather than raising, since callers may legitimately probe availability. `ExamRequest` still does not validate against this list — that remains deferred to a later orchestration WP.
- Historical question order is preserved (workbook row order), both in `all_questions` and within `questions_for_category()`.
- The repository is read-only after construction (tuples / `MappingProxyType`); nothing in this subsystem constructs or exposes a `SourceEvidenceChunk` from historical data.

## PDF Text Extraction (WP-004)
`src/exam_generator/ingestion/` extracts the project's factual-source PDFs (student summaries and `course_book.pdf`) into typed, page-aware in-memory representations, stopping before chunking.

- **Library**: [PyMuPDF](https://pypi.org/project/PyMuPDF/) (`pymupdf`), not pypdf/pdfminer. Selected after directly comparing extraction of the real student-summary PDFs: PyMuPDF returns Hebrew/RTL text in correct logical reading order and extracts ~14x faster, whereas pypdf returned Hebrew visually reversed (e.g. `ןילוסא ריש` instead of `שיר אסולין`) and emitted xref warnings. `pymupdf.open(path, filetype="pdf")` is used explicitly (not relying on extension-based auto-detection) so a non-PDF file cannot be silently accepted as some other MuPDF-supported document type.
- **Extraction-layer models** (`ExtractedPage`, `ExtractedDocument`) are structurally separate from `SourceEvidenceChunk` (WP-002): they represent raw page-aware extraction output, not post-chunking factual evidence. Nothing in this subsystem constructs a `SourceEvidenceChunk`; chunking is an explicitly separate, later WP's responsibility.
- Page numbers are human-readable, 1-based, and must form the contiguous sequence `1..N` in physical PDF order - consistent with the 1-based page convention already established by `SourceEvidenceChunk` (WP-002).
- Text is preserved as extracted (no translation, lowercasing, or semantic normalization); only the underlying library's own text-layer extraction is used - no OCR.
- **Blank-page policy**: an individual page may legitimately have empty extracted text (real course-book/summary PDFs contain scattered blank/divider pages) without failing the document; page numbering and ordering are never altered because of a blank page. A whole document containing **no** usable text on any page fails closed (`PdfTextExtractionError`).
- **Source-discovery policy**: student-summary PDFs are every `*.pdf` file in the configured data directory except the fixed `course_book.pdf` filename, sorted lexically by filename for determinism; the course book is resolved via that same fixed filename. Source classification (`SourceType.STUDENT_SUMMARY` vs. `COURSE_BOOK`) happens only at this discovery boundary - the generic `extract_pdf()` API requires the caller to pass `source_type` explicitly and never infers it from a filename.
- Extracted documents/pages are read-only after construction (frozen models, `tuple` page sequence).

## Factual Source Chunking and Corpora (WP-005)
`src/exam_generator/chunking/` converts WP-004 `ExtractedDocument`/`ExtractedPage` output into WP-002 `SourceEvidenceChunk` objects, and assembles them into read-only `FactualSourceCorpus` instances (`build_student_summary_corpus()`, `build_course_book_corpus()`). `SourceEvidenceChunk` remains the sole authoritative factual-chunk model - no competing chunk model was introduced.

- **A chunk never spans more than one physical PDF page (frozen V1 decision).** Chunking runs independently within each non-blank `ExtractedPage`, so `chunk.page` always identifies the exact physical page containing all of that chunk's text.
- **Chunking is deterministic and character-based**, not token-based - no tokenizer/NLP/embedding dependency was introduced. Configured via `config/app.yaml`'s `chunking.chunk_size`/`chunking.chunk_overlap` (defaults: `1800`/`300` characters), validated by `ChunkingConfig` (positive `chunk_size`, non-negative `chunk_overlap`, `chunk_overlap` strictly less than `chunk_size`, bool rejected for both).
- **Boundary-aware splitting**: near the configured chunk end, a bounded backward search (a fixed fraction of `chunk_size`) prefers a newline, then Hebrew/English sentence-ending punctuation (`. ? !`), then any whitespace, before falling back to a hard character split. Adjacent chunks on the same page overlap by approximately `chunk_overlap` characters; overlap never crosses a page boundary, and the algorithm is guaranteed to make forward progress (no infinite loops) regardless of where a boundary is found.
- **Chunk IDs** are stable and deterministic: `"{source_type}:{source_file}:{page:04d}:{ordinal:04d}"` (e.g. `STUDENT_SUMMARY:student_summary_1.pdf:0005:0001`) - no UUIDs, no `hash()`, no process-dependent identifiers. `FactualSourceCorpus` construction validates chunk-ID uniqueness and raises `DuplicateChunkIdError` otherwise.
- **Blank pages produce zero chunks** but do not affect later pages' physical page numbers; a document that yields zero chunks overall fails closed (`ChunkingError`).
- **Corpus separation**: the student-summary corpus and course-book corpus are always built and returned separately (`build_student_summary_corpus()` / `build_course_book_corpus()`); nothing merges them. Corpus ordering is deterministic: source-file order → physical page order → within-page chunk ordinal order.
- Category assignment is explicitly out of scope for chunking; `SourceEvidenceChunk`/corpora carry no category field. Retrieval/indexing/ranking are downstream, later-WP responsibilities - this WP only produces the in-memory factual corpus.

## Local Retrieval and Category Integration (WP-006)
`src/exam_generator/retrieval/` builds a deterministic, local lexical retrieval baseline over a WP-005 `FactualSourceCorpus`, and activates canonical-category resolution/aliasing for `ExamRequest` (deferred by WP-002).

- **V1 retrieval baseline: character n-gram TF-IDF** (`scikit-learn`'s `TfidfVectorizer(analyzer="char_wb", ngram_range=(3, 5))`), not embeddings/vector search. Chosen because the corpus mixes Hebrew, English anatomical terminology, and mixed text; character n-grams need no language-specific stemming/stop-words/lemmatization. The analyzer is a fixed internal policy (not configuration); `top_k`/`ngram_min`/`ngram_max` are configured via `config/app.yaml`'s `retrieval` section (defaults `8`/`3`/`5`), validated by `RetrievalConfig`.
- **One retrieval index = one `SourceType` (frozen V1 rule).** `FactualRetrievalIndex.from_corpus()` requires an explicit `source_type` and rejects (`SourceTypeMismatchError`) any corpus containing a chunk of a different type - a single index can never silently mix student-summary and course-book material. `build_student_summary_retrieval_index()` / `build_course_book_retrieval_index()` are always separate; results are never combined.
- **`RetrievalResult` (`chunk`, `score`, `rank`) is structurally separate from `SourceEvidenceChunk`** - no retrieval metadata was added to the WP-002 chunk model. `score` is a `[0.0, 1.0]` lexical-similarity value only; it is explicitly **not** grounding confidence, factual confidence, or probability of correctness. No API interprets a score threshold as a grounding decision.
- **Zero-score results are never returned** (a tiny `1e-9` floating-point tolerance around true zero is used, not a meaningful similarity threshold - see `exam_generator.retrieval.index`); a query with no lexical overlap returns an empty result sequence rather than being padded to `top_k`.
- **Deterministic tie-breaking**: results are ordered by score descending, then original corpus position ascending, for reproducible ordering when scores are equal. No random tie-breaking.
- **Canonical categories always originate from `HistoricalQuestionRepository.canonical_categories`** (WP-003) - never duplicated as constants/YAML lists. `config/category_mapping.yaml` (`mapping: {alias: canonical_category}`, WP-001 placeholder) is now activated: `CategoryResolver` validates that every alias target is an actual canonical category and that no alias key collides with an existing canonical category name, failing clearly (`InvalidCategoryMappingError`) otherwise. Exact canonical names always resolve to themselves; unknown names fail (`UnknownCategoryError`) - no fuzzy matching, translation, or LLM-based guessing.
- **Canonical category text is the V1 baseline retrieval query** (`retrieve_for_category()`); no query expansion via historical questions, textbook text, or LLM synonyms. `resolve_exam_request_categories()` resolves every requested category (failing on any unknown one), combining counts when multiple requested categories (canonical + alias, or multiple aliases) collapse onto the same canonical category, while preserving the total requested count.
- Historical questions never enter factual retrieval: the historical repository participates in WP-006 only as the source of canonical category names, never as indexed content.
- No retrieval index is persisted; it is rebuilt in memory from the deterministic WP-005 corpus each time.

## LLM Boundary
Application logic uses an LLM abstraction/factory rather than provider SDK calls directly.

Target conceptual interface:
- provider-neutral client/interface
- OpenAI implementation initially
- future provider implementations can be added without redesigning generation/orchestration

Provider, model, and generation/validation parameters are external configuration.

### LLM Abstraction and OpenAI Provider (WP-007)
`src/exam_generator/llm/` (`errors.py`, `models.py`, `provider.py`, `factory.py`, `openai_provider.py`) implements this boundary concretely.

- **`LLMProvider`** (abstract base class) exposes `generate_structured(*, messages, response_model, profile) -> response_model instance`, `provider_name`, `model_name`. Only `openai_provider.py` imports the `openai` SDK; `models.py`/`provider.py`/`factory.py` are provider-independent and never import it, so a future provider can be added without touching those modules or any caller.
- **Structured output**: uses the OpenAI SDK's Responses API (`client.responses.parse(..., text_format=response_model)`), which returns a validated instance of the caller-supplied Pydantic model directly via `response.output_parsed` - no hand-maintained JSON Schema duplication, no `json.loads` of raw prose. Any arbitrary caller-supplied Pydantic model works; the provider never hard-codes a specific response model.
- **`LLMMessage`** (`role` ∈ `{system, user, assistant}`, non-blank `content`) is the provider-independent message contract; OpenAI SDK message/input types are never exposed to callers. **`LLMProfile`** (`GENERATION`, `VALIDATION`) selects the matching `config/llm.yaml` parameter section - generation and validation parameters can never be accidentally interchanged.
- **Provider construction**: `build_llm_provider(llm_config, api_key=None)` is a factory keyed on `llm_config.provider`; only `"openai"` is supported in V1, anything else fails clearly (`LLMConfigurationError`) rather than silently falling back. `OPENAI_API_KEY` is read from the environment only at provider-construction time, never during ordinary configuration loading (preserving the WP-001 decision that config loading never requires a key) and never accepted via `config/llm.yaml` or any committed file.
- **Retry policy (frozen V1 decision, refined WP-020)**: the OpenAI client is constructed with `max_retries=0`, disabling the SDK's default transport-level retries. One `generate_structured()` call = exactly one logical application LLM call/result; generation-attempt/quality-regeneration/diversity control happens entirely outside the provider, with no hidden SDK-level retries to confuse attempt accounting. Since WP-020, one logical call may involve up to `1 + structured_output_retries` (default `1`, `config/llm.yaml`) *physical* API calls - narrowly, only when the provider's response text itself could not be parsed as JSON at all (see "Structured-Output Transient Recovery (WP-020)" below) - never a new logical call, never a new candidate-production attempt.
- **Error hierarchy**: `LLMError` → `LLMConfigurationError`, `LLMRequestError` (invalid caller input, e.g. empty messages), `LLMProviderError` (→ `LLMAuthenticationError`, `LLMRateLimitError`), `LLMResponseError` (→ `LLMRefusalError`, `LLMStructuredOutputError` (WP-020)). Expected OpenAI SDK exceptions are translated with the original exception preserved as `__cause__`; secrets never appear in any exception message.
- Structured-output refusals (`content.type == "refusal"` in the Responses API output) are never parsed as if successful; they raise `LLMRefusalError`. A missing/absent parsed object, or a parsed object of the wrong type, raises `LLMResponseError` - the provider never returns `None`/a raw dict/raw text when a response model was requested, and never repairs an invalid parsed result.
- Synchronous V1 API only (no `async`); no production prompts exist yet (WP-008's responsibility) - WP-007 only makes arbitrary structured-output requests possible for later layers.

## Prompt Boundary
Substantial prompts are external files organized by purpose, for example:
- system
- generation (`STYLE_SIMILAR`, `INDEPENDENT`)
- grounding validation
- MCQ quality validation
- category validation
- textbook check
- ingestion/category classification if required

Python loads/render prompts; prompt content is not embedded as large literals in application logic.

### External Prompt Infrastructure (WP-008)
`src/exam_generator/prompts/` (`errors.py`, `models.py`, `repository.py`, `renderer.py`, `formatting.py`, `context.py`) implements this boundary concretely, loading and rendering the seven production prompt files under `prompts/` (`system/exam_generator.txt`, `generation/question.txt`, `validation/{grounding,mcq,category,quality,textbook}.txt`).

- **Prompt files are plain UTF-8 text with named `{placeholder}` syntax** - Python's standard-library `str.format()`/`string.Formatter` mechanism, not Jinja2/Mustache/a YAML or JSON prompt DSL. No new production dependency was introduced. `{{`/`}}` is the standard-library literal-brace escape. Only plain named fields are supported; positional/numbered fields (`{0}`, `{}`), attribute/index access (`{x.y}`, `{x[0]}`), conversion syntax (`{x!r}`), and format specs (`{x:>10}`) are all rejected as malformed template syntax (`PromptTemplateError`) - the template system is deliberately static-text-plus-named-placeholders only.
- **`PromptId`** (str enum: `SYSTEM`, `QUESTION_GENERATION`, `GROUNDING_VALIDATION`, `MCQ_VALIDATION`, `CATEGORY_VALIDATION`, `QUALITY_VALIDATION`, `TEXTBOOK_VALIDATION`) is the only prompt identity application code may use; the `PromptId` → filesystem path mapping is private to `repository.py`.
- **`PromptRepository.from_directory(path)` / `.from_default_location()`** load, validate, and hash every required prompt file up front at construction time (fail closed on a missing/empty/whitespace-only/malformed file) and return read-only `PromptTemplate` instances (`prompt_id`, `text`, `required_variables`, `version`) via `.get(prompt_id)`. `required_variables` is always derived from the template's actual placeholders (`string.Formatter().parse()`), never a second hand-maintained list. `.from_default_location()` resolves `config/app.yaml`'s existing `paths.prompts_dir` relative to the project root - no new configuration was added.
- **Prompt version identity**: SHA-256 hex digest of the exact prompt file's raw bytes (read via `Path.read_bytes()`, not text-mode, so the hash is unaffected by newline translation). Content identity/audit metadata only, not a security mechanism.
- **Strict rendering (`render_prompt(template, **variables)`)**: the supplied variable set must equal `required_variables` exactly - a missing or an unexpected variable both raise `PromptRenderError` rather than silently substituting an empty string or ignoring an extra value. Rendering performs exactly one `str.format()` substitution pass; substituted values are never re-parsed for placeholder syntax, so evidence/reference text containing brace-like or placeholder-like substrings is preserved as inert data.
- **`build_prompt_messages(*, system_template, task_template, variables)`** renders the shared system prompt (no variables) and one task prompt (with `variables`) into the normal `(SYSTEM LLMMessage, USER LLMMessage)` pair, reusing WP-007's `LLMMessage`/`MessageRole` directly - no competing message model. Nothing in `exam_generator.prompts` imports the OpenAI SDK or calls `LLMProvider.generate_structured()`.
- **Source-role delimiting**: `formatting.py` wraps already-selected `SourceEvidenceChunk`/`HistoricalStyleReference` objects in explicit `--- BEGIN ... ---` / `--- END ... ---` markers before they are ever substituted into a template - `format_student_summary_evidence()` (mandatory, ≥1 chunk, labeled AUTHORITATIVE), `format_course_book_evidence()` (may legitimately be empty, labeled SECONDARY - NOT PRIMARY GROUNDING), `format_historical_reference()` (labeled NOT FACTUAL EVIDENCE; `None` renders an explicit "no reference supplied" sentinel rather than fabricating one). Each formatter also rejects a chunk of the wrong `SourceType` (`PromptContextError`), so student-summary and course-book evidence can never be silently cross-labeled. Caller-supplied chunk/reference order is always preserved; nothing in this module retrieves, ranks, or selects. The shared system prompt instructs the model that text inside any delimited section is data, not instructions.
- **`GenerationPromptContext`/`GroundingPromptContext`** (frozen dataclasses) are the only prompt-context value objects introduced; they exist solely to make an invalid prompt construction impossible before rendering - `GenerationPromptContext` enforces that `STYLE_SIMILAR` requires a `historical_reference` and `INDEPENDENT` must not be supplied one, and that `category`/`source_evidence` are non-blank/non-empty. `.render_variables()` on each produces exactly the variable set its production prompt requires. No other validation prompt (MCQ/category/quality/textbook) needed a dedicated context object; their inputs are supplied directly to `render_prompt()` using the shared formatting helpers.
- **Production prompt content**: the generation prompt requires Hebrew question/answer text (Latin anatomical terminology allowed inline), exactly four answer choices, one correct answer using the existing 1-based convention, and states student-summary evidence as the sole factual authority for generation (course-book evidence is not supplied to the generation prompt at all in V1). The grounding validation prompt requires independent evaluation, explicitly states that the generator's own evidence claims are never proof, and aligns its requested fields with `GroundingValidationResult`. The textbook validation prompt states the secondary-authority rule explicitly (cannot ground independently, cannot replace missing student-summary grounding) and aligns its three possible outcomes with `TextbookCheckStatus`. All five validation prompts remain separate files/identities - no single "validate everything" prompt.

No embeddings, vector databases, question generation, validation *behavior*, orchestration, or an LLM call of any kind was introduced by this WP; `exam_generator.prompts` only loads, validates, formats, and renders - it never invokes `LLMProvider.generate_structured()`.

## Question Generation (WP-009)
`src/exam_generator/generation/` (`errors.py`, `generator.py`) implements the first real generation path, wiring together WP-006 retrieval, WP-003 historical data, WP-008 prompt infrastructure, and WP-007's LLM abstraction into one `QuestionGenerator.generate_candidate_question(*, category, generation_mode) -> CandidateQuestion` call. Generation only - the returned candidate is not independently validated.

- **LLM-response -> domain-candidate boundary**: the LLM never populates `CandidateQuestion` directly. It is asked for a new, WP-002-adjacent `GeneratedQuestionResponse` (`question`, `answers`, `correct_answer`, `evidence_chunk_ids`, `historical_reference_id`) via `LLMProvider.generate_structured(response_model=GeneratedQuestionResponse, profile=LLMProfile.GENERATION)`. This response model deliberately excludes `category`/`generation_mode` - both are supplied by the caller's request, not something the LLM is asked to invent, and are assigned onto `CandidateQuestion` directly from the resolved request context. `evidence_chunk_ids`/`historical_reference_id` are the model's *claimed* provenance only; `_validate_generated_provenance()` rejects (`InvalidGeneratedOutputError`) any claimed evidence chunk id not present in the chunks actually retrieved, and any claimed historical-reference id that does not match the reference actually supplied (or any historical-reference id at all under `INDEPENDENT`, where none was supplied). A rejected claim fails the whole generation call - it is never silently dropped or corrected.
- **Deterministic historical-reference selection (`STYLE_SIMILAR` only, V1 policy)**: the first historical question for the canonical category in workbook order (`HistoricalQuestionRepository.questions_for_category(category)[0]`) - no randomness, no diversity/retry awareness (deferred to WP-013). No suitable reference for the category fails clearly (`MissingHistoricalReferenceError`); generation never silently falls back to `INDEPENDENT`.
- **Generation flow / fail-before-LLM-call ordering**: resolve category -> retrieve student-summary evidence (fail closed with `MissingEvidenceError` if empty, before any LLM call) -> select historical reference if `STYLE_SIMILAR` (fail closed with `MissingHistoricalReferenceError` before any LLM call) -> build the WP-008 `GenerationPromptContext`/prompt messages -> exactly one `generate_structured()` call -> validate claimed provenance -> construct `CandidateQuestion`. No course-book retrieval, and no grounding/MCQ/category/quality/textbook validation, occurs anywhere in this path.
- **One-call, no-retry generation semantics (frozen V1 decision, mirrors WP-007's provider-level `max_retries=0`)**: `QuestionGenerator.generate_candidate_question()` makes exactly one semantic LLM call per invocation. Any retry/diversity/multi-attempt policy belongs entirely to WP-013 and is not present here.
- All dependencies (`CategoryResolver`, `FactualRetrievalIndex`, `HistoricalQuestionRepository`, `PromptRepository`, `LLMProvider`) are injected explicitly through `QuestionGenerator.__init__`; `QuestionGenerator.from_default_configuration()` wires the normal real-project configuration (and is the only path that requires `OPENAI_API_KEY`).

**Evidence-identifier fidelity (discovered/fixed in WP-010, applies to this prompt too)**: the live smoke test found the model sometimes drops a `SourceType` chunk id's prefix (e.g. reports `student_summary_2.pdf:0008:0001` instead of the real `STUDENT_SUMMARY:student_summary_2.pdf:0008:0001`) when citing `evidence_chunk_ids`, which WP-009's provenance check then correctly rejects as an invented id. `prompts/generation/question.txt` was updated to instruct the model to copy each identifier's full "Chunk:" line value character-for-character, including everything around any colon - this fixed the issue in live testing. See "Independent Grounding Validation (WP-010)" below for the parallel fix to the grounding prompt.

## Independent Grounding Validation (WP-010)
`src/exam_generator/validation/` (`errors.py`, `grounding.py`) implements the first independent check on a WP-009 `CandidateQuestion`: `GroundingValidator.validate_grounding(candidate) -> GroundingValidationResult`. Generation and grounding validation remain fully separate operations - the validator never trusts the generator's own claims.

- **Independent evidence retrieval (frozen V1 query policy)**: the validator never uses any evidence the generator claims to have used. It builds its own deterministic retrieval query - `f"{candidate.category} {candidate.question} {<intended correct answer text>}"` (the three distractors are deliberately excluded, since diluting the query with wrong-answer text would weaken retrieval precision for the one claim that actually needs checking) - and queries the student-summary retrieval index fresh. It is expected and acceptable for this independently retrieved evidence to overlap with what generation used; the invariant is that validation evidence selection is never *derived from* generation's claims.
- **Student-summary-only primary authority**: the validator has no course-book retrieval dependency at all (structurally - there is no constructor parameter for one, mirroring WP-009's `QuestionGenerator`), and reuses WP-008's `format_student_summary_evidence()` (via `GroundingPromptContext`) which itself rejects a wrong-`SourceType` chunk. A `STYLE_SIMILAR` candidate's historical reference is never supplied to the validator at all - `GroundingPromptContext`/`validate_grounding()` have no historical-reference parameter, so there is nothing for a historical reference to be smuggled in through. Generation mode does not change the grounding standard applied.
- **Grounding provenance verification**: `GroundingValidationResult.evidence_chunk_ids` returned by the LLM is checked against the actual validation-evidence chunk ids; any id not present there raises `InvalidGroundingOutputError` rather than being silently dropped or repaired - mirroring WP-009's `_validate_generated_provenance()` pattern exactly.
- **Negative verdict vs. operational failure (a core WP-010 rule)**: `GroundingValidationResult(passed=False, ...)` is a normal, successful return value - never converted to/from an exception. Empty independent retrieval fails closed *before* any LLM call (`NoValidationEvidenceError`); a provider/LLM failure during the call propagates as-is (e.g. `LLMProviderError`) and is never caught and reinterpreted as a failed grounding verdict.
- **One-call, no-retry validation semantics**: exactly one `LLMProfile.VALIDATION` call per `validate_grounding()` invocation, matching WP-009's generation semantics. Retry/regeneration-on-failure is explicitly WP-013's job.
- **Evidence-identifier fidelity fix**: `prompts/validation/grounding.txt`'s `evidence_chunk_ids` field description was updated identically to the WP-009 generation-prompt fix above (copy the full "Chunk:" line verbatim) - the same live-observed model behavior affected both prompts. This is the second production-prompt content change WP-010 made; both were made only because a live call exposed a reproducible, verifiable defect (the exact exception this project's "don't tune prompts speculatively" rule allows), and both were confirmed fixed by a subsequent successful live call.

## MCQ, Category, and Quality Validation (WP-011)
`src/exam_generator/validation/` (`mcq.py`, `category.py`, `quality.py`) implements the three remaining primary candidate-quality validators, sibling to WP-010's `GroundingValidator`: `MCQValidator.validate(candidate) -> MCQValidationResult`, `CategoryValidator.validate(candidate) -> CategoryValidationResult`, `QualityValidator.validate(candidate) -> QualityValidationResult`. Each is a small, focused, independently-constructible class (`from_default_configuration()` classmethod, explicit injected `prompt_repository`/`llm_provider` otherwise) - no generic validator framework/base class was introduced, per the WP's explicit preference for three small explicit validators over an abstraction that would obscure their different responsibilities.

- **No retrieval of any kind**: none of the three validators has a retrieval-index constructor parameter (structurally, mirroring WP-009/WP-010's identical pattern), and none of the three prompts (`mcq.txt`, `category.txt`, `quality.txt`) references course-book/student-summary evidence or historical questions. Each operates purely on the candidate's own already-known content, formatted via WP-008's existing `format_candidate_question()` - no new prompt-context value object was introduced for these three (matching WP-008's own explicit decision not to add one, since none of the three has an invalid-combination invariant analogous to `GenerationPromptContext`'s mode/reference rule); each validator builds its small, fixed variable dict inline instead.
- **Category validation supplies only the candidate's own canonical category** (`candidate.category`, rendered as the prompt's `expected_category` variable) - never a resolver, never an alias table. `CategoryValidator` has no dependency capable of alias resolution or reclassification; it judges the supplied category/question pairing exactly as WP-011 requires, structurally unable to retrieve or substitute a different canonical category.
- **Independence of verdicts (a core WP-011 rule)**: no validator's constructor or `validate()` call takes another validator's result as input, and no validator invokes another validator's prompt - each of the four candidate-quality prompts (`grounding`, `mcq`, `category`, `quality`) is requested by exactly one corresponding validator. This makes diagnostics such as `Grounding PASS / MCQ FAIL / Category PASS / Quality FAIL` directly representable, rather than collapsing to one opaque `valid=false`. Later orchestration (a future WP) decides which combination of these four independent results a candidate must satisfy to be accepted.
- **Negative verdict vs. operational failure**: identical to WP-010's rule - `valid=False`/`MCQValidationResult`/`CategoryValidationResult`/`QualityValidationResult` are normal, successful return values; a provider/LLM/structured-output failure propagates as-is (e.g. `LLMProviderError`) and is never caught and reinterpreted as a negative verdict.
- **One-call, no-retry semantics**: exactly one `LLMProfile.VALIDATION` call per `validate()` invocation for each of the three validators, matching WP-009/WP-010's identical semantics. Retry/regeneration-on-failure remains a later WP's job.
- No production prompt content was changed for WP-011 - the live smoke test (see below) produced informative negative verdicts rather than exposing a prompt-contract defect, so per this project's "don't tune prompts speculatively" rule, nothing was changed.

## Secondary Textbook Consistency Validation (WP-012)
`src/exam_generator/validation/textbook.py` implements `TextbookValidator.validate(candidate) -> TextbookCheckResult`, a secondary, non-authoritative check independent of all four WP-010/WP-011 validators.

- **Authority boundary (the central WP-012 rule)**: student summaries remain the sole primary factual-grounding authority; course-book evidence is secondary corroboration/conflict-surfacing only, for audit purposes. `TextbookValidator` never reads, constructs, or modifies a `GroundingValidationResult`, and has no dependency capable of doing so - a `Grounding FAIL` / `Textbook CONSISTENT` combination (or the reverse) is fully representable and never reconciled by this validator. `prompts/validation/textbook.txt` (WP-008, unmodified) already states this boundary explicitly to the model.
- **Independent course-book-only retrieval (V1 query policy, identical in shape to WP-010)**: `f"{candidate.category} {candidate.question} {<intended correct answer text>}"` (distractors excluded) queried against `build_course_book_retrieval_index()` - never the student-summary index. `TextbookValidator.__init__` has a `course_book_index` parameter and structurally no `student_summary_index`/historical-reference parameter of any kind, mirroring `GroundingValidator`'s identical no-course-book-parameter guarantee in the opposite direction.
- **Empty retrieval is not an operational failure (differs from WP-010 by design)**: student-summary grounding is mandatory, so `GroundingValidator` fails closed (`NoValidationEvidenceError`) when retrieval is empty. Course-book coverage is optional secondary material, so when independent course-book retrieval returns nothing, `TextbookValidator` returns `TextbookCheckResult(status=NOT_FOUND, ...)` directly **without making an LLM call at all** - there is nothing for a model to judge against, and `TextbookCheckStatus.NOT_FOUND` (which the WP-008 prompt already defines as covering "insufficient, absent, or unclear" evidence) represents this precisely with the existing WP-002 contract, unmodified. This is why `validate()` makes *at most* one `LLMProfile.VALIDATION` call, not *exactly* one.
- **Verdict semantics reuse the existing `TextbookCheckResult`/`TextbookCheckStatus` contract unchanged**: `CONSISTENT` (supports), `POTENTIAL_CONFLICT` (contradicts), `NOT_FOUND` (insufficient/absent/unclear - covers both "retrieval found nothing" and "the LLM judged the retrieved evidence insufficient"). No new status/field was added; WP-012 did not need to redesign this contract.
- **Provenance verification**: unlike `GroundingValidationResult` (a `list[str]` of chunk ids), `TextbookCheckResult` carries at most one `source_page` (int) and one `reference_text` (str) - there is no chunk-id list to check. `_validate_textbook_provenance()` therefore verifies, independently and only when the corresponding field is non-`None`: `source_page` must equal the page of at least one independently-retrieved course-book chunk actually supplied to the LLM call, and `reference_text` must appear verbatim as a substring of at least one supplied chunk's text. Either mismatch raises `InvalidTextbookOutputError` - never silently dropped or corrected - mirroring WP-009's/WP-010's identical provenance-rejection pattern, adapted to this contract's actual fields rather than an invented chunk-id list that does not exist on the model.
- **No other validator is invoked**: `TextbookValidator` has no dependency on `GroundingValidator`/`MCQValidator`/`CategoryValidator`/`QualityValidator`, and calls no prompt but `PromptId.TEXTBOOK_VALIDATION` (plus the shared system prompt). This is the fifth and final independent primary/secondary validation result; combining them into an acceptance policy remains explicitly out of scope (a later control-layer WP's job).
- No production prompt content was changed during WP-012 itself - that WP's own live smoke test produced an informative `NOT_FOUND` verdict rather than exposing a prompt-contract defect. `prompts/validation/textbook.txt` *was* later modified during WP-013's live smoke test, for an unrelated reference-text-fidelity reason - see "Live-Test-Driven Textbook Prompt Fix (WP-013)" below.

## Single-Question Production Control Layer (WP-013)
`src/exam_generator/production/` (`errors.py`, `models.py`, `producer.py`) implements the control layer that turns WP-009 generation and the five WP-010/WP-011/WP-012 validators into a reliable single-question production cycle: `QuestionProducer.produce_question(*, category, generation_mode) -> QuestionProductionResult`.

- **Acceptance is deterministic Python policy, never an LLM decision (the central WP-013 rule)**: `CandidateValidationResults.accepted` is a plain boolean expression over the five existing, unmodified validator result models - `grounding.passed AND mcq.valid AND category.valid AND quality.valid AND textbook.status != POTENTIAL_CONFLICT`. No LLM is ever asked "should this be accepted"; `producer.py` contains no `LLMProvider`/`generate_structured` reference of any kind - it only calls the already-independent generator and validators and combines their results in plain Python.
- **Primary vs. secondary validators, exactly per WP-012's own established rule**: grounding, MCQ, category, and quality are primary and must all pass (`.passed`/`.valid`). The textbook check is secondary: `CONSISTENT` and `NOT_FOUND` never block acceptance (an absent/insufficient textbook check does not invalidate an otherwise properly grounded candidate), but an explicit `POTENTIAL_CONFLICT` does block it. No weighted score or confidence threshold is used anywhere in this policy.
- **Complete validation for diagnostics**: `_validate_candidate()` always runs all five validators, in the fixed order grounding -> MCQ -> category -> quality -> textbook, for every successfully generated candidate - never short-circuited after the first negative verdict. This makes combinations such as `Grounding FAIL / MCQ FAIL / Category PASS / Quality FAIL` fully observable per attempt, which is more diagnostically useful than recording only the first failure.
- **Bounded, quality-driven regeneration reuses the existing WP-001 `generation.max_generation_attempts` config value** (`config/app.yaml`, already `GenerationBehaviorConfig.max_generation_attempts: Field(gt=0)`, default `3`) - no new configuration was introduced. `QuestionProducer.__init__` additionally validates any directly-injected `max_attempts` itself (`InvalidProductionConfigurationError` if not a plain int `>= 1`), so the invariant holds even for test-constructed instances that bypass config loading.
- **Attempt semantics**: one attempt = one `generate_candidate_question()` call + its full five-validator cycle. `produce_question()` stops at the first accepted candidate; every completed attempt (accepted or not) is preserved as an immutable `QuestionAttempt` (`attempt_number` 1-based, `candidate`, `validations`, and a derived `.accepted` property - never a caller-suppliable field, so it can never drift out of sync with `validations.accepted`). A successful cycle returns `QuestionProductionResult(candidate, attempts)` with the full attempt history, not just the final candidate.
- **Exhaustion is a normal, expected outcome, not a bug**: if every attempt is rejected, `QuestionAttemptsExhaustedError` is raised carrying every completed `QuestionAttempt` (`.attempts`) for diagnostics. The last rejected candidate is never returned as though accepted, and acceptance criteria are never relaxed on the final attempt.
- **Operational failure vs. quality rejection remains structurally distinct, by simply not catching anything**: `produce_question()` has no `try`/`except` around generation or validation at all - a `passed=False`/`valid=False`/`POTENTIAL_CONFLICT` result is a normal attempt outcome that may trigger regeneration, while an operational failure (`LLMProviderError`, an invalid structured response, a retrieval/prompt-infrastructure error) propagates immediately out of `produce_question()`, consuming no further attempts. `max_attempts` bounds candidate-quality regeneration only, never API resilience.
- **`category`/`generation_mode` are held fixed across every attempt** - the same two arguments are passed to `generate_candidate_question()` on every loop iteration; nothing here ever switches generation mode or category after a rejection.
- **Regeneration for WP-013 is the plain existing WP-009 generation path called again with the same inputs** - no validator-feedback prompting, no dynamic "your previous answer failed because..." prompt rewriting, and no historical-reference-selection redesign (WP-009's deterministic first-in-category selection is unchanged, so repeated `STYLE_SIMILAR` attempts may reuse the same historical reference - acceptable for this control-layer baseline per the WP).
- **No exam-level diversity/orchestration**: `QuestionProducer` operates on exactly one question per `produce_question()` call; semantic uniqueness, duplicate detection, answer-position balancing, historical-reference rotation, and category-distribution orchestration across multiple questions are all explicitly out of scope, deferred to exam orchestration.

### Live-Test-Driven Textbook Prompt Fix (WP-013)
The WP-013 live smoke test's initial run surfaced a reproducible defect in `prompts/validation/textbook.txt` (WP-008/WP-012, unmodified until now): when the model reported a `reference_text`, it sometimes paraphrased/summarized course-book content instead of quoting it verbatim, which WP-012's own provenance check (`_validate_textbook_provenance()`) then correctly rejected as unverifiable (`InvalidTextbookOutputError`) - reproduced directly against a fixed, real, non-empty retrieved evidence set. This mirrors WP-010's `evidence_chunk_ids`-fidelity precedent exactly: the prompt already warned against inventing evidence but did not explicitly require verbatim, character-for-character copying. `prompts/validation/textbook.txt` was updated (with explicit user approval, since it is an already-shipped file) to require `source_page` to exactly match a supplied evidence item's `Page:` value, and `reference_text` to be a contiguous, character-for-character excerpt of that item's `Text:` content - or left empty if no exact quote is available - never paraphrased, translated, or reconstructed from memory. New version hash prefix: `de8e3f35c8b6fd2c`. No other prompt content, requirement, or policy was changed.

## Exam Orchestration (WP-014)
`src/exam_generator/orchestration/` (`errors.py`, `models.py`, `orchestrator.py`) implements the layer that turns a complete `ExamRequest` into a complete `ExamOutput`: `ExamOrchestrator.generate_exam(request) -> ExamGenerationResult`, invoking WP-013's `QuestionProducer` once per requested question.

- **Category/count resolution is entirely reused from WP-006, not reimplemented**: `resolve_exam_request_categories(request, resolver)` (unchanged) performs alias resolution and count-combination before any plan is built; `ExamOrchestrator` has no alias-handling logic of its own.
- **Deterministic question plan (`build_exam_plan()`, a pure function)**: for an already-canonicalized `ExamRequest`, produces an immutable `tuple[PlannedQuestion, ...]` - each entry a global 1-based `position`, its canonical `category`, and its assigned `generation_mode`. Identical input always produces an identical plan.
- **Generation-mode allocation follows the master brief's established policy verbatim** ("Questions alternate between two modes within each category") - `STYLE_SIMILAR`/`INDEPENDENT` alternate starting at `STYLE_SIMILAR` for each category's *own* first question (the alternation restarts per category rather than carrying a single running parity across the whole exam), since the brief's wording is explicitly scoped "within each category." No ratio/percentage was invented - the brief specifies simple alternation, not a proportion.
- **Category-count preservation is a hard invariant, never load-balanced across categories**: the plan contains exactly the canonicalized requested count for each category, and a production failure in one category never causes another category to over-produce to compensate. `ExamOutput.questions`'s existing WP-002 contiguous-1..N-numbering validator, combined with `position` being assigned directly as `ExamQuestion.number`, structurally guarantees the final question count and ordering match the plan exactly.
- **WP-013's `QuestionProducer` is invoked exactly once per planned question (twice or more only under bounded duplicate replacement - see below), and is never duplicated**: all generation, all five validators, acceptance policy, and per-question bounded quality regeneration remain entirely inside `QuestionProducer.produce_question()`. `orchestrator.py` contains no `LLMProvider`/`generate_structured` reference of any kind, matching `producer.py`'s own identical guarantee from WP-013.
- **Exam-level failure is immediate and preserves diagnostic context, never a silently partial exam**: if `QuestionProducer` raises `QuestionAttemptsExhaustedError` for any planned question, `ExamOrchestrator` raises `QuestionProductionFailedError` (its own distinct error, not a re-raise) carrying `planned_question` (the failing plan entry), `completed_productions` (every question already successfully accepted before this failure), and `attempts_exhausted` (the underlying `QuestionAttemptsExhaustedError.attempts`). No `ExamGenerationResult`/`ExamOutput` is ever constructed for a partial exam.
- **Candidate -> clean conversion reuses WP-002's `candidate_to_exam_question(candidate, number)` unmodified** - `ExamOrchestrator` never hand-assembles an `ExamQuestion`. `number` is always the plan's `position`, so exam ordering is exactly plan order (WP-014's own explicitly simplest V1 ordering rule - no shuffling).
- **Exact-duplicate protection (deterministic, non-semantic, per WP-014's explicit scope)**: `_normalize_question_text()` collapses all whitespace runs (which also trims leading/trailing whitespace) and case-folds a candidate's question text; a normalized match against any question already accepted into the current exam is rejected. No embeddings, semantic similarity, or additional LLM call is used for this - `orchestrator.py` contains no such reference.
- **Bounded duplicate replacement is a distinct budget from WP-013's own `max_generation_attempts`, using a new, small configuration value**: `config/app.yaml`'s `generation.max_duplicate_replacement_attempts` (new `GenerationBehaviorConfig` field, `Field(gt=0)`, default `2`) bounds how many *additional* `produce_question()` calls the orchestrator may make for one planned question after an accepted-but-duplicate result, before giving up. `ExamOrchestrator.__init__` also validates any directly-injected value itself (`InvalidOrchestrationConfigurationError` if not an int `>= 1`), mirroring `QuestionProducer`'s identical WP-013 pattern. `max_generation_attempts` (WP-013) governs *quality* regeneration entirely inside one `produce_question()` call and is never touched by duplicate-replacement logic.
- **Duplicate replacement always reuses the same planned question's category/generation_mode** - the retry loop calls `produce_question()` with the identical `planned.category`/`planned.generation_mode` on every replacement attempt; nothing about a planned question's specification changes because a duplicate was rejected.
- **Duplicate-replacement exhaustion is a normal orchestration-level failure, not an operational one**: if every replacement attempt (including the first) also duplicates an already-accepted question, `QuestionProductionFailedError` is raised with `duplicate_productions` populated (every rejected `QuestionProductionResult` for that planned question) and `attempts_exhausted=None` - the same error class as WP-013-exhaustion failure, distinguished by which optional field is populated, since both represent "this planned question could not be completed" without needing two parallel error hierarchies.
- **Production history is fully retained, not just the final clean exam**: `ExamGenerationResult.productions` is a `tuple[QuestionProductionRecord, ...]`, one per accepted question, each wrapping its `PlannedQuestion`, its full WP-013 `QuestionProductionResult` (accepted candidate + every attempt), and `duplicate_replacement_attempts` (how many replacements this question needed before acceptance). No final audit-model (`QuestionAudit`/`ExamAudit`) assembly happens yet - that remains a later output-focused WP.
- **Sequential, not parallel, question production** - `generate_exam()` is a plain `for` loop over the plan; no concurrency was introduced, per the WP's explicit V1 scope.
- **`CleanQuestion`/`Exam` (the WP's own conceptual names) do not exist as such** - the real, already-established WP-002 contracts are `ExamQuestion`/`ExamOutput`, reused unmodified rather than introducing parallel/duplicate names, per WP-014 section 3's own explicit instruction to preserve established models when they differ from the WP's assumed naming.

### Live-Test-Driven Textbook Prompt Fix #2 (WP-014)
The WP-014 live smoke test's first attempts hit an operational failure distinct from WP-013's: `TextbookCheckResult.reference_text` was returned as an empty string (`""`) rather than omitted, which the existing `NonBlankStr` field type correctly rejects as a pydantic `ValidationError`. The cause was WP-013's own just-added instruction wording ("...leave reference_text empty rather than approximating one") - ambiguous between "omit the field" and "return an empty string," and the model took the literal reading. Fixed (with explicit user approval) by rewording to "omit reference_text entirely (return null, not an empty string)". New version hash prefix: `192b24c66a7bc404`. This is a narrow, mechanical correction of WP-013's own recent wording, not new scope.

Separately, the live smoke test also encountered - and did **not** attempt to fix - two other operational failures typical of this project's already-established strict-provenance-by-design approach: an occasional non-verbatim `reference_text` (the same class of issue the first WP-013 fix targeted, evidently not eliminated to 100% reliability by that fix - see Known Issues) and, once, an invented `evidence_chunk_ids` value from the WP-009 generator (the same class of issue WP-010 fixed once already, for a different specific wording symptom). Both are exactly the kind of operational failure WP-013/WP-014 are explicitly designed to propagate rather than mask, and neither was judged to have an obvious, narrow, mechanical wording defect the way the two fixed issues did - see "Known Issues" in `docs/PROJECT_STATUS.md` for the honest accounting rather than further speculative prompt changes.

## Exam Output and Audit Trail (WP-015)
`src/exam_generator/output/` (`errors.py`, `models.py`, `audit.py`, `bundle.py`, `serialization.py`) implements the final output boundary: a deterministic, zero-LLM-call transformation from a successful WP-014 `ExamGenerationResult` into the two separate WP-002 output contracts. Public entry points: `build_exam_audit(generation_result, *, exam_id, generated_at, llm_config, diversity_target) -> ExamAudit`, `build_exam_output_bundle(...) -> ExamOutputBundle` (pairs the audit with `generation_result.exam` unchanged), and `serialize_exam_json()`/`serialize_audit_json()`/`write_exam_json()`/`write_audit_json()`.

- **Clean exam vs. audit remain structurally separate, never merged**: `ExamOutputBundle(exam: ExamOutput, audit: ExamAudit)` associates them without combining them into one model. The clean exam is `generation_result.exam` itself, reused unmodified (WP-014 already built it correctly) - this layer never rebuilds or hand-assembles an `ExamQuestion`. `ExamQuestion`'s own WP-002 schema structurally has no field capable of holding validation/evidence/generation-mode metadata, so "no internal metadata in the clean exam" is a schema-level guarantee, not a policy this layer has to enforce by convention.
- **`QuestionAudit` gained one new field, `attempts: list[QuestionAttemptAudit]` (min length 1)** - the smallest justified extension to the existing WP-002 contract (per WP-015 section 4), since the pre-existing single `grounding`/`mcq_validation`/`category_validation`/`quality_validation`/`textbook_check` fields could only represent one (the final/accepted) result, not WP-013's full per-attempt history. Those pre-existing fields are unchanged in meaning - they continue to mirror the *final accepted* attempt's results; `attempts` now additionally preserves every attempt (including rejected ones) in order, each with its own five validation results and `accepted` flag. `QuestionAttemptAudit` is a new sibling model in `models/audit.py`, not a new top-level package - keeping the audit contract in one place.
- **Two genuine provenance gaps are represented as honest absence, never fabricated (WP-015 section 9)**: `QuestionAudit.historical_reference_id` is always `None` in WP-015's construction, and `evidence` is always `[]`. Neither is derivable from current production history without a deeper architectural change to already-shipped WP-009/WP-010/WP-012 components (`QuestionGenerator` validates then discards any claimed `historical_reference_id` rather than persisting it onto `CandidateQuestion`, by WP-009's own explicit design; none of `QuestionGenerator`/`GroundingValidator`/`TextbookValidator` return the raw `SourceEvidenceChunk` objects they internally retrieve). Both fields already permit absence in the pre-existing WP-002 contract (`| None` / `default_factory=list`), so representing them as empty is honest, not a workaround. This was a deliberate choice over the WP's alternative-sanctioned path ("make the smallest architectural addition ... to capture them at execution time") because that alternative would mean threading new return values through `QuestionGenerator`, `GroundingValidator`, `TextbookValidator`, and every WP-013/WP-014 model built on top of them - exactly the "broad refactoring of previous WPs" WP-015 section 10 explicitly discourages, for two fields whose absence the existing contract already tolerates.
- **Grounding-evidence *identity* is not actually lost, just not duplicated at the top level**: `GroundingValidationResult.evidence_chunk_ids`/`.evidence_text` (already part of WP-010's contract) are preserved intact inside every attempt's nested `grounding` result (`attempts[i].grounding.evidence_chunk_ids`). This is the generation-evidence/grounding-evidence/textbook-evidence source-role separation WP-015 section 8 requires - each validator's own result stays nested under its own name rather than being merged into one generic `sources` list, so the distinction is structural, not by convention.
- **Model/provider provenance is read from `LLMConfig` (plain configuration data), never from a live `LLMProvider`**: `build_exam_audit()`'s `llm_config: LLMConfig` parameter supplies `ExamAudit.provider`/`.model` directly from `LLMConfig.provider`/`.model`. `load_llm_config()` (WP-001) deliberately does not require `OPENAI_API_KEY`, so this layer can build a complete audit - including provider/model metadata - with zero API key and zero LLM/provider object ever constructed or serialized. Prompt-version/hash provenance (WP-015 section 10) was investigated and found genuinely unavailable from current production history (no validator/generator call site returns which `PromptTemplate.version` it used); since `QuestionAudit`/`ExamAudit` have no existing field requiring it, nothing was fabricated or newly added for it - documented as a known gap, not implemented.
- **`build_exam_audit()` is a pure function: every input beyond `generation_result` is caller-supplied** (`exam_id`, `generated_at`, `llm_config`, `diversity_target`) rather than invented internally (no `datetime.now()`, no random ID generation, no internal config loading) - identical inputs always produce an identical `ExamAudit`. `diversity_target` is populated from whatever the caller supplies (typically `config/app.yaml`'s `generation.initial_diversity_target`, the configured value - honest since no dynamic relaxation logic exists yet, per the pre-existing "Decisions Made (WP-014)" note on those same placeholder fields) rather than a value this layer invents.
- **Cross-consistency is verified deterministically inside `build_exam_audit()`, failing closed (`AuditConsistencyError`) rather than silently repairing a mismatch**: question count, question number/category/text/answers/correct-answer correspondence between `generation_result.exam` and the constructed audit, and that every audit question's underlying final production attempt is actually marked `accepted` - a rejected candidate can structurally never be represented as a completed exam question. Under normal use (an `ExamGenerationResult` produced by `ExamOrchestrator.generate_exam()`, never hand-modified) this always passes; the check exists to catch a genuinely tampered/malformed result.
- **Serialization uses pydantic's own `model_dump_json()` exclusively** - no hand-built recursive JSON conversion. Confirmed: non-ASCII (Hebrew) text is preserved unescaped by default (no `\uXXXX`), enums serialize to their plain string value, `datetime` to ISO-8601. `write_exam_json()`/`write_audit_json()` write to exactly the caller-supplied path (UTF-8) and nowhere else - no timestamp/random-filename policy, no directory scanning, matching WP-015's explicit "keep file-system concerns minimal" instruction; filename/timestamp policy remains WP-016 CLI's job.
- **Zero LLM calls, structurally**: no module in `exam_generator.output` imports `exam_generator.llm` or references `LLMProvider`/`generate_structured` at all - the entire layer operates only on already-produced, already-validated data plus caller-supplied plain metadata.
- **Failed/exhausted `ExamGenerationResult`s are out of scope, per WP-015 section 16** - `QuestionProductionFailedError` (WP-014) already carries fully structured, directly-inspectable diagnostics (`planned_question`, `completed_productions`, `attempts_exhausted`/`duplicate_productions`) via existing pydantic models; no dedicated WP-015 serialization function was added for the failure path, since one is not needed to make that data inspectable and the WP explicitly warns against broadening this WP into "a general exception-reporting framework."

## CLI and Application Entry Point (WP-016)
`src/exam_generator/cli.py` implements the single command-line adapter around the already-complete pipeline: `exam-generator generate --request <path> [--exam-output <path>] [--audit-output <path>] [--force]` (installed console entry point, `pyproject.toml`'s `[project.scripts]`; also runnable as `python -m exam_generator.cli generate ...` without installing).

- **The CLI is strictly a thin adapter, never a second orchestration layer**: `main()`/`_run_generate()` parse arguments, read/validate the request file into the existing `ExamRequest` (via `ExamRequest.model_validate()` - no hand-rolled duplicate validation), call `ExamOrchestrator.from_default_configuration()` and `.generate_exam(request)` unchanged, then `build_exam_output_bundle()` and `serialize_exam_json()`/`serialize_audit_json()` (all WP-015, unchanged) to produce the two output strings. No new generation, validation, retrieval, acceptance, planning, or duplicate policy is introduced anywhere in this module - `cli.py` contains no logic that could diverge from what `ExamOrchestrator`/WP-015 already do when invoked directly from Python.
- **`OPENAI_API_KEY` comes only from the environment, via the existing `OpenAIProvider`/`build_llm_provider()` resolution path** - the CLI has no `--api-key` argument at all (structurally impossible to supply one on the command line) and never reads/touches the environment variable itself. A missing key surfaces as `LLMConfigurationError`, raised as soon as `ExamOrchestrator.from_default_configuration()` constructs its six internal LLM-backed components - i.e. before any real generation attempt, satisfying "fail clearly before attempting exam generation where practical" without any CLI-specific pre-check. The key is never printed, logged, or serialized into either output file - confirmed by test, and structurally true since no code path in `cli.py` ever holds or references the key's value.
- **Output-file safety**: existing `--exam-output`/`--audit-output` targets are checked *before* calling the orchestrator (cheap, local, and avoids wasting real API calls generating an exam that couldn't ultimately be written) - `CliUsageError` unless `--force` is passed. Both output JSON strings are fully serialized (via WP-015's pure `serialize_exam_json()`/`serialize_audit_json()`) *before* either file is written, so a hypothetical serialization failure in one can never leave the other written alone; each individual file write is atomic (temp file in the same directory + `os.replace()`), so a crash mid-write never leaves a truncated/corrupted target file. Default output paths (`exam.json`/`exam_audit.json` in the current directory) are fixed, non-random, non-timestamped strings, per the WP's explicit instruction - no UUID/timestamp filename policy was introduced.
- **Exit-code policy is a small, fixed three-value scheme**: `0` success; `2` (`EXIT_USAGE_ERROR`) for request/config/output-target problems the user can fix by changing their invocation, request file, or environment (malformed/missing/invalid request JSON, `ConfigError`, `LLMConfigurationError`, `CategoryResolutionError`, existing output without `--force`, output-write `OSError`); `1` (`EXIT_GENERATION_FAILURE`) for everything that only surfaces once real generation/validation is underway (`QuestionAttemptsExhaustedError`, `QuestionProductionFailedError`, `GenerationError`, `GroundingValidationError`, `TextbookValidationError`, `RetrievalError`, `PromptError`, `LLMError` and its provider-failure subclasses, `AuditConsistencyError`). `_classify_error()` implements this as an ordered, most-specific-first `isinstance` mapping (e.g. `LLMConfigurationError` - a subclass of `LLMError` - is checked before the general `LLMError` case) with no wildcard/catch-all branch: an exception type not on the list is deliberately re-raised with its full traceback rather than swallowed, so genuinely unexpected bugs stay visible during development instead of being silently downgraded to a generic CLI error message.
- **Progress reporting is a fixed sequence of coarse stage messages to stdout** ("Loading request...", "Initializing exam generator...", "Generating exam...", "Writing exam output...", "Writing audit output...", "Done.") - no progress bar library, no per-question progress (WP-014's `ExamOrchestrator` exposes no per-question callback/hook, and the WP explicitly forbids refactoring it merely to add one).
- **No CLI-specific configuration surface exists**: application/LLM/category/generation-attempt/duplicate-replacement configuration all continue to come from `config/app.yaml`/`config/llm.yaml`/`config/category_mapping.yaml` via `ExamOrchestrator.from_default_configuration()`'s existing default-construction chain, unchanged; the CLI adds no new settings of its own beyond the four command-line flags directly tied to *this one invocation* (request path, two output paths, force flag).
- **Only one subcommand exists (`generate`)**, implemented via `argparse` subparsers (not Click/Typer - no new dependency was added for a CLI this small, per the WP's own explicit preference for the standard library). No `validate`/`inspect-corpus`/`search`/`show-config` or similar exploratory commands were added, per the WP's explicit "keep the public CLI small" instruction.

## Evaluation Layer (WP-017)
`src/exam_generator/evaluation/` (`errors.py`, `models.py`, `metrics.py`, `runner.py`, `retrieval_fixture.py`, `report.py`) is a read-only observer over the existing, unmodified pipeline - it introduces no new generation/validation/retrieval/acceptance policy, and is never imported by `production`/`orchestration`/`output`/`cli` (a one-way dependency: evaluation depends on the pipeline, never the reverse). `scripts/run_evaluation.py` is the manual, non-pytest driver (mirrors `scripts/smoke_openai.py`'s "not part of the automated suite" status).

- **`CandidateEvaluationRunner` wraps an existing `QuestionProducer`**, calling `produce_question()` once per planned `(category, generation_mode, question_position)` triple from `build_evaluation_plan()` (a local reimplementation of `orchestration.build_exam_plan()`'s alternating-mode policy - deliberately not imported, so evaluation has zero dependency on the orchestration package). Every attempt (accepted or rejected) is recorded as a `CandidateAttemptRecord`; `QuestionAttemptsExhaustedError` is caught and its `.attempts` recorded normally (an exhausted unit is data, not a runner failure). A fixed, explicit tuple of known operational-error types (`KNOWN_OPERATIONAL_ERROR_TYPES` - `LLMError`, `GenerationError`, `GroundingValidationError`, `TextbookValidationError`, `RetrievalError`, `PromptError`, and `pydantic.ValidationError`) is caught and recorded as an `OperationalFailureRecord`, letting the plan continue to the next item; anything not in that tuple propagates, so a genuinely unexpected exception still surfaces rather than being silently absorbed into a report. No operational failure is ever retried.
- **`pydantic.ValidationError` is deliberately included in the known-operational-error tuple** - a live baseline run showed the OpenAI SDK's own structured-output parser can raise it directly (before any project `LLMError` wrapping applies) for a malformed response (observed: an empty-string required `reason` field). Without this, one such response would abort the entire evaluation run rather than being recorded as the operational failure it is - a narrow, explicitly-documented instrumentation fix (WP-017 section 3's own allowance), not a change to any generation/validation/retrieval code.
- **`RetrievalEvaluationRunner` re-derives "expected relevant chunks" fresh, at evaluation time, via literal substring search over the actual corpus being evaluated** - `RetrievalEvalQuery.expected_literal_term` is never a pre-computed/hardcoded chunk-id list. `retrieval_fixture.py`'s ~37 queries were each verified, by direct corpus inspection (not by trusting TF-IDF's own top-ranked result, which would be circular), to have at least one genuine literal match; `RetrievalEvaluationRunner` raises `UngroundedRetrievalQueryError` rather than silently reporting a meaningless "miss" if a fixture entry's term is ever not found at all.
- **`metrics.py` is pure, I/O-free, and independently testable** - every aggregate number (acceptance rate, first-attempt rate, attempts-per-question stats, exhaustion rate, per-validator failure rates, textbook-status distribution, per-category rollups, Recall@K) is a plain function over already-collected records, with no coupling to how those records were produced (live run or synthetic test fixture).
- **Evaluation result models are entirely separate from the WP-002/WP-015 audit/output contracts** - `CandidateAttemptRecord`/`EvaluationReport`/etc. never extend or reuse `QuestionAudit`/`ExamAudit`/`ExamOutputBundle`, and no WP-015 output function is called by anything in `evaluation/`. `CandidateAttemptRecord` additionally carries the accepted candidate's own question/answer text (`question_text`/`answers`/`correct_answer`, always `None` for a rejected attempt) - added specifically to make WP-017's own required human quality review possible; not used by any metric.
- **`tests/integration/test_end_to_end_pipeline.py`** wires real components (real retrieval/TF-IDF over an in-memory synthetic corpus, real prompt rendering, real provenance validation, real acceptance policy, real exam planning/duplicate-detection, real audit construction) together with a small scripted `FakeLLMProvider` (implements the real `LLMProvider` interface; queues per-response-model canned responses/exceptions) - the only faked component. No real API key or network access is required; this verifies cross-component contracts the unit suites cannot (each unit suite mocks its own immediate collaborators, not the whole chain).

## Reliability Hardening and V1 Acceptance (WP-018)
WP-017's live baseline evaluation found the V1 pipeline's primary bottleneck was operational reliability, not candidate quality or retrieval: 14 of 20 planned questions (70%) hit an operational failure, 9 of those (45% of all 20) an empty-string `QualityValidationResult.reason` at `validation_temperature=0.0`. WP-018 root-caused and fixed this and related structured-output reliability issues, without changing retrieval, the acceptance policy, or adding any generic LLM retry.

- **Root cause (confirmed by direct reproduction, not assumption)**: none of the five validation-result models (`GroundingValidationResult`, `MCQValidationResult`, `CategoryValidationResult`, `QualityValidationResult`, `TextbookCheckResult`) carried `Field(description=...)` metadata, unlike `GeneratedQuestionResponse` (WP-009), which does on every field. Because `OpenAIProvider.generate_structured()` passes the Pydantic model directly as `text_format` to `client.responses.parse()`, the JSON Schema actually sent to the model is auto-derived from the Pydantic model - with no field descriptions, the model receives no schema-level signal that `reason` must be non-empty, only whatever prose the task prompt happens to state (and `quality.txt`/`mcq.txt`/`category.txt` never described the response schema at all - unlike `grounding.txt`, which already had a "Your structured response corresponds to the following fields" section). A controlled reproduction (`client.responses.create()` called directly, bypassing this project's own Pydantic validation, with the real `quality.txt` prompt and a fixed candidate at `temperature=0.0`) confirmed 5 of 8 calls returned `reason=""` (always paired with `valid=True`); adding a `Field(description=...)` to `reason` plus an explicit "required, must never be an empty string" prompt instruction reduced that to 0 of 10 in the same reproduction.
- **Fix applied uniformly across all five validation-result models**: every field of `GroundingValidationResult`, `MCQValidationResult`, `CategoryValidationResult`, `QualityValidationResult`, and `TextbookCheckResult` (`src/exam_generator/models/validation.py`) gained an explicit `Field(description=...)`, matching `GeneratedQuestionResponse`'s existing pattern; `mcq.txt`, `category.txt`, and `quality.txt` each gained a "Your structured response corresponds to the following fields" section identical in spirit to `grounding.txt`'s pre-existing one, explicitly stating every `reason` field is required and must never be empty. `grounding.txt`'s own `reason` description was strengthened with the same explicit non-empty wording for consistency. This is a schema-plus-prompt fix, not a Pydantic-constraint change - `NonBlankStr`'s `reason` validator is unchanged and still fails closed on any empty value that does still occur.
- **Generation/grounding evidence-id provenance wording strengthened (not redesigned)**: `question.txt` and `grounding.txt` already required copying `evidence_chunk_ids` character-for-character (WP-010); both gained an explicit "if you are not confident of the exact identifier, leave this list empty rather than guessing" instruction, since an empty list was already a legitimate, accepted value and the fix only needed to make that more clearly the model's fallback. `_validate_generated_provenance()`/`_validate_supporting_evidence_ids()` (the strict application-side rejection of any invented id) are unchanged.
- **Textbook provenance redesigned from verbatim-text reproduction to stable-identifier citation (the one contract change WP-018 made)**: `TextbookCheckResult` gained `evidence_chunk_ids: list[NonBlankStr]` (mirroring `GroundingValidationResult`'s existing field exactly), now the primary, strictly-verified provenance signal - `_validate_textbook_provenance()` (`src/exam_generator/validation/textbook.py`) checks it against the actually-supplied course-book chunk ids first, raising `InvalidTextbookOutputError` for any invented id, before falling through to the pre-existing `source_page`/`reference_text` checks. `reference_text` is demoted to optional secondary color only (`textbook.txt`: "Citing evidence_chunk_ids is sufficient and preferred - you do not need to also supply reference_text") rather than removed, since a mismatch there is still rejected when the model does supply it. This was chosen over further strengthening the existing verbatim-quoting instruction (WP-013/WP-014's already-twice-patched approach) because `SourceEvidenceChunk.chunk_id` is already a deterministically available, exact-match identifier - the same mechanism `GroundingValidationResult` already uses successfully - making free-text verbatim reproduction of arbitrary-length course-book excerpts an unnecessarily fragile way to establish the same provenance fact. `schemas/exam_audit.schema.json` was regenerated (`scripts/generate_schemas.py`) to reflect the new field.
- **New deterministic, non-LLM structural quality check (`src/exam_generator/validation/structural.py`)**: `detect_duplicated_answer_numbering()` is a pure, regex-based function - no LLM call - that flags a candidate whose answer choices redundantly repeat leading enumeration numbering inside their own text (e.g. `"1. ..."`), the exact defect WP-017's human review found the LLM-based `QualityValidator` missed once. It requires at least 2 of the 4 answers to match (`^\s*\d+\s*[.):]\s+` at the very start of the answer), so an isolated legitimate leading number (or ordinary numeric content like "12 pairs of cranial nerves", which the pattern never matches at all since it requires a `.`/`)`/`:` separator immediately after the digits) is never falsely rejected. `QualityValidator.validate()` runs this check first; if it finds a defect, it returns `QualityValidationResult(valid=False, reason=<mechanical explanation>)` directly, **without making an LLM call at all** - mirroring `TextbookValidator`'s existing empty-retrieval short-circuit pattern (an "at most one LLM call" validator, not "exactly one"). This is a narrow, single-purpose check, not a general heuristic quality engine - it looks for exactly this one artifact.
- **No generic automatic LLM retry was added anywhere** - WP-013's bounded quality-driven regeneration (`max_generation_attempts`) remains the only retry mechanism in the system; a `LLMProviderError`/`InvalidGroundingOutputError`/etc. still propagates immediately and is never silently retried.
- **Evidence (before/after, live evaluation, identical methodology to WP-017)**: two independent live runs, same 5 categories x 2 questions/run as WP-017's own baseline, combined in `evaluation/evaluation_report_wp018_combined.{json,md}`. Operational failures: 1 of 25 attempts (4%) - one residual invented `evidence_chunk_ids` in grounding validation - versus WP-017's 14 of 20 planned questions (70%). Zero empty-`reason` failures occurred (WP-017: 9, the dominant failure mode). Zero duplicated-answer-numbering defects were found among 19 accepted candidates on manual re-inspection (WP-017: 1, in a 4-question sample). Retrieval was deliberately untouched and confirmed unchanged: Recall@3=86.5%, Recall@5/@8=94.6%, identical to WP-017. A final representative CLI acceptance run (`exam-generator generate`, 2 categories x 2 questions, both generation modes) produced all 4 questions on the first attempt with exit code 0.
- **V1 acceptance decision: V1 ACCEPTED WITH KNOWN LIMITATIONS.** The dominant, previously-blocking reliability defect (the empty-reason failure class) is fixed and evidenced as fixed, not merely tested. A residual, much-lower-rate provenance-invention failure mode remains (now ~4% of attempts, was ~20% combined across generation/grounding/textbook in WP-017) - this is a known V1 limitation, not a blocker, because the existing strict provenance checks continue to correctly reject it (fail closed) rather than silently accepting fabricated evidence; it is recorded here for a future WP to revisit if the rate does not continue to fall. TF-IDF retrieval remains accepted for V1 - WP-018 found no evidence to reconsider WP-017's conclusion.

## Bounded Generation-Contract Recovery and Failure Context (WP-019)
A real full-exam acceptance run (20 categories x 4 questions requested) failed immediately at the first planned question: a single `InvalidGeneratedOutputError` (invented `evidence_chunk_ids`) propagated as an uncaught operational failure and aborted the entire exam, with no indication of which planned question had failed. WP-019 addressed both problems without weakening strict provenance.

- **Generation-contract failures became a third, distinct recovery class, owned by `QuestionProducer`** - alongside WP-013's existing candidate-quality regeneration. `produce_question()` now catches `InvalidGeneratedOutputError` specifically around the `QuestionGenerator.generate_candidate_question()` call: the fabricated response is discarded completely (never repaired/normalized/guessed at), recorded as a failed attempt, and the loop continues - consuming the *same* bounded `max_generation_attempts` budget candidate-quality rejections already share, not a new parallel budget. No validator ever runs for a discarded response.
- **`QuestionAttempt`/`QuestionAttemptAudit` gained an alternate outcome shape** - `candidate`/`validations` (or the audit's four primary validator fields) became optional, paired with new `generation_failure_type`/`generation_failure_message` fields, guarded by a `model_validator` enforcing exactly one outcome is ever populated. A generation-contract-failure attempt never fabricates a candidate or validation result for a response that never became one.
- **Exam-orchestration failure context**: `QuestionProductionFailedError` gained `operational_cause`. `ExamOrchestrator._produce_unique_question()` now catches a curated tuple of known operational-error types (`LLMError`, `GenerationError`, `GroundingValidationError`, `TextbookValidationError`, `RetrievalError`, `PromptError`, `pydantic.ValidationError` - mirroring `exam_generator.evaluation`'s own `KNOWN_OPERATIONAL_ERROR_TYPES` precedent from WP-017) around the producer call and wraps *any* of them - not only WP-013 exhaustion - with `"Exam generation failed at question X/N (category=..., generation_mode=...). Completed questions: N. Cause: ..."`, chained via `raise ... from exc` so the original exception remains fully inspectable. A genuinely unexpected exception (not in that tuple) still propagates raw with its full traceback - never silently reclassified as an expected failure.
- **No generic retry was introduced.** Only `InvalidGeneratedOutputError` specifically is recoverable; auth/rate-limit/network/retrieval/prompt/config failures, other validators' operational failures, and candidate-quality/provenance rejections all remain exactly as bounded (or unbounded-but-immediate) as before.

## Structured-Output Transient Recovery (WP-020)
The subsequent real 2-per-category acceptance run (post-WP-019) completed 16 of 40 questions before failing with a raw `pydantic.ValidationError` obtaining a `GroundingValidationResult`: `Invalid JSON: EOF while parsing a string`. Tracing the failure path (`OpenAIProvider.generate_structured()` -> `client.responses.parse()` -> the OpenAI SDK's internal `post_parser` callback -> `parse_text()` -> `model_parse_json()`, i.e. `response_model.model_validate_json(raw_text)`) confirmed this is a genuine SDK-internal call, invoked synchronously inside `.parse()` itself - not a network/HTTP failure (the HTTP round-trip already succeeded), not a refusal, and not caught by any of `OpenAIProvider`'s existing `openai.*` exception handlers (which only cover HTTP/auth/rate-limit/connection failures) - it was a raw `pydantic.ValidationError` escaping the provider completely uncaught. The truncated response's trailing run of literal `\n` characters is a classic `max_output_tokens`-cutoff signature, though pydantic-core does not expose enough granularity to safely distinguish "truncated by a token limit" from "otherwise syntactically broken JSON" - both surface identically.

- **A precise, empirically-verified distinction separates a structural parse failure from a domain-level rejection.** Reproducing both cases directly against the real models confirmed: a response whose text cannot be parsed as JSON at all raises `pydantic.ValidationError` with exactly one error of type `json_invalid`; a response that parses successfully but violates one of this project's own constraints (e.g. `NonBlankStr`'s non-empty check) raises `type=value_error` (or `missing`/etc. for other constraint kinds) instead. `_is_malformed_structured_output(exc)` (`src/exam_generator/llm/openai_provider.py`) checks specifically for `len(exc.errors()) == 1 and exc.errors()[0]["type"] == "json_invalid"` - never a blanket `except ValidationError: retry`. Under OpenAI's `strict: True` structured-output mode, type/enum/required-ness violations are already guaranteed impossible server-side, so in practice these are the only two ways a `ValidationError` reaches this layer at all.
- **Retry ownership is the provider itself, not `QuestionGenerator`/`QuestionProducer`/any validator** - deliberately different from WP-019's provenance recovery, which the provider cannot own (it has no concept of application provenance). A malformed/unparseable structured response is something the provider *does* understand: it owns the messages, the response model, the structured API invocation, and the conversion into that model, so it is the narrowest layer able to recognize "the call completed, but usable structured output was not obtained." `generate_structured()` retries the *exact same physical request* (same messages, same response model, same profile parameters) - nothing about the request is regenerated, re-retrieved, or altered between physical attempts.
- **One logical structured-output operation may now involve up to `1 + structured_output_retries` physical API calls, but always exactly one logical result.** Before WP-020 these were 1:1. A structured-output retry is never represented as a new `QuestionAttempt`, a new candidate-production attempt, or a new validator call in any audit/evaluation record - it is purely internal to one `generate_structured()` invocation. If both physical calls fail, the *logical* operation fails operationally (`LLMStructuredOutputError`), exactly like any other single operational failure the layers above already know how to propagate/contextualize (WP-019's orchestration-level wrapping applies unchanged, since `LLMStructuredOutputError` is an `LLMError` subclass already in the known-operational-error tuple).
- **New provider-independent error type**: `LLMError` -> `LLMResponseError` -> `LLMStructuredOutputError`, raised only once the bounded retry is exhausted, chained via `from exc` so the original `pydantic.ValidationError` remains inspectable. Never used for authentication, rate limiting, connectivity, provider HTTP failures, refusals, application provenance violations, or prompt/configuration failures - each of those keeps its own existing, unchanged exception type and still makes exactly one physical call.
- **Configuration**: `LLMConfig.structured_output_retries` (`config/llm.yaml`, `StrictNonNegativeInt`, default `1`, bool rejected) - the number of retries *after* the initial physical call (`0` = one call total, `1` = at most two). No backoff/jitter/interval/retry-matrix configuration was added - WP-020 is one small bounded number, not a resilience framework.
- **Observability without a logging framework**: `OpenAIProvider.structured_output_retry_events` exposes a tuple of `StructuredOutputRetryEvent` (`response_model_name`, `profile`, `attempts_made`, `recovered`) - recorded only for logical operations that actually needed a retry (never for a clean first-call success), inspectable by any caller holding a reference to the provider instance (evaluation/smoke-test code, tests). Carries no prompt/message content or secrets.
- **No generic retry, no auth/rate-limit/network retry, no backoff/jitter, was introduced anywhere.** `LLMAuthenticationError`, `LLMRateLimitError`, `LLMProviderError` (connection/status), and `LLMRefusalError` all still make exactly one physical call and propagate immediately, unchanged from before WP-020 - existing behavior for these was deliberately left untouched (WP-020 sections 15-17).

## Validator Provenance Recovery (WP-021)
A 20-question controlled reliability sample (post-WP-020) measured a residual, purely stochastic exam-killing failure: `GroundingValidator` occasionally returns a syntactically valid `GroundingValidationResult` that claims `evidence_chunk_ids` never actually supplied - correctly rejected as `InvalidGroundingOutputError` (fail-closed, exactly as designed), but with no retry at all, one bad roll of the model terminates the entire exam even though the candidate itself may be perfectly valid. WP-021 adds a third, narrowly-scoped recovery mechanism for exactly this class, without weakening strict provenance in any way.

- **A third distinct recovery mechanism, deliberately kept separate from WP-019 and WP-020.** WP-019 recovers a *generation-contract* failure (the candidate itself never became usable) by discarding the whole candidate and generating a fresh one, consuming a `QuestionProducer` attempt. WP-020 recovers a *provider-level structured-output* failure (the physical response couldn't even be parsed as JSON) by repeating the exact same physical API call. WP-021 recovers a *validator provenance* failure (the response parsed fine and is otherwise well-formed, but claims evidence it was never given) by repeating the exact same *logical* validation call - same candidate, same already-retrieved evidence (retrieval happens exactly once per `validate_grounding()`/`validate()` invocation, never repeated), same prompt, same response model, same `LLMProfile.VALIDATION`. All three mechanisms compose cleanly and independently: a single physical grounding call can itself use WP-020's bounded recovery, and that whole logical call can itself be one of WP-021's (at most two) logical attempts - four physical calls in the worst case, still exactly one `QuestionAttempt`.
- **Retried only when a syntactically valid response claims unsupplied provenance** - `GroundingValidator.validate_grounding()`/`TextbookValidator.validate()` each wrap their existing provenance check (`_validate_supporting_evidence_ids()`/`_validate_textbook_provenance()`, both unchanged in logic) in a small bounded loop: on `InvalidGroundingOutputError`/`InvalidTextbookOutputError`, discard the response completely (never repaired/normalized/guessed at - the same fail-closed contract as always) and resubmit the identical request once more. A normal negative verdict (`passed=False`, or a textbook `NOT_FOUND`/`POTENTIAL_CONFLICT`) is never retried - it is returned immediately as the valid, successful result it is. Any operational failure (auth/rate-limit/network/prompt/retrieval/other-`ValidationError`) is never caught here and propagates exactly as before.
- **Textbook is subject to the identical failure class, and all three of its provenance checks are retryable, not just `evidence_chunk_ids`.** Inspection confirmed `_validate_textbook_provenance()` raises the same `InvalidTextbookOutputError` for an invented `evidence_chunk_ids` entry, an invented `source_page`, or a non-matching `reference_text` - each represents the identical "the model claimed provenance it was never actually supplied" stochastic mistake, not three different failure classes, so all three are retried uniformly by discarding and resubmitting the whole response (never per-field repair).
- **No shared base class was introduced** (WP-021's own explicit instruction) - `GroundingValidator`/`TextbookValidator` each own their own small, near-identical retry loop; `MCQValidator`/`CategoryValidator`/`QualityValidator` are untouched, since none of them owns factual evidence provenance.
- **Retry count is a documented validator-level constant** (`_MAX_PROVENANCE_RETRIES = 1` on each of the two validators), not new YAML configuration - deliberately, since this is internal recovery policy for one validator's own logical-call boundary, not an application-wide or LLM-transport-level setting the way WP-020's `structured_output_retries` is.
- **Attempt semantics unchanged**: a provenance retry never creates a new `QuestionAttempt` - it is fully internal to one validator call, exactly as WP-020's structured-output retry is internal to one `generate_structured()` call. `QuestionProducer` has no visibility into, and requires no changes for, either mechanism.
- **Observability**: `GroundingValidator.provenance_retry_events`/`TextbookValidator.provenance_retry_events` (each a tuple of `ProvenanceRetryEvent`: `validator`, `attempts_made`, `recovered`) - recorded only for logical operations that actually needed a retry, mirroring WP-020's `StructuredOutputRetryEvent` pattern exactly but kept in its own `exam_generator.validation.models` module (not merged with the LLM-layer event type, since these describe an application-level, not provider-level, retry).
- **`מבוא` remains untouched by this WP**, per its own explicit scope exclusion - a separate diagnostic (`evaluation/ver020_mavo_retrieval_diagnostic.md`) found it "limited but sufficient for 2 questions," not grounds for category-specific production policy; `max_generation_attempts` remains 3, unchanged.

## LLM-Facing Validator Evidence References (WP-022)
A read-only diagnostic (`evaluation/ver021_local_reference_diagnostic.md`) traced the exact grounding-provenance path end to end and found that nothing downstream ever required the *LLM itself* to reproduce a canonical `SourceEvidenceChunk.chunk_id` string - only that the *application* ultimately possesses one. WP-022 acts on that finding: the grounding and textbook LLM contracts now ask for small, call-local evidence references instead of canonical identifiers, reducing how often WP-021's provenance retry is even needed, without weakening the underlying invariant at all.

- **The existing `[Evidence N]` prompt labeling (`_format_evidence_chunk()`, `prompts/formatting.py`, unchanged) is the mechanism** - each evidence item was already rendered with a 1-based positional label; WP-022 simply asks the model to cite that label instead of the `Chunk:` line's canonical string. The formatter itself was **not** touched, since it is shared with generation (`GenerationPromptContext`), which remains explicitly out of WP-022's scope and still relies on the canonical `Chunk:` line being present.
- **New LLM-facing response models, mirroring `GeneratedQuestionResponse`'s established pattern**: `GroundingValidationResponse`/`TextbookValidationResponse` (`src/exam_generator/models/validation.py`) carry `evidence_refs: list[int]` (1-based, matching the displayed `[Evidence N]` labels) in place of `evidence_chunk_ids`/canonical identifiers. `TextbookValidationResponse` is deliberately smaller than `TextbookCheckResult` - it drops `source_page`/`reference_text` as LLM-facing fields entirely, since both become derivable deterministically once a reference resolves to a real `SourceEvidenceChunk`. Neither response model is ever exposed beyond its validator.
- **Resolution happens entirely inside the validator, immediately after strict reference validation**: `_resolve_grounding_response()`/`_resolve_textbook_response()` (`src/exam_generator/validation/{grounding,textbook}.py`) bounds-check every reference against `1..len(supplied_evidence)` - treating zero, negative, and out-of-range values identically, so every case benefits equally from WP-021's retry - then construct the existing, unchanged `GroundingValidationResult`/`TextbookCheckResult` with genuine canonical `evidence_chunk_ids` resolved from the actual supplied evidence. No fuzzy matching, clamping, or substitution exists anywhere in this path; an invalid reference is rejected exactly as an invented canonical string was before.
- **`TextbookCheckResult.source_page` is now deterministically derived from the first resolved evidence chunk** (never claimed by the LLM); **`reference_text` is always `None` going forward** - there is no deterministic equivalent of a short human-readable excerpt once verbatim reproduction is no longer required from the model, and manufacturing one from the full chunk text would change the field's meaning without adding provenance value already covered by `evidence_chunk_ids`. The field remains on the contract (not removed) for downstream/schema stability - an honest, documented absence, not a fabricated value.
- **WP-021's retry loop required no structural change.** Retrieval and `messages` construction already happened exactly once, before the retry loop, in both validators - the identical `[Evidence N]` mapping is therefore automatically reused across every physical/logical retry, with no risk of renumbering or re-retrieval, confirmed directly from the code (not merely assumed) during the diagnostic.
- **WP-020 remains fully independent, confirmed from the code, not assumed**: a local reference like `9` (out of range) is syntactically valid JSON - WP-020's malformed-JSON detection (`_is_malformed_structured_output()`, keyed on a single `json_invalid` pydantic-core error) never sees it at all; it reaches the validator's own bounds-check exactly like an invented canonical string did before.
- **Generation, `historical_reference_id`, MCQ/category/quality validators, retrieval, and `מבוא`'s treatment are all explicitly unchanged** - WP-022 addresses only the measured grounding/textbook provenance-failure class, per its own scope exclusions.

## Partial Exam Completion and Per-Question Failure Reporting (WP-023)
Every WP-018-022 acceptance run chased one specific residual failure class to exhaustion; the next run then hit a *different* one, always aborting the entire exam at whatever question happened to fail. WP-023 is a deliberate architectural pivot away from that pattern: rather than continuing to chase the last failure mode, `ExamOrchestrator` now distinguishes a **question-local failure** (safe to record and continue past) from a **system-level failure** (must still abort immediately), so an isolated per-question failure no longer discards every other successfully-produced question in the run.

- **The question-local/system-level split is deliberately minimal, not a redesign of WP-019's operational-failure concept.** Only the failure classes WP-023 explicitly names are question-local: WP-013's own `QuestionAttemptsExhaustedError` (attempt-budget exhaustion), WP-021's `InvalidGroundingOutputError`/`InvalidTextbookOutputError` (provenance-recovery exhaustion), and duplicate-replacement exhaustion (WP-014's own exam-level duplicate protection). Everything else that was already in WP-019's `_KNOWN_OPERATIONAL_ERROR_TYPES` tuple - `LLMError` (including `LLMResponseError`/`LLMStructuredOutputError`), `GenerationError`, `GroundingValidationError`'s/`TextbookValidationError`'s other members (e.g. `NoValidationEvidenceError`), `RetrievalError`, `PromptError`, and a raw `pydantic.ValidationError` - remains system-level, unchanged. This was a deliberate, conservative choice (WP-023 section 6: "do not guess"): two pre-existing, deliberately-written integration tests (`test_invalid_structured_validator_output_is_an_operational_failure`, `test_structured_output_retry_exhaustion_is_a_contextualized_exam_failure`) already asserted that a raw `ValidationError` and an exhausted `LLMStructuredOutputError` must still abort the whole exam - an earlier, broader draft classification that treated these as question-local directly contradicted that established intent and was reverted before implementation.
- **`_KNOWN_OPERATIONAL_ERROR_TYPES` (WP-019) is now two tuples in `orchestrator.py`**: `_QUESTION_LOCAL_ERROR_TYPES` (`InvalidGroundingOutputError`, `InvalidTextbookOutputError`) and `_SYSTEM_LEVEL_ERROR_TYPES` (everything else, unchanged in membership from WP-019's original tuple). `QuestionAttemptsExhaustedError` is handled in its own `except` clause, as before, since it carries its own `.attempts` history.
- **`_produce_unique_question()` no longer always raises on failure - it returns a discriminated result.** Its return type became `QuestionProductionRecord | FailedPlannedQuestion`: a question-local failure (any of the three cases above) is *returned* as a new `FailedPlannedQuestion` (`orchestration/models.py`) rather than raised, exactly as a validator's negative verdict is already a normal, non-exceptional result rather than an exception - WP-023 extends that same established principle one layer up, to orchestration. A system-level failure still *raises* `QuestionProductionFailedError` immediately, exactly as WP-019 established; a genuinely unexpected exception is still left uncaught.
- **`QuestionProductionFailedError` is narrowed to represent only a system-level abort.** Its `attempts_exhausted`/`duplicate_productions` fields (which used to represent the two question-local cases) were removed - those cases no longer raise this exception at all - leaving only `planned_question`, `completed_productions`, and a now-required `operational_cause`.
- **`FailedPlannedQuestion` reuses existing models rather than duplicating them** (`planned: PlannedQuestion`, `failure_type`, `failure_message`, `attempts: tuple[QuestionAttempt, ...]` for attempt-budget exhaustion, `duplicate_productions: tuple[QuestionProductionResult, ...]` for duplicate-replacement exhaustion - at most one of the two is ever non-empty). Whatever attempt/production history genuinely exists is preserved; nothing is fabricated for a failure that happened before any attempt record could be built (e.g. WP-021 provenance exhaustion, which carries no attempts at all).
- **`generate_exam()`'s loop now continues past a question-local failure** instead of letting the first raised exception propagate: each planned question's result is inspected, `FailedPlannedQuestion`s accumulate into a list, successful `QuestionProductionRecord`s accumulate into another, and the loop always reaches the end of the plan unless a system-level failure raises. `ExamGenerationStatus` (`COMPLETE`/`PARTIAL`, in `models/audit.py` since both the orchestration result and the audit need it) reflects whether any planned question failed.
- **Clean-exam numbering is renumbered contiguously 1..N over accepted questions only, never gap-preserving** - `candidate_to_exam_question(candidate, number)` is now called with the accepted-only enumeration index (`enumerate(productions, start=1)`), not `planned.position` directly, since a failed planned position leaves no clean-exam slot to preserve (worked example: planned 1 accepted/2 failed/3 accepted/4 accepted -> clean exam numbers 1, 2, 3, not 1, 3, 4). Each production's original planned position remains fully available via `QuestionProductionRecord.planned.position` - the two are no longer the same value once a failure has occurred earlier in the plan, matching `ExamOutput`'s own pre-existing contiguous-numbering validator (WP-002, unchanged) without requiring any change to it.
- **`ExamGenerationResult` gained `status`, `failed_questions: tuple[FailedPlannedQuestion, ...]`, and `exam: ExamOutput | None`** (previously always a required `ExamOutput`). `exam` is `None` only when zero planned questions were accepted (every planned question failed locally) - `ExamOutput.questions` structurally requires at least one question (`Field(min_length=1)`, WP-002, deliberately left unweakened per WP-023 section 22's own instruction not to casually loosen that constraint) and there is no honest non-empty exam to construct in that edge case. A `model_validator` enforces `len(plan) == len(productions) + len(failed_questions)`, `exam is None` only when there are zero productions, and `status` agrees with whether `failed_questions` is empty.
- **The audit contract gained the same status/count/failed-question representation, without weakening the numbering split.** `QuestionAudit` gained `planned_position` (the original plan position) alongside the existing `number` (now purely the final, contiguous clean-exam number) - the smallest extension that avoids overloading one field with two meanings, per WP-023 section 16. `ExamAudit` gained `status`, `planned_question_count`, `accepted_count`, `failed_count`, and `failed_questions: list[FailedQuestionAudit]` (a new sibling model to `QuestionAudit`, carrying `planned_position`/`category`/`generation_mode`/`failure_type`/`failure_message`/`attempts`); `questions`'s pre-existing `Field(min_length=1)` was relaxed to `default_factory=list`, since a `PARTIAL` result with zero accepted questions is now a legitimate, representable state (WP-023 section 22's own edge case) - `failed_questions` carries the detail in that case instead. Two `model_validator`s enforce the count bookkeeping (`accepted_count == len(questions)`, `failed_count == len(failed_questions)`, `planned_question_count == accepted_count + failed_count`, status/failed_count agreement) and that every planned position 1..`planned_question_count` is represented in exactly one of `questions`/`failed_questions`, never both and never neither. `schemas/exam_audit.schema.json` was regenerated; `exam_output.schema.json`/`exam_request.schema.json` are unaffected.
- **`output/audit.py`'s docstring/module-level claim that "a rejected/exhausted `ExamGenerationResult` never reaches this layer" is now false and was corrected** - a `PARTIAL` result reaching `build_exam_audit()`/`build_exam_output_bundle()` is a normal, legitimate case since WP-023; only a genuinely system-level failure still aborts before any result reaches this layer at all. `_validate_consistency()` was extended (not replaced) to also check the failed-question count and each failed question's planned-position/category/generation_mode correspondence, alongside its pre-existing accepted-question checks (now driven by the new contiguous numbering rather than `planned.position` directly).
- **`ExamOutputBundle.exam` became `ExamOutput | None`**, mirroring `ExamGenerationResult.exam` exactly, for the same all-failed edge case. `write_exam_output_bundle()` (`output/serialization.py`) skips writing the exam file (writing only the audit) when `bundle.exam is None`, rather than failing on a `None` `ExamOutput`.
- **CLI reporting distinguishes `COMPLETE`/`PARTIAL`/system-level-fatal, and `PARTIAL` exits `0`.** `_run_generate()` writes both outputs (or just the audit, in the all-failed edge case) once orchestration safely reaches the end of its plan, regardless of status - the pre-existing "serialize both before writing either" and atomic-write behavior are unchanged, just now also applied to a `PARTIAL` result rather than only a `COMPLETE` one. A `COMPLETE` result prints the pre-existing one-line success message; a `PARTIAL` result prints a distinct report (`Exam generation completed with partial results.` / `Requested: N` / `Generated: M` / `Failed: K` / each failed planned question's position, category, mode, and failure type/message) and still returns `EXIT_SUCCESS` - per WP-023 section 21's explicit preference for exit `0` absent a concrete compatibility reason otherwise, and because `PARTIAL` must never be conflated with the genuinely fatal case. `_classify_error()`'s `QuestionProductionFailedError` mapping (still `EXIT_GENERATION_FAILURE`) is unchanged in meaning, now exclusively covering system-level aborts; its `QuestionAttemptsExhaustedError`/`GenerationError`/`GroundingValidationError`/`TextbookValidationError` branches were removed as genuinely unreachable (those failure types no longer propagate out of `generate_exam()` at all).
- **No retry-ownership changes anywhere** (WP-023 section 12, explicit): WP-013's `max_generation_attempts`, WP-019's generation-contract recovery, WP-020's structured-output retry, and WP-021's provenance retry are all completely unchanged - WP-023 operates strictly after those mechanisms reach their own normal outcome (success, or the specific exhaustion exceptions above), never adding another retry layer inside `ExamOrchestrator`.
- **Out of scope, per WP-023's own explicit exclusions**: no generation-side local evidence-reference fix for WP-022's own residual `תאי מערכת העצבים`/INDEPENDENT generation-provenance-hallucination finding (deferred to a future WP-024), no change to `max_generation_attempts` or any category-specific attempt budget, no retrieval/acceptance-policy/validator changes, no REST API/GUI/checkpoint-resume features.

## Generation-Side Local Evidence References (WP-024)
WP-022 removed fragile canonical chunk-ID reproduction from grounding/textbook *validation* by asking the model for small, call-local `evidence_refs` instead. Generation itself still used the older mechanism - the LLM had to reproduce a canonical `SourceEvidenceChunk.chunk_id` verbatim - and WP-022's own targeted diagnostic found this was now the dominant remaining generation reliability problem (a highly reproducible invented chunk id). WP-024 applies the identical, already-proven WP-022 pattern to generation.

- **The final provenance boundary, end to end**: the generation LLM cites a local `evidence_refs: list[int]` (matching the "[Evidence N]" labels already shown in the prompt); `QuestionGenerator` deterministically resolves those references, immediately after the structured response returns, into genuine canonical `SourceEvidenceChunk.chunk_id` values; the LLM is never trusted to manufacture canonical provenance itself. This mirrors WP-022's `LLM cites [Evidence N] -> application resolves N -> canonical id` boundary exactly, now applied one layer earlier in the pipeline.
- **`GeneratedQuestionResponse.evidence_chunk_ids: list[NonBlankStr]` became `evidence_refs: list[int]`** (`src/exam_generator/models/question.py`), field description adapted from WP-022's grounding/textbook wording. Every other field on the response model, and the rest of the generation contract, is unchanged.
- **`CandidateQuestion`'s own schema is deliberately untouched** - it never carried an evidence field before WP-024 (a pre-existing WP-015 decision: `QuestionGenerator` already validated-then-discarded any claimed provenance rather than persisting it onto the candidate, since independent grounding validation never trusts generation's claims anyway) and still does not after it. The resolved canonical ids exist only transiently, inside the one function that validates them, and are never attached to anything downstream.
- **`_resolve_generated_evidence_refs()` (`src/exam_generator/generation/generator.py`) mirrors WP-022's `_resolve_grounding_response()`/`_resolve_textbook_response()` pattern exactly**: every reference is bounds-checked against `1..len(source_evidence)` - zero, negative, and out-of-range values all rejected identically - raising the existing, unchanged `InvalidGeneratedOutputError` (no new subtype was justified) rather than repairing/clamping/fuzzy-matching. A repeated reference (e.g. `[1, 1, 3]`) resolves to its canonical id only once, preserving first-occurrence order (`dict.fromkeys()`) - deliberate, since a duplicate citation is not additional evidence of anything a single citation didn't already establish. `_validate_generated_provenance()` now calls this resolver first (triggering the same fail-closed check the old string-based check performed), then continues to its pre-existing, unchanged `historical_reference_id` validation.
- **Prompt wording updated to match** (`prompts/generation/question.txt`): the "if you report which evidence supports your answer" instruction was rewritten to ask for the "[Evidence N]" number instead of copying the "Chunk:" identifier - explicitly telling the model not to reproduce that identifier, since the shared evidence formatter (`_format_evidence_chunk()`, unchanged, still shared with grounding/textbook validation) continues to render it as informational text. No other generation instruction was touched.
- **`historical_reference_id` is deliberately unchanged** - a small integer id has never been the reliability problem WP-022/WP-024's diagnostics identified, and generalizing the local-reference pattern to it was explicitly out of scope.
- **WP-019/WP-020/WP-021/WP-022/WP-023 all remain unchanged, confirmed rather than assumed**: an invalid `evidence_refs` value still raises `InvalidGeneratedOutputError`, so WP-019's existing bounded generation-contract recovery (discard, retry within the same `max_generation_attempts` budget) continues to work automatically with no code change; a malformed/truncated physical response is still WP-020's own concern (a syntactically-valid-but-out-of-range integer is not malformed JSON, so `_is_malformed_structured_output()` never sees it); WP-021/WP-022's validator-side local-reference implementations were not touched or refactored to share code (the two resolution functions are structurally similar but deliberately not merged into a shared utility, per WP-024's own "avoid premature abstraction" instruction - each is a handful of lines, tied to a different response/result model shape); WP-023's question-local-vs-system-level distinction and `PARTIAL`-result semantics are exercised unchanged (an exhausted generation-contract recovery from an invalid local reference is still question-local via `QuestionAttemptsExhaustedError`, exactly as before). No new retry layer was introduced anywhere.
- **Schemas unaffected**: `GeneratedQuestionResponse` is an LLM-facing intermediate model never exported into `exam_request`/`exam_output`/`exam_audit` JSON Schemas (confirmed by re-running `scripts/generate_schemas.py` - byte-identical output for all three).

## Evidence-Grounded Question Target Planning and Within-Category Diversity (WP-025)
WP-024 achieved the first fully `COMPLETE` real acceptance run (40/40 accepted), but human review of that exam found a real exam-construction quality problem WP-024 itself could not have caught: multiple questions requested from the same category were often near-duplicates of each other - testing the same fact reworded, or the same relationship approached from the opposite direction - even though each one individually passed every validator cleanly. The problem was never candidate validity; it was that nothing had ever decided, *before* generation, that two requested questions from one category should test different things. WP-025 introduces a planning step that makes diversity a property of what is asked for, not something enforced (or missed) after the fact.

- **The conceptual flow gained one new stage, inserted once per category, before any generation for that category begins**: `category -> retrieve factual evidence -> plan N distinct evidence-supported question targets -> {target 1 -> generate -> existing validators, target 2 -> generate -> existing validators, ...}`. Diversity is achieved primarily *by construction* - deliberately not by generating arbitrary questions and using WP-013's three-attempt budget to reject duplicates after the fact (WP-025's own explicit non-goal).
- **New `src/exam_generator/planning/` package (`planner.py`)**, structurally a sibling of `generation/`/`validation/`/`production/`/`orchestration/`/`output/`, not a submodule of any of them: `QuestionTargetPlanner.plan_targets(*, category, count) -> list[QuestionTarget]`. Every dependency is injected explicitly (category resolver, student-summary retrieval index, prompt repository, LLM provider) - the identical wiring pattern `QuestionGenerator` already uses, reusing the exact same `retrieve_for_category()` call and index rather than inventing new retrieval behavior (retrieval itself is explicitly unchanged by this WP).
- **`QuestionTarget` (`src/exam_generator/models/target.py`)**: a generation *plan*, never a generated question, a validator verdict, or an accepted exam question - `target_id`, `category`, `topic`, `factual_focus`, `supporting_evidence_chunk_ids` (genuine canonical ids, already resolved - never a raw LLM claim). Lives in the shared `models/` package (not `orchestration/models.py`, where `PlannedQuestion` lives) because it is consumed across three layers (planning, orchestration, generation), the same reason `CandidateQuestion` lives there rather than in any one layer's own module.
- **Planner provenance reuses WP-022/WP-024's proven local-reference pattern exactly, one layer earlier**: `QuestionTargetPlanningResponse`/`PlannedQuestionTargetResponse` (LLM-facing, `models/target.py`) carry `evidence_refs: list[int]` - small, call-local, 1-based references matching the "[Evidence N]" labels already shown in the prompt - never canonical chunk id strings. `_resolve_planned_targets()` (`planning/planner.py`) bounds-checks every reference against `1..len(source_evidence)` (zero/negative/out-of-range all rejected identically) and resolves valid ones to genuine canonical `SourceEvidenceChunk.chunk_id` values, reusing the existing `InvalidGeneratedOutputError` (no new subtype was justified) rather than inventing a parallel error hierarchy. A single invalid reference anywhere in the response discards *every* target from that attempt, never partially repaired - the same fail-closed philosophy WP-022/WP-024 already established, applied uniformly rather than per-field.
- **The planner may legitimately return fewer targets than requested - never more, never fabricated.** This is the WP's answer to limited-content categories (the kind VER-020's earlier diagnostic found for `מבוא`, generalized rather than special-cased): the prompt explicitly instructs the model to return fewer genuinely distinct targets rather than inventing artificial diversity, and a stochastic planner-provenance defect (an invalid local reference) degrades internally to "zero usable targets from this attempt" rather than raising or retrying - deliberately, since WP-025 explicitly forbids adding another hidden retry layer, and a single planning hiccup must never be able to abort an otherwise-healthy 40-question exam. `plan_targets()` makes exactly one LLM call, exactly like `QuestionGenerator.generate_candidate_question()` - no retry loop of any kind lives in this layer.
- **A planned position beyond the number of targets actually planned becomes question-local, not system-level**: `ExamOrchestrator.generate_exam()` (`orchestration/orchestrator.py`) now groups the deterministic plan by category (preserving the plan's own overall position order exactly, since `build_exam_plan()` already assigns positions category-by-category), calls `plan_targets(category, count)` once per category, and - for any planned position with no corresponding target - records a `FailedPlannedQuestion` (`failure_type="InsufficientDistinctTargetsError"`) directly, **without ever calling the producer** for it. This is deliberately not a candidate-production problem, so it never consumes WP-013's `max_generation_attempts` budget (WP-025 section 10's explicit, critical requirement). A genuine system-level failure while planning (provider/auth/rate-limit failure, or `MissingEvidenceError` - reused unchanged from `generation.errors`, for the rare case of literally zero retrievable evidence for the category, distinct in kind from "evidence exists but doesn't support N *distinct* targets") still aborts the whole run immediately via the existing `QuestionProductionFailedError`, contextualized against that category's first planned position - exactly mirroring how a system-level candidate-production failure already behaves; WP-023's `PARTIAL`/`COMPLETE` semantics and every other question-local/system-level classification are completely unchanged.
- **Generation receives its assigned target explicitly, and the target remains fixed across every retry.** `QuestionGenerator.generate_candidate_question()` and `QuestionProducer.produce_question()` both gained a required `target: QuestionTarget` parameter (no default - every call must be deliberate about which target it targets); `GenerationPromptContext` gained a required `target` field, enforced to belong to the same category as the call itself. `_produce_unique_question()` passes the same `target` object into every one of its bounded duplicate-replacement retries, and `QuestionProducer`'s own WP-013/WP-019 attempt loop never asks the planner for anything - the target is orchestration's concern, decided once, before any attempt begins; a rejected/duplicated candidate is retried toward the *same* target, never a newly-planned one (WP-025 section 9's explicit requirement, verified directly by test).
- **The prompt makes genuine diversity explicit, not left to the model's judgment of "different enough"**: `prompts/generation/question_target_planning.txt` (new; `PromptId.QUESTION_TARGET_PLANNING`) explicitly rules out four specific classes of superficial "diversity" the WP-024 human review actually observed - reworded phrasing, question/answer inversion, the same structure-plus-property tested differently, and the same narrow relationship approached from opposite directions - all illustrated with the spinothalamic-tract/hippocampus examples from the WP itself. `prompts/generation/question.txt` gained a new "Assigned question target" section instructing the model to test specifically its assigned target, never silently switching to an easier fact, and never letting a `STYLE_SIMILAR` historical reference (style only, never factual authority - an invariant already established since WP-008 and left completely unchanged) override the planned factual focus.
- **No additional post-generation diversity validator was added.** WP-025 section 11 explicitly required first determining whether target-identity-by-construction plus the existing generation constraints are sufficient before adding one, and to prefer the simpler design; this WP's live evidence (see the acceptance-run diversity review below) was judged sufficient without one - documented here as a deliberate decision, not an oversight, and revisitable if future evidence shows target-based planning alone is insufficient.
- **Count is fully general, not hard-coded to 2** - `plan_targets(category, count)` accepts any positive count, and the category-grouped orchestration loop above works identically whether a category requests 1, 2, or 4 questions; no code path assumes exactly two.
- **`מבוא` (and every other category) receives no special-case treatment anywhere in this WP** - the honest-shortfall mechanism is fully general, per the WP's own explicit instruction; if `מבוא`'s evidence supports fewer distinct targets than requested, that surfaces through the identical `InsufficientDistinctTargetsError` path any other limited-content category would.
- **Schemas are unaffected** - `QuestionTarget`/`QuestionTargetPlanningResponse`/`PlannedQuestionTargetResponse` are never exported into `exam_request`/`exam_output`/`exam_audit` JSON Schemas (confirmed by re-running `scripts/generate_schemas.py` - byte-identical output for all three); no audit-model field was added to persist a target, mirroring the existing, deliberate `CandidateQuestion`-carries-no-evidence-field precedent (WP-009/WP-015) rather than introducing a new provenance-persistence pattern for this one case.

## Target-Aware MCQ Framing (WP-026)
WP-025A's diagnostic of WP-025's 4/40 acceptance-run failures found a single shared structural cause: every failed `QuestionTarget` had an *enumeration/classification-shaped* `factual_focus` ("X consists of/is divided into A, B, C"), and generation was converting these literally into "recall the full list" questions - a form that produces several simultaneously-defensible answer choices and fails `MCQValidator`. WP-026 fixes this at the generation-prompt level only, per its own explicit required sequencing (attempt a generation-only fix first; a planner-prompt change is permitted only if live evidence later shows it necessary).

- **Core distinction made explicit to the model**: a `QuestionTarget` describes WHAT knowledge to test, not a literal sentence to reproduce. *Narrowing* within the target - selecting one specific, evidence-supported relationship contained in it (one member, one distinguishing property, one location, one function) - is allowed, and required whenever the target as literally stated would not support a clean one-best-answer question. *Switching* to a different, easier, or unrelated fact from the evidence is still forbidden, unchanged from WP-025.
- **`prompts/generation/question.txt` gained four new prose sections** (no new template variables - `PromptRepository`'s `required_variables` set is unchanged, so no Python code was touched anywhere in this WP): target-vs-literal-form and narrowing permission; "Testing enumeration or classification targets" (recognize the shape, prefer one member + one distinguishing property over full-list recall, illustrated with a concrete worked white-matter-fibers example contrasting weak vs. strong framing); a distractor-construction rule forbidding recombination of the target's own enumerated members as distractors; and "Nested or hierarchical classifications" (make the hierarchy level being tested explicit in the question's wording; a true classification from an adjacent hierarchy level is not an acceptable distractor merely because it is real - written generically, with no category name, since the rule must generalize beyond the one diagnosed case). The `STYLE_SIMILAR` historical-reference guidance was also updated: if the historical reference's own form would itself produce an ambiguous enumeration-style question, that form must not be copied - producing a valid one-best-answer question always takes priority over matching historical form.
- **No validator was added or weakened, no attempt-limit change, no planner change.** `QuestionTargetPlanner` and `max_generation_attempts` are unchanged from WP-025; the fix is entirely upstream-of-validation prompt guidance.
- **Live verification**: a focused 4-target control run reused the exact same four `QuestionTarget`s that failed in WP-025's acceptance run (from the WP-025A diagnostic). Result: 4/4 accepted (WP-025A baseline: 3/4, with the fourth - a PNS autonomic/somatic-vs-sympathetic/parasympathetic hierarchical case - exhausted twice, 6/6 attempts, across both the WP-025 acceptance run and WP-025A's own control run). The previously-reproducibly-failing case succeeded this time on attempt 2, using explicit "basic division" hierarchy-level wording. A supplementary informal second probe on that same hardest case (run afterward, for completion-report detail only, not part of the sanctioned control run) exhausted again with the same adjacent-hierarchy-level ambiguity recurring - recorded honestly as a known limitation: the fix meaningfully improves but does not fully eliminate this specific failure mode's stochasticity. See `implementation/WP-026_COMPLETION_REPORT.md` for the full acceptance-run result and diversity re-review.

## Candidate Question Validation
Generation and validation are separate operations.

A question is acceptable only if at minimum:
- student-summary grounding exists;
- claimed correct answer is supported by retrieved evidence;
- no alternative answer is equally correct based on the supplied context;
- exactly four choices exist;
- category is appropriate;
- structured output validates.

Frozen domain-contract decisions (WP-002):
- Answer IDs are 1-based (1..4) throughout the domain model, both in the external exam-question contract (`answer1`..`answer4` + `correct_answer`) and the internal `CandidateQuestion` representation.
- `GroundingValidationResult.passed` is centralized derived logic: a grounding result passes if and only if `grounded AND correct_answer_supported AND other_answers_not_equally_correct` are all true. Callers must use this property rather than re-deriving the rule.
- Grounding `confidence` is bounded to `[0.0, 1.0]` but does not by itself determine pass/fail.
- A candidate question's own generation output never carries a self-reported "grounded" claim; grounding is established only by the independent validator's result.

## Diversity and Retry
- Alternate `STYLE_SIMILAR` and `INDEPENDENT` generation modes per category.
- Similarity is allowed.
- A configurable diversity/differentiation target may be progressively relaxed if necessary to fulfill requested counts.
- Grounding and factual-validity requirements are never relaxed.

## Textbook Check
Secondary and initially non-authoritative. Statuses are frozen (WP-002) as exactly:
- `CONSISTENT`
- `NOT_FOUND`
- `POTENTIAL_CONFLICT`

A potential conflict is surfaced in audit data. It does not silently replace student-summary grounding. A `CONSISTENT` result does not itself satisfy student-summary grounding, and a missing/absent textbook check does not invalidate an otherwise properly grounded question.

`TextbookCheckResult.evidence_chunk_ids` (WP-018) is the primary, strictly-verified provenance signal, mirroring `GroundingValidationResult.evidence_chunk_ids`. Since WP-022, the LLM never claims this (or `source_page`) directly - both are resolved/derived deterministically by `TextbookValidator` from the model's call-local evidence references (see "LLM-Facing Validator Evidence References (WP-022)"). `reference_text` remains on the contract but is always `None` - no longer LLM-facing at all.

## Output Contracts
Domain models: `src/exam_generator/models/`. Machine-readable JSON Schemas (generated from those models via `scripts/generate_schemas.py`): `schemas/exam_request.schema.json`, `schemas/exam_output.schema.json`, `schemas/exam_audit.schema.json`.

### Exam JSON
V1 top-level contract is `{"questions": [...]}` (an object with a `questions` array), not a bare JSON array — frozen by WP-002 (`ExamOutput`). Question numbers must be unique and form the contiguous sequence `1..N`. Each question contains only clean fields, no traceability/audit information:
- `number`
- `question`
- `answer1`
- `answer2`
- `answer3`
- `answer4`
- `correct_answer`
- `category`

### Audit JSON
Contains internal traceability, including source evidence and validation diagnostics. Top-level contract (`ExamAudit`, WP-002): `exam_id` (non-empty), `generated_at` (timezone-aware datetime; naive datetimes rejected), `provider`, `model`, and a non-empty `questions` list of per-question `QuestionAudit` entries (unique question numbers enforced). Does not contain the clean exam itself, and does not track token usage/cost in V1.

Each `QuestionAudit` entry's `grounding`/`mcq_validation`/`category_validation`/`quality_validation`/`textbook_check` fields represent the final, accepted attempt's results; `attempts` (added WP-015, non-empty list of `QuestionAttemptAudit`) additionally preserves every attempt - including rejected ones - each with its own `attempt_number`, `accepted` flag, and independent copy of all five validation results. `historical_reference_id` and `evidence` are populated by WP-015's audit construction as `None`/`[]` respectively - both genuinely unavailable from current production history (see "Exam Output and Audit Trail (WP-015)" above), not fabricated.
